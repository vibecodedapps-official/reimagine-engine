# Requirements: 0.1.0

Drafted 2026-10-14 from the product specification. Architecture is in architecture.md, the order of work in build-plan.md, the hand-run checks in acceptance.md, and the choices with their evidence in decisions.md. Where this document and the architecture disagree, this document wins until it is amended. Nothing here is implemented.

Each requirement ends with how it is checked:

- **test**: an automated test under `tests/`, run by `npm test` and CI.
- **lint**: a rule in `tools/lint.mjs`, run by `npm run lint` and CI.
- **acceptance**: a hand-run item in acceptance.md, recorded with date, machine and CLI versions.
- **review**: checked by reading, once, in the pull request that merges it.

A requirement that rests on a spike names the spike in decisions.md. If a later run of that spike fails, the requirement is amended before the milestone that depends on it merges.

Numbers are never reused. A retired requirement keeps its number with the word "Retired" and the reason.

## Suite

1. **One repository, one marketplace.** The marketplace is named `reimagine-engine` and lists exactly six plugins: `rules`, `loop`, `audit`, `primer`, `gate` and `guard`, each at `plugins/<name>/`. Before a release a prerelease catalog may list a plugin that is built at a prerelease version (requirement 14), so a second machine can install it from `main` before its release, and may list `repo-docs` until requirement 268 retires it. Until the gate's scaffold milestone the catalog, lint's name list, the README and the repository's hub say four plugins, and that milestone moves all of them to five in one commit (decision 132). Amended 2026-11-04: six with `guard`, all moved in one commit of M73 (decision 181). Check: lint.
2. **Plugin directories hold only what a user installs.** Under `plugins/<name>/` there are the manifest, the skills, commands, agents, hooks, scripts, output styles and reference files the plugin uses at run time, plus `README.md` and `LICENSE`. No tests, no design documents, no fixtures. Check: lint.
3. **ASCII.** Every shipped file under `plugins/` is ASCII. Check: lint.
4. **License per plugin.** The root `LICENSE` and each `plugins/<name>/LICENSE` is the Apache License 2.0 text with the holder line `Copyright 2026 vibecodedapps.net`. Check: lint.
5. **Prerequisites.** Node 22 or later and, on Windows, Git for Windows. The audit plugin's live checks, work-item validation and collision check also need `jq`; the README says so and says what runs without it. No other tool is required. Amended 2026-11-04: `guard` also needs `git` and the `claude` command on the PATH, since its script runs both as child processes (decision 181). Check: review.
6. **Prompt first.** The only executable files under `plugins/` are `plugins/rules/scripts/rules.mjs`, the eleven audit scripts (`readonly.sh`, `handoff.sh`, `ledger.sh`, `working-tree.sh`, `revert-tests.sh`, `live.sh`, `memory.sh`, `work-items.sh`, `collisions.sh`, `run-copies.sh`, `report.sh`), the two primer hooks `plugins/primer/hooks/drift.sh` and `plugins/primer/hooks/notice.sh`, the three gate scripts `plugins/gate/scripts/findings.mjs`, `plugins/gate/scripts/next.mjs` and `plugins/gate/scripts/split.mjs` (requirement 318), and `plugins/guard/scripts/guard.mjs` (requirement 334). Every one of them has a test under `tests/`. A new script ships only with its test. A workflow script under `plugins/audit/workflows/` is an executable whose check is `node --check`, the lint rule of requirement 219 and acceptance item 43, because its runtime needs a session (decision 95); none ships until requirement 270's gate is met. Check: lint.
7. **No plugin options.** No manifest declares `userConfig`, and no file references `${user_config.*}`. Check: lint.
8. **Five hooks outside a request.** Only five hooks run without a session request: the rules SessionStart staleness notice, the primer SessionStart memory notice, the primer drift check, the guard SessionStart staleness notice and the guard PermissionDenied denial record. No other plugin ships a `hooks/hooks.json`. Check: lint.
9. **Independent plugins.** `loop` and `audit` do not require `rules`; no manifest declares `dependencies`. Each plugin works alone after `/plugin install <name>@reimagine-engine`. Check: lint; acceptance.
10. **Reusable files carry nothing owner-specific.** No shipped file names a person, a person's email address (an address at a `.invalid` domain is allowed), an absolute path under a user's home, or a specific repository other than this one. Check: lint.
11. **Nothing external names a model, agent or tool.** Pull request bodies, pull request comments, ticket comments and commit messages name the activity and the date, never the model, the agent type or the tool that produced the text, never a review pass or its level, and never another term the suite or a run coined. A commit message of `/audit:act` follows the repository's convention (requirement 194) and carries a date only where that convention does (decision 264). Run records and reports kept in a run directory, and a record attached to a ticket, may name them. Amended 2026-10-27: review passes and levels are added (decision 141). No plugin types an attribution trailer of its own or removes one the host's attribution setting adds; that setting decides alone (decision 136). Amended 2026-11-09: terms the suite or a run coined are added, and a record attached to a ticket may carry them (requirement 349, decision 220). Check: review; acceptance.
349. **What leaves a run.** The loop's, the gate's and the audit's `SKILL.md` each carry the item of requirement 348 word for word, on one line, as the one list item under a `## What leaves the run` heading, since each plugin works alone (requirement 9) and the house rules block may be absent or stale in the user's instruction file (decision 221). Lint fails when a skill has no such section, when the section holds another number of list items than one, whatever their marker, or when the item is not one `- ` line that equals an item of `core.md` with its lines joined and has nothing under it that a Markdown reader would add to it (decision 244); the `rules-feedback` skill names the three copies. A run's working output (verdicts, pass lists, levels, commit ids, manifests, logs, handoff context) stays in the run directory or a record attached to a ticket; a pull request gets what its reviewer needs about its code; a ticket gets what changed for its readers, what happens next and who decides. Primer and guard post nothing and carry no copy. What the item asks before a post is prose in the item and its copies, held by lint and by tests of each plugin's posting text; no hook enforces it (decision 226). Check: lint; test; review.
12. **Commit form.** Commits in this repository and commits the loop makes read `type(scope): subject` in lowercase, with a body that says why. A bare `@token` in a subject or pull request text is written in backticks. Check: review.
13. **Moves and renames apart.** A commit that moves or renames files changes no file content; string renames go in their own commit. Check: review.

The first release is 0.1.0; before it a built plugin may ship as `0.1.0-alpha.<n>`, a semver prerelease that sorts below 0.1.0, and the 0.1.0 target of every plugin stands. ### Mechanism

22. **One target.** The target file is `$CLAUDE_CONFIG_DIR/CLAUDE.md`, else `~/.claude/CLAUDE.md`. It is created when missing. There is no other target. Check: test.
23. **Bytes outside the block are kept.** Every byte before the begin marker and after the end marker is preserved, including a byte order mark, bytes that are not UTF-8, the file's line ending, and a missing final newline. Check: test.
24. **Symlinks.** A target that is a symlink is written through, at the file it points to. A dangling or hard-linked target is refused without writing. Check: test.
25. **Block format.** The block starts with `<!-- reimagine:house-rules begin version=<v> options=<list> join=<none|blank|newline> digest=<16 hex> -->` and ends with `<!-- reimagine:house-rules end -->`. The digest is of the body in LF form; a CRLF file gets a CRLF block. Check: test.
26. **States.** A target is `absent`, `current`, `stale`, `edited`, `malformed` or `declined`. A version change alone with the same rules is `current`. A malformed block is reported with its line numbers and nothing is written. Check: test.
27. **Plan then apply.** `plan` writes a plan file in the plugin data directory and shows the diff, one hunk per changed run, with three lines of context. `apply` refuses when the target changed after the plan, including a file created where none was. Check: test.
28. **Ask per change.** The skill shows the diff and asks before `apply`, once per target change. Check: review; acceptance.
29. **Backup.** An existing target is copied to `<path>.reimagine-backup-<YYYYMMDDHHMMSS>` before any write; an existing backup is never overwritten and the write does not happen. A created file has no backup and `remove` deletes it unless the user added text, in which case only the block is removed. Check: test.
30. **Atomic writes.** The target is written to `<path>.reimagine-tmp-<pid>` and renamed into place, keeping permissions. Two applies started at once both land in the state and plan files; a lock directory `rules.lock` serializes them and a lock left by a dead run is taken over. Check: test.
31. **Remove.** `remove` takes out the block and the bytes of its join, so install then remove gives back the original bytes for LF, CRLF, BOM and no-final-newline files. Check: test.
32. **Decline.** `decline` records the digest; the next plan says so and the staleness notice stays quiet until the shipped text changes. Check: test.
33. **Adopt.** `plan --adopt` finds rules already present outside the block, as a Markdown reader sees them (items, paragraphs, headings; not fences, HTML comments or indented code), removes a full copy including its headings, and puts the block where the copy was. Text that differs, fenced examples, and user text under a heading are kept. A file holding Markdown that adopt does not handle is left alone and the plan recommends decline. Check: test.
34. **Recommendation.** The plan counts the rules already outside the block and recommends `apply`, `adopt` or `decline`; decline only when every rule is already present. Check: test.
35. **Imports.** `@path` imports in the target are followed read-only: at a line start or after white space, not in code, fences, quotes or the block; relative to the importing file, from `~/`, or absolute; four hops; fifty files; 256 KiB per file; a directory, an oversized file or a missing nested file is a read error, not a skip. The plan names what each import holds. Check: test.
36. **Options.** `core` is always applied; `windows` is added on Windows and refused elsewhere. Recorded options are kept on a rerun unless `--options` overrides them. Check: test.
37. **Script output.** A refusal is one line on stdout starting `rules: ` with exit 1; `status` exits 0. Check: test.
38. **Script size.** `rules.mjs` is at most 700 lines and imports only `node:` built-ins. Check: lint.
39. **The skill never edits the file itself.** `/rules` runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs <verb> ${CLAUDE_PLUGIN_DATA}` with the Bash tool, which its `allowed-tools` pre-approves, and relays its output; it never writes `CLAUDE.md` with the Edit or Write tool. The skill sets `disable-model-invocation: true`. Check: lint; review.
40. **The skill names the output style.** `/rules` ends by printing how to select the output style: `/output-style rules:Concise Plain`, or the equivalent `/config` path. Check: review; acceptance.
41. **Staleness notice.** The SessionStart hook, matcher `startup` only, runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs session-start ${CLAUDE_PLUGIN_DATA}` and prints one `systemMessage` line, `rules: the house rules in <path> are older than this plugin's; run /rules to update them`, when the block is `stale` and not declined. It prints nothing otherwise, writes nothing, and exits 0 even when the state file cannot be read. Check: test; acceptance (the message is visible at startup).
42. **Line-ending changes do not hide staleness.** A block whose file changed line ending still reads as current or stale by its rules, and a hand edit still reads as edited. Check: test.

## The `loop` plugin

### Invocation

45. **Prose invocation.** The skill is `run` in the `loop` plugin, so it answers as `/loop:run`; it is user-invocable and its description names "reimagine loop" as the primary phrase and "run the loop" as a secondary one. There is no separate command. The bare `/loop` belongs to the host's bundled interval skill and is not ours. There are no flags; a token starting with `--` is read as prose. 46. **Reading block first.** After only the read-only calls that resolve ids (`git remote`, `gh`, `az`, an MCP read, a file read) and before any other tool call, the skill states how it read the request in one block with four headings: Tickets, Mode, Scope, Effort. The reading block's Scope line names the checkout in use. When the named checkout is a linked worktree, the record of requirement 82 lives in its main checkout, the first `worktree` line of `git -C <checkout> worktree list --porcelain`, and the detached-worktree run of requirement 80 does not apply: a differing flagged path there ends `blocked`, naming the path and the main checkout, which "primary <main checkout>" runs with the exception. Without the phrase, `<checkout>` is the toplevel of the session's repository, which `git rev-parse --show-toplevel` prints, and preflight ends `blocked` when that command fails; when `git rev-parse --show-prefix` prints a prefix, the session started below the toplevel, and the primary's commands run in the forms above, counted as prompts the same way, since the host returns the shell to the session's start folder after a call that ends outside it; the record root stays that toplevel, the handoff and the manifest name it as the primary's repository, and a relative exclude path that `git rev-parse --git-path info/exclude` prints is read against the folder `git -C` names (decision 218). The word is "primary", not "in", because the remaining request text is joined into the ad-hoc description and "in" occurs in prose; it mirrors the Scope line. Check: review; test (the phrase in SKILL.md and the README, and the checkout the handoff names); acceptance (item 45).

Step 0.2 fetches it with the same explicit refspec, a fetch that fails ends `blocked` naming the branch, and `run.md` and the reading block's Mode line record it (`; base <branch>`). It is the review base (requirement 88), the pull request base (requirement 116) and the branch whose workflow files the deploy judgment reads (requirement 56). Check: review; test (the phrase in SKILL.md and the README; the key in the configuration block); acceptance (item 45).

54. **What invoking approves.** Invoking the loop by name approves, for that run only: creating a branch, committing, pushing that branch, opening one pull request per repository, editing the body of a pull request this loop opened, commenting once per run on that pull request, commenting on the source tickets, and, for the open items of requirement 351, opening a ticket or commenting on an existing one and attaching a record to each ticket the run comments on or opens. The loop never removes an ask-first rule. In multi-repository runs the rules of every repository are unioned. Check: review; acceptance.

Check: review.

### Roles and models

60. **Orchestrator.** The session model orchestrates, judges, reviews each slice diff and decides; it never implements a slice. No fallback: without it the run stops. Check: review.
61. **Implementer.** Each slice is implemented by an Agent subagent at model `sonnet`, one per slice, parallel for slices with disjoint files, serial otherwise. Parallel implementers run no checks and say so; the orchestrator runs each slice's checks afterwards one command at a time, and a command several slices name runs once. Check: review; acceptance.
62. **Plan reviewer.** A fresh-context Agent subagent at model `opus`, given the request text, the file paths and the required reply shape, told to read and report only, reviews the plan in step 3. On a model or tool error the call is retried once at the `fallback-reviewer` model, `sonnet` by default, or, when that model is the reviewer's own, at `sonnet`, or at `opus` for a reviewer on `sonnet`, and the swap is recorded and named in the report; a denial or a timeout is not an error. The reviewer stays swapped for the rest of the run. Step 5 has no fresh reviewer; its one pass is requirement 63. Amended 2026-11-05: `opus` in place of `fable`, and `sonnet` as the retry, so no default selects the top tier and the retry still changes model (decision 182). Check: review; acceptance.
63. **Final review role.** Every run's step 5 uses the built-in `code-review` skill with an explicit level (requirement 285) and the range `<merge-base>...HEAD` as a full sha, never `--comment` or `--fix`; `code-review` covers the primary whenever it is the session's checkout, a linked worktree included; where that skill is not listed, or the diff lives in a worktree that is not the session's checkout or in an additional repository, an Agent subagent at `opus` reviews a patch file with the acceptance criteria and the same reply shape, with the level word passed as its `effort` (`xhigh` where the word was "max", requirement 285), once, retried once at `sonnet` on an error. The stand-in is not a swap and is named in the report, with its retry. Amended 2026-11-05: the retry one tier down (decision 182). Check: review; acceptance.
64. **Reader.** Read-only work worth splitting out runs on `haiku`; the orchestrator may instead read itself. Check: review.
65. **Model configuration.** `.reimagine.json` `models` accepts `implementer`, `reviewer`, `fallback-reviewer` and `reader`, each one of `sonnet`, `opus`, `haiku`, `fable`. It never changes the risk floor or the step 5 role. Unknown keys and bad values are reported and ignored. Check: review; acceptance.
66. **Agent calls carry the request shape.** A plan review asks for a numbered list of objections ranked by impact, each marked blocking or non-blocking with a confidence of high, medium or low and a one-line reason, ending with `NO BLOCKING OBJECTIONS` when there are none, and asks the reviewer to name the code that reads each contract change and confirm the shapes match, and, for every data change, to confirm that each read-only companion of it, such as a listing kept as its rollback record, reads the same rows the write touches (decision 203). Blocking means the change would ship wrong behavior, break an acceptance criterion, or violate a repository rule. The `opus` stand-in of requirement 63 receives the plan, the inputs, the acceptance criteria and a patch file written from `git diff <merge-base>` after new files are marked with `git add -N`; the `code-review` skill reads its range itself. An empty diff is never sent to review. Check: review.

### Budgets and rounds

67. **Per-call budgets.** Minutes: `subagent` 20 for an implementer call, `review` 30 for a review pass, `check` 15, `ci` 45. `.reimagine.json` `timeouts` overrides any of them; `run` sets the run budget. Where a tool takes a timeout the budget is passed; the Bash foreground cap is 10 minutes, so a longer check runs in the background beside a background `sleep` of its budget, since a background command notifies only when it ends, and whichever ends first stops the other. An Agent or SendMessage call is judged against its budget by the `duration_ms` of its completion notification, and by `date` before and after it only when the notification carries none; when an implementer call returns the orchestrator records its checkout's status and file hashes as `post-<n>`, beside the call's `pre-<n>`; a notification that arrives for an implementer call after that call already returned is not a new call and changes nothing unless a path differs from `post-<n>` that no later call, edit or commit of the run changed, which ends the run `blocked` naming the path; any other late notification, or one for an agent the run did not launch, is logged and changes nothing; the implementer brief tells the implementer to start no background command (decision 149). Check: review.
68. **Run budget.** The default run budget is 240 minutes, overridden by "budget <n> minutes" in the request, then `timeouts.run`, then a session instruction. Waits on questions are excluded. On expiry the output is kept and the run ends `blocked`, naming the budget; after a push the pull request is left as it is. Check: review.
69. **Risk floor.** A change that adds, alters or removes an auth check, a permission rule, a schema or migration, a row-level security policy, a data access path, or a public API's signature or behavior, directly or through shared code or configuration, is floored: reviewers receive effort at least `high`, and the report says which trigger applied. Incidental edits (a typo in a migrations README, a comment in an auth module, a rename with no signature change) do not trigger it. For a schema, migration or data access change, the floor also asks whether every read-only companion of it reads the same rows the write touches (decision 203). The floor is judged at the plan and again on the actual diff after step 4, and never falls. Check: review; acceptance.
70. **Higher-risk rule.** Retired 2026-10-25 (decision 128): the rule selected only the step 5 role, which requirement 63 now fixes for every run; the risk floor of requirement 69 alone sets the step 5 level (requirement 285). Check: review.
71. **Date discipline.** `date -u +%Y-%m-%dT%H:%M:%SZ` runs only at the start of step 0 and of each step, before and after each timed call (for a batch of Agent calls, before and after the batch, while each call's budget is judged by its notification, requirement 67), after each push returns, at the terminal state, and just before and after each question. Times are copied into the record from the command output, never from memory or arithmetic. Check: review.
72. **Round cap.** No step repeats more than three times. A round is one pass by the stage's reviewer plus the fixes it leads to. The orchestrator's single fix after the step 4 cap is not a round; step 5 has one pass per run and no round (requirement 111). Each CI repair cycle gets one step 5 pass and one full step 6 run; cycles are capped at three. Check: review.

The one exception is a worktree run, which writes the `.reimagine/` exclude, the record directory and the worktree at step 0.3; from then a failure writes the report to the record. Check: review.

A remote is Azure DevOps when its host is `dev.azure.com`, `ssh.dev.azure.com` or `vs-ssh.visualstudio.com`, or ends in `.visualstudio.com`; preflight records that and the remote's organization and project. Check: review; test; acceptance.

77. **Continue checks.** A continued branch must pass `git check-ref-format --branch` and must not be checked out in another worktree (the failure names the three ways around it: start the run inside that worktree, "primary <that path>", or "also edit <that path> on <branch>"). A branch with a record may exist locally only, as after a `prepared` run, or nowhere, as after a plan-only run, and is then created like a new branch; when it also exists on the remote, the local tip must be at or behind the remote head and is fast-forwarded to it. 79. **Clean tree.** `git status --porcelain` must be empty and `git diff --cached --quiet` must pass, else `blocked`; the loop never stashes, resets or cleans. Check: review; acceptance.
80. **Flagged files.** Paths marked skip-worktree or assume-unchanged are compared against HEAD with `git cat-file --filters`; a difference with a clean status creates a worktree, detached at the start commit, at `<checkout-parent>/<checkout-name>-reimagine-<branch-slug>`, beside the checkout and never inside it. Dependencies are installed in the worktree before the baseline, else the check is "not run". A switch in a worktree detaches in place and fast-forwards with `git fetch .`. Check: review.

Check: review; test (the configuration block in the skill is byte-identical to the README's and has exactly those keys).

### Record and idempotency

82. **Record location.** The record lives at `.reimagine/loop/<branch-slug>/` in the primary repository's record root of requirement 281, a toplevel and never a folder below it, where the slug is the branch name lowercased with every run of characters outside `[a-z0-9]` replaced by `-`, at most 60 characters, then trailing `-` removed. `.reimagine/` is added to `.git/info/exclude`, never to `.gitignore`. Nothing under `.reimagine/` is ever staged. `steps.json` records the exact branch name; a record whose branch differs from the run's branch is a slug collision and ends `blocked`. Amended 2026-11-09: the requirement now states the trailing `-` removal that `SKILL.md` already makes, since the name of a record attached to a ticket relies on it (decision 228). Check: review; acceptance.
83. **Branch known at preflight.** The branch is the continued one, the "on branch" one, the branch of the one existing record whose `tickets` list holds one of the request's tickets (several such records stop the run), or the predicted name: `fix/<ids>-<slug>` when a ticket is labeled bug or titled "fix", else `feat/<ids>-<slug>`, else `work/<slug>`; a collision with an existing local or remote branch that has no record ends `blocked`. A record whose pull request merged or closed ends `blocked`, naming the pull request and the "on branch" form that starts a new branch. Check: review.
84. **Record files.** `inputs.md` (invocation block with time, each ticket as fetched, files and text, verification notes, drift corrections, buildable status, risk floor), `plan.md` (plan plus a review log per round), `run.md` (the durable log), `steps.json` (the completion record), `report.md` (every terminal state), `handoff.md` and `audit-manifest.json` with the exports it names (when the run has its own commit, requirement 355), patch and snapshot files, and `pr-body.md` and comment bodies, which are never committed. Check: review.
85. **Completion record.** `steps.json` holds the branch, a list of runs with number, start, end and terminal state, and one entry per step with `status` (`running`, `complete`, `failed`, `skipped`), the run number, start and end, the hashes of its inputs (for Steps 1 and 2, each open input's version: an issue's `updatedAt`, a work item's `rev`, a case's `SystemModstamp`, or the hash of a file or description), and its output paths. The entry is written `running` when the step starts and `complete` only after its outputs exist; it is written through a temporary file and a rename; it is the only record of completion. Check: review; acceptance.
86. **Second run appends.** A second invocation on the same branch appends run `n+1` to the same record; `run.md` and `inputs.md` gain a dated section per run; nothing from a prior run is modified except `steps.json`, `plan.md` (appended), and `report.md`, `handoff.md`, `audit-manifest.json` and the exports (rewritten). Per-run files without a counter (the pull request body, ticket comments, patches) take a `-run<n>` suffix from run 2 on, so none is overwritten. Check: acceptance.
87. **Preflight reads the branch state.** On an existing record the loop lists `git log <merge-base>..<tip>`, where the tip is the remote head when the branch exists on the remote, marks every commit either as its own (named by a commit line the loop wrote in `run.md`) or foreign, writes the list to `inputs.md`, and judges tickets done by their recorded closing commit. Check: acceptance.
88. **Review base.** Every diff review and every "changed lines" count uses the merge-base with the base branch of requirement 76, so foreign commits are reviewed with the loop's own. Check: review.
89. **Built slices are not rebuilt.** A slice whose closing commit is on the branch is skipped; a ticket with a closing commit is marked done. A slice the loop built to `complete` and did not commit records its file hashes, and a slice whose call failed or that is still `running` records none, so its partial edits never count as committed, each `git hash-object --no-filters -- <path>` of the working copy, the `--` keeping a path that starts with `-` from being read as an option, and counts as committed when the branch tip holds them, as after a `prepared` run that the user committed: for each path, `git cat-file -e <tip>:<path>` succeeds, since a path the tip lacks would hash as the empty blob, and the recorded hash equals either `git rev-parse <tip>:<path>`, the blob as committed, or `git cat-file --filters <tip>:<path> | git hash-object --stdin --no-filters`, the blob as a checkout writes it; under `core.autocrlf` the first matches a working copy whose line endings the commit kept and the second one whose endings it converted (decision 152). Check: test (the hash command and the `steps.json` example in `record.md`); acceptance (item 60).
90. **Same tickets, no new work.** An input is done when the plan names a slice that serves it, every such slice has a commit on the branch, and its text is the text it was last planned from: a ticket whose title or the fields that say what it asks for changed, or a file whose text changed, since the latest run whose part of the plan holds it is open again, and the run takes it up like a new input (decision 245). When every ticket is done and the plan has no open slice, the run verifies the checks (step 6). When the work is published (the run that last reached step 7 ended `done` and a pull request is open on the branch), it rewrites the report, posts nothing, commits nothing, and ends `done`, except that it writes the body of its own pull request again when the branch tip is a commit no run made and no logged body describes it (decision 251); otherwise step 7 publishes the committed work. Check: acceptance.
91. **New tickets extend the plan.** New tickets add slices to `plan.md`, which goes through plan review again; the new slices are built and reviewed; the pull request this loop opened gets its body updated once per run with `gh pr edit --body-file <absolute path>` and one comment per run; a pull request the loop did not open gets a comment only and its body is never edited. Check: acceptance.
92. **Interruption safe.** Every step records completion before the next starts. A rerun recomputes the input hashes, reuses every step whose inputs are unchanged and whose outputs exist (step 4 only when its slices are committed), rechecks the tree, and resumes at the first incomplete or changed step. Step 3.7 sets up the checkout in every run that builds or checks. A post is logged when it returns: the pull request in `steps.json` before any other call, a ticket when its filing or comment returns and again when its attach does, a body edit and a pull request comment with the head each describes. A run with nothing to push and no ticket newly filed or found repeats no body edit and no comment that `run.md` logs for that head (decision 246). Check: acceptance.
93. **Never rewrite.** The loop never force pushes, rebases, resets or amends. Before each push it reads the remote head with `git ls-remote`; a head that differs from the one preflight fetched ends the run `blocked` (fast-forwarding belongs to preflight, requirement 77). Check: review; acceptance.
94. **Terminal states.** `done` (pull request open, CI green or not applicable, report written); `plan-only`; `prepared` (every step through 6 complete, publication withheld before any push, with the publish commands); `blocked` (a blocking defect, a denied permission, a budget exceeded, a preflight failure); `stopped` (a question the run cannot decide, before any branch is created). After `blocked` nothing more is published; pushed work stays and is linked. Check: review.
95. **Snapshot before an implementer call.** Before each implementer or fix call the loop records `git status`, a patch and file hashes. After a failed call it restores only paths that were clean before the call; anything else ends `blocked`. Check: review.
96. **Commit snapshot option.** With `.reimagine.json` `commit: true`, each run that publishes commits `docs/runs/<branch-slug>/plan.md` and `report-<n>.md` with state `publishing`. The report is not posted: the run posts on the pull request what it posts without `commit: true`. Amended 2026-11-09: the terminal report is no longer posted as a pull request comment in an external form, since it is run output and the snapshot already carries it (decision 225). Check: review; acceptance.

### Plan (steps 1 to 3)

97. **Verification before planning.** For each ticket the loop reads the inputs, verifies claims (for a bug it reproduces or runs a check that confirms or rejects the explanation), records drift between the ticket and the code in `inputs.md`, and marks each input buildable, partial or blocked. Check: review.
98. **Repository gate.** A candidate checkout (an absolute path in the inputs that `git -C <dir> rev-parse --show-toplevel` maps to a checkout other than the primary, its submodules or the adopted ones, and that the inputs ask to change) triggers the adoption question of requirement 50; one found later ends `blocked`. A submodule path is not a separate repository. Check: review.
99. **Plan content.** `plan.md` holds, per input, scope, acceptance criteria and buildable status; across inputs, shared changes, migrations and API changes, tests, checks, order of work, and slices with disjoint files; per slice, the files owned, the change, criteria, tests, checks and the implementer. Slice count is a plan property. A slice is sized to fit one implementer call within the subagent budget in force (requirement 67), and the plan step names that budget and its source where it says when to split, since a call past it ends the run `blocked`. Check: review.
100. **Plan review rounds.** Each round verifies every objection, revises, appends a review log to `plan.md`, and is done when the reply ends `NO BLOCKING OBJECTIONS` and the orchestrator finds none. A disagreement that is the user's call ends `stopped`; the cap with a blocking objection ends `blocked`. Check: review.
101. **Plan only.** In plan-only mode the run ends `plan-only` after the review, having changed nothing in the tree. A plan confirmation not answered with a clear yes also ends `plan-only`; a change request is another round within the cap; after a yes the clean-tree, flagged-file, branch, remote-head and pull request checks run again. Check: review; acceptance.
102. **Execution setup.** After the plan is final the loop reverifies against the start commit when the planning snapshot differs from it, creates or switches to the branch, discovers the checks and runs the baseline once, and installs plan-added dependencies after the ask-first yes and before any implementer. Check: review.
103. **No comment before the plan.** Nothing is published before the plan is final, and nothing new is published on a blocked run. Check: review.

### Build (step 4)

104. **Slice brief.** Each implementer receives its slice from `plan.md`, the files it owns, the acceptance criteria, the checks, the repository's line-ending convention, the subagent budget in force, and the instruction to change nothing outside its files, add nothing the brief does not ask for, and start no background command. Check: review.
105. **Slice review.** The orchestrator reviews each slice diff with `git add -N` then `git diff <merge-base> -- <slice files>`, checks line endings with `git ls-files --eol`, and sends findings back; three rounds per slice, then one orchestrator fix; a still-blocking finding ends `blocked`. Check: review.
106. **Re-evaluation.** After step 4 the risk floor is judged on the actual diff. Check: review.
107. **Baseline failures.** A check failing on the base is matched by test names, not counts, since some failures are timing-dependent. Check: review.

### Final review (step 5)

108. **Integrate first.** Step 5.1 runs the full suite on the integrated tree and fixes regressions; every later edit is logged. Check: review.
109. **One pass.** Step 5.2 is one pass of the `code-review` skill (requirement 63) over the complete diff from the merge-base, at the level of requirement 285, after `git diff <merge-base> --stat` shows a change; an empty diff is recorded as "no changes" and sent to nothing. The pass has the review budget of requirement 67; a pass past it ends the run `blocked` naming the budget. Check: review.
110. **Triage.** The orchestrator sorts every finding of the pass into one of three buckets with a one-line reason, the buckets of requirement 299: fix (a correctness finding inside the change), defer (reuse, simplification, efficiency, or a pre-existing issue the change did not introduce) and reject (a false positive). A finding matching a rejection recorded in `run.md` or `plan.md` keeps its disposition unless it brings new evidence. The fix bucket is applied in one batch through the implementer of the slice that owns the code, after a snapshot (requirement 95); the orchestrator reads the fix diff as step 4.3 reads a slice, and a fix the read finds wrong goes back to its implementer once, then is restored from the snapshot and its finding deferred with the reason; deferred findings join the open items of requirement 351, or the report's notes when they are not open items, and rejected ones the report's rejected list, and neither touches code. Amended 2026-11-09: requirement 351 takes the deferred findings in place of the retired 119 (decision 223). Check: review.
111. **No second pass.** The skill does not review the fixes again in the same run: step 6 verifies the checks, and the report suggests the gate for a converged review (requirement 120). A CI repair cycle runs one more pass (requirement 127). Check: review.
285. **Step 5 level.** The level typed to the `code-review` skill is the effort word's level in force (`low`, `medium`, `high`, `xhigh`), `high` with no effort word, at least `high` on a floored run (requirement 69), and never above `xhigh`: the word "max" gives `xhigh` to the skill while Agent calls keep `max`, and `ultra` is never typed (decision 122). The level is recorded in `run.md` and in the manifest's `reviews` key (requirement 286). Check: review; test (the level table in `risk.md`).

### Checks (step 6)

112. **Discovery order.** `.reimagine.json` `checks` first, then manifest-defined test, lint, typecheck and build commands (npm scripts, Makefile, pyproject pytest, ruff and mypy, cargo test and clippy, go test and vet, gradlew check), then CI jobs that run those; a CI job not mappable to a local command is deferred to CI, not guessed. With a `checks` key those commands are the ones run, and the manifests and the CI jobs are still read: each CI job that no configured check covers is named as deferred to CI in `run.md` and the report, so a gap shows before publishing. Check: review; test (the key's entry in `SKILL.md` and the README).
113. **Reuse.** Step 6 reuses the step 5.1 run when no edit was logged since. Each failure not matching the baseline is fixed through the owning implementer after a snapshot, as step 5.1 fixes a regression, and step 6 runs again, at most three times before publication, plus one run per CI repair cycle (requirement 127). Check: review.
114. **Not run versus denied.** A check without its resource is "not run" with its exact command and directory; "denied" means only a refused permission. Check: review.

### Publish (step 7)

117. **Body sections.** `pr-body.md` has, in order: What changed (per input, complete or partial, and what changed, with no remainder or deferred item), Where the ticket and the code differ, Decisions for the reviewer (with any commit on the branch that is not the loop's, and whether its review covered it), Checks not run (a check someone must still run names the ticket that tracks it), Follow-ups (one line per ticket filed or commented on for an open item of requirement 351, from the latest line for it across every run of the record, items that share a ticket sharing its line, with its ticket reference, else "none"; the continued comment's Follow-ups lists only the tickets its run filed or commented on), Related pull requests, Closes. Amended 2026-11-09: What changed loses what is left and the deferred items, Follow-ups is added (decision 223), and Drift corrections, the loop's own word, becomes Where the ticket and the code differ (decision 225). Check: review; test.
118. **Ticket comments.** After the pull request is open, one status comment per ticket the run took up, where a ticket done at preflight gets none unless no run has commented on it, written for the ticket's readers as requirement 352 says: what changed for them, stated plainly as complete or partial, what happens next and who it waits on, the pull request link as where to follow it, and what is not done with the ticket that tracks each. The criteria met, not met or not confirmed, each with its evidence, go in the ticket's record, attached as requirement 352 says. GitHub through `gh issue comment`, run alone after its body file is written (requirement 116); Azure DevOps through the MCP tool, else `az boards work-item update --discussion`; Salesforce through its MCP tool; a host without a tool gets the comment text in the report instead. No comment is posted on a blocked run. The text names no run-internal path, model, agent, tool, review pass, level or other term the loop coined. Amended 2026-10-27: review passes and levels are added (decision 141). Amended 2026-11-09: the comment is written for the ticket's readers, its criteria and evidence move to an attached record, and the rule on issues moves to requirement 351 (decision 225). Check: review; acceptance.
119. **Deferred items.** Retired 2026-11-09: a deferred item no longer sits as prose in the pull request body; each open item is settled, put to the user or filed to a ticket (requirement 351), and a deferred finding that is not an open item is a note in the report only (decision 223). Check: review.
351. **Open items.** Added 2026-11-09 (decision 223). Once per run, before any pull request body or comment is written, after the first push or, on a run that ends `prepared`, before its body file is written, each open item of the run is one of three things, recorded in `run.md` with its evidence. An open item a CI repair pass adds is settled the same way. On a pull request this loop opened, the body is edited once more when 7.3 ends without a block, if a repair cycle pushed a commit that makes the body untrue of the new head or its pass filed a ticket; otherwise a ticket it files is named in the report. A run that ends `blocked` or `stopped` before the open items are settled lists each in the report's Open items as open, with its description and why it is owed, for a later run on the branch to settle. Every draft, on any run, is logged in `run.md` and listed in the report's Open items with its files and the commands that file it and attach its record. Check: review; test; acceptance.

## The `audit` plugin

### Invocation

142. **Prose invocation.** The skill `audit` is user-invocable and its description names "reimagine audit". Requests such as "reimagine audit PR 123 and 124 in app, tickets AB#4567 and AB#4580" are read into bundles; a manifest file path is accepted and is what the loop handoff writes. Thin commands `/audit:run`, `/audit:resume`, `/audit:act` and `/audit:handoff` forward to the skill. Each command holds `$ARGUMENTS` unquoted, so a manifest path and the words after it are separate tokens, and only quotes the user typed keep text together. Check: lint (frontmatter); test (`tests/audit/lint.sh` fails on a command file that quotes `$ARGUMENTS`); acceptance (item 68).
143. **Reading block.** After only the read-only calls that resolve ids and before any other tool call, the skill states bundles (repository, pull request or branch and base, tickets), references, sources of truth, claims files, effort hint, budget and model overrides, and how each ticket resolved, naming each ticket whose body was not read. Check: acceptance.
144. **Effort is a hint; size sets the default.** The default tier is `low` for one bundle, one ticket and under 500 changed lines; `medium` up to three bundles, five tickets and under 5,000 lines; `high` otherwise. A hint ("effort high") overrides it. The tier sets the pass-one scopes, how much pass two attacks, and whether the late adversary runs. Check: review.
145. **Manifest.** Keys: `bundles[]` (`repo`, `pr` or `branch` plus `base`, `tickets[]`, `ticket_token`, `run_once`, `head`, `test_command`, `test_run`, `test_paths`, `test_setup`, `test_timeout`), `references[]`, `sources_of_truth[]`, `claims[]`, `scratch`, `forge_exports`, `groups[]`, `questions`, `models`, `budget`, `max_agents`, `_test`. `reviews` (written by the loop, requirement 286) and `gate` (written by the gate, requirement 315) are ignored and not an error, since stage 1 reads only the keys it names (decision 129). A bundle's `checks` (read by the gate, requirement 300) is ignored the same way: stage 1 reads only the bundle keys it names, so a key it does not name is neither read nor an error. Validation messages name the key. Check: review; test (fixture manifests).
146. **Exported forge files.** A ticket or pull request on a host without a tool is supplied as a `file:` export in markdown with frontmatter or JSON; a ticket requires id, url, title, state and description, a pull request id, url, title and body, every file source, exported_by and exported_at; a missing key stops the run with a sentence saying what an export holds and where its format is shown. `forge_exports.command` is recorded, never run. A ticket id takes a form of requirement 138 or stays as the user wrote it; how the ticket resolved, an Azure DevOps or Salesforce MCP tool as `mcp:<tool>`, is recorded beside the id and never as it (decision 261). Check: review; test.
147. **Pause background fetch.** After the reading block the skill tells the user to pause background fetch, for example VS Code `git.autofetch`; `/audit:run` adds no sentence of its own (decision 264). Check: review.

### Stage model

148. **Nine stages.** Orient, digest, domain map, pass one, pass two, second opinion, converge, report, act, in that order with these dependencies: 1 alone; 2, 3 and 4 together; a per-group barrier opens stage 5 when 2 and 3 are done and top-ups finished; 6 after every pass two; 7 the late adversary and the merger; 8 always. A stage whose input is absent is `not_applicable`; a failed stage counts as satisfied and the run ends `partial`. Check: review; acceptance.
149. **Completion record.** `stages.json` holds `plugin_version`, `approvals[]` (`fetch`, `live`, `export-over-1gb`, `background-fetch`, `local-branch`) and per-stage entries with `status` (`running`, `complete`, `failed`, `not_applicable`, `superseded`), `inputs` as file hashes from `git hash-object --no-filters`, `outputs`, `agents[]` (type, requested model, scope, start, end, tokens labeled "task notification, subagent_tokens; scope not documented", duration, result), `swaps`, `superseded`. It is written through a temporary file and `mv -f`, the entry goes `running` at start and final only after the outputs exist and the read-only check passed, and it is the only record of completion. Check: review; acceptance.
150. **Roles.** Digester `haiku`; mapper and merger `sonnet`; auditor and adversary `opus`; second opinion a fresh `adversary` at `opus`. The manifest `models` key overrides any role with `opus`, `sonnet`, `haiku` or `fable`. Agents are launched with the Agent tool as `audit:<role>`, in the background, never as a fork, never general-purpose, each with its own scratch folder. Amended 2026-11-05: the second opinion at `opus` in place of `fable`; `fable` stays an accepted override (decision 182). Check: review; acceptance.
151. **Failure ladder.** Digester, mapper, auditor and adversary: relaunch on the same model, then on `opus`, or on `sonnet` for a role already on `opus`, as a swap, then the scope fails. Merger: the orchestrator merges, a second failure fails stage 7. Second opinion, per batch: relaunch on `sonnet`, or on `opus` for a second opinion already on `sonnet`, as a swap, then stage 6 fails. An agent fails when it returns an error, when its last line is not `status: complete`, or when fault injection marks it failed. Swaps are recorded and named in the report. Amended 2026-11-05: the swap rung no longer names `fable`; it still changes model, since the swap on record recovered a usage-limit failure that a same-model retry would not (decision 182). Check: review.
152. **Queue and budget.** At most `max_agents` (default 8) agents run; launch order digests, maps, pass one; relaunches go first; scope is never merged or dropped to fit. A soft budget applies only to the invocation that gave it; once expired nothing more launches from stages 2 to 7, unstarted stages are recorded `failed` with "not run: budget expired", and the run goes to stage 8. Check: review.
153. **Orient.** Stage 1 refuses partial clones, reading every configuration source before any object is read and setting no variable before a git command, and its baseline refuses one nested in an audited repository (decision 260), asks once for one `git fetch --no-tags --refmap=` into remote-tracking refs, takes the read-only baseline per repository before any other work, builds a working-tree head with `working-tree.sh` when asked, reads forge data into files without passing it through the model, writes the three-dot diffs with `--no-ext-diff`, exports trees by one `git cat-file --batch` stream, prepares revert keys, writes claims, groups, the brief and the stage entry. Check: review; test.
154. **Digest.** Applicable when a source of truth is a document corpus (more than half of its files have document extensions). Chunks of about 450,000 bytes filled with whole directories; oversized files split at the last LF into byte ranges read in slices of at most 24,000 bytes; an incomplete read ends `status: failed at byte <offset>`. Check: review; test.
155. **Domain map.** Per-ticket questions `<ticket>-M<n>` with group ids; the mapper answers with quotes or `not found` with the search used. Check: review.
156. **Pass one.** Scopes by tier: `low` one `combined`; `medium` one per group plus `tests-hygiene` plus `interactions` with more than one bundle; `high` one per group plus `tests`, `hygiene`, `interactions`. The barrier compares `consumed:` hashes with the digest and map outputs and runs a top-up per miss until none remains. A missing Decisions, Scope or Outward trace section is `not assessed`, not a failure. Check: review; test.
157. **Pass two.** A fresh adversary per complete pass-one report, never a continuation, attacking none, the five riskiest, or all Verified OK and outward-trace entries by tier, writing verdicts, challenged sections, coverage gaps, new findings `<scope>-P<n>` with `origin: pass2`, map corrections (one round of top-ups writing `<scope>-T<n>`), claims challenged. The ledger `ledger/5.md` is built by `ledger.sh build5` from `ledger/inventory.txt` and checked with `ledger.sh check --through 5`, one retry. Check: review; test.
158. **Second opinion.** Stage 6 runs whatever stage 5's result, unless the budget has expired (requirement 152, decision 264). A fresh `adversary` at `opus` (then `sonnet`; amended 2026-11-05, decision 182) receives the request file with every finding including dropped ones, every pass-two file, the brief, evidence rules, claims, diffs, live files, and the audited sources named by absolute path and sha; inputs carry a sentinel line that the answer must acknowledge. The mandatory set from `ledger.sh mandatory` is written to `tmp/` and moved into `ledger/` only on exit 0, then split into batches of at most 60 ids; one launch per batch; only the first batch carries additions `X<n>` with `origin: second-opinion`. The answer is saved verbatim under `second-opinion/`, never retyped. `ledger/6.md` is written with positions, acknowledgments, `## Seen, no position` from `ledger.sh seen`, and checked with `ledger.sh check --through 6`. Check: review; test.
159. **Converge.** The late adversary runs at medium and high, and at low only with live files, over the ids from `ledger.sh late-ids`, writing `late/adversary.md` checked by `ledger.sh late-check`; its own findings `L<n>` never count. `gate.md` comes from `ledger.sh gate`. The merger writes `converged.md` with items `## C<n>` in the shape fixed in `agents/merger.md` (absorbs, sources, gate, disposition, severity, positions, reason, tickets, recommended change), split by group when a group's slice exceeds 450,000 bytes or the ledgers together exceed three times that, the slices being cut before the mode is chosen unless the ledgers together are under the threshold, where no slice can pass it and none is cut, and `ledger.sh check --through 7` verifies it; each merger reads every file it takes whole to its last line, in pages. `C<n>` is the id form that the report, act and the claims verdicts use. A slice section, and a merger's reading of a section, starts and ends only at a heading outside a code fence; a slice copy that reaches the end of the file inside an open fence ends with a closing fence line, and a merger's reading treats a `### <id>: ` block as no block when the file ends inside an open fence and, outside a fence, no line after its heading starts with `### ` or `## ` or is an end line. Check: review; test.
160. **Report.** Items come from `converged.md` when its check passed, else the ledgers with recomputed gates, else pass one and two with everything provisional. The verdict is `not ready` with a counted blocker or high, `merge after fixes` with a counted medium, else `ready to merge`; a partial run says `audit incomplete`. `report.md` carries `revision: sha256:<hex>` of its body, `work-items.jsonl` is validated by `work-items.sh check` and never applied, and `claims-verdicts.md` is written. The body is built from part files under `report/parts/`: `report.sh parts` writes the copied ones, `08-decisions.md`, `10-claims.md` and `claims-verdicts.body.md` (requirement 322), the orchestrator writes the others with the Write tool, the header and sections 1 to 7, the rest of section 8, 9, 11 and 12, and `report.sh assemble` joins them into the body the revision hashes. The closing lists `act first`, the exact `/audit:act` line, `your decision`, and a `--live` line when eligible. Coverage lists stages 1 to 7, each with its state and the read-only checks it accepted, and stage 8's line is the fixed sentence ``Stage 8: its read-only check runs after this report is hashed; its result is in `baseline/8-check.md`.``, since the report is hashed before that check runs (decision 198). Section 3 shows every Verified OK item in full at tier `low`; at `medium` and `high` a challenged item in full and an item not challenged as its first line cut at 150 characters with its pass-one file, grouped by scope with the scope's count (decision 199). Check: review; test.
161. **Resume.** `/audit:resume <run-id> [--from <stage>] [--live <file>]` reruns from the earliest of: `--from`; the first stage whose entry is missing, not complete, or lists a missing output; stage 5 without `ledger/inventory.txt`; the first stage whose inputs changed (forge data re-hashed, pinned shas re-resolved, upstream outputs re-hashed, `plugin_version` compared, live inputs compared), except that with `--live` a recorded `plugin_version` other than the current one does not invalidate stage 1 when every other input of stage 1 is unchanged, the first rerun stage's entry recording both versions and the report's Coverage naming them (decision 202); stage 1 when a direct tree or a working-tree bundle changed. Superseded outputs move to `superseded/<k>/`. When the first rerun stage is 4 or 5 because its entry is missing or `running`, and its recorded inputs have not changed, a `pass1/<scope>.md` or `pass2/<scope>.md` whose last line is `status: complete` and whose `consumed:` hashes equal the current hashes of those files is kept where it is and not superseded; the stage launches only the scopes with no kept file, and its entry lists the kept files among its outputs (decision 146). A changed head or base asks before restarting from stage 1; with `--live` it refuses. A new report gets a new revision, which voids earlier act approvals. Check: review; test.

### Evidence

162. **Eight hard rules.** Read-only boundary; prevention and detection (no Edit or NotebookEdit, a Bash allow-list by instruction, detection by `readonly.sh`); no model, agent or tool names in anything external, the trailer the host's attribution setting adds kept (requirement 11, decision 170); no advisor tool; live data only from a user-supplied `--live` file; evidence cited; disk first; claims are not facts. Each agent definition restates rules 2 and 4 in its own words after its opening paragraph (decision 148): no advisor tool and no second-opinion tool, whatever the host offers, and no tool outside its frontmatter list; the Bash commands of rule 2 and nothing else, with `mkdir -p` of its own scratch folder allowed, no interpreter run with an inline program or a heredoc, and no command that waits on input; every redirect inside its scratch folder; and an output file that is final once it writes `status: complete`, so a later wake-up ends with no write. Check: review; lint (agent tools; the restated rules; the kept trailer).
163. **When a finding counts.** Only after a fresh adversary other than its author challenged it and the second opinion saw it: at medium and above a stage 6 position is required; at low a complete stage 6 that requested it suffices; `X<n>` counts once the late adversary gave a verdict; `L<n>` never counts except a carried one under the live rule; when stage 6 failed nothing passes on its account. The gate reason strings are fixed. Check: review; test (`ledger.sh gate`).
164. **Four questions.** Best practice, semantic drift, technical debt, decision quality, replaceable through the manifest `questions` key or extended with `extends: default`. Check: review.
165. **Claims.** Kinds verification, decision, scope, status, code; a verification claim is `true, reproduced` only when the audit reproduced it; `false, contradicted` needs counter-evidence; otherwise `not verified, not reproduced`; environment claims always need a live check. The pass-two adversary writes a claims-challenged line for every verification claim marked true. Stage 1 assigns a claim that names no file to its ticket's group when that group exists and holds a file; else across the bundle's groups that hold a file, in claim order, one claim per group in turn, starting again at the first; else to the first group. Once every claim is assigned, a group holding more than 80 claims that name no file keeps the 80 with the lowest numbers, and the rest move in turn across the bundle's other groups that hold a file; the brief's Claims section records each scope's claim count and each move (decision 148). Check: review; test.
166. **Evidence kinds and labels.** Quote `repo@sha:path:line`, search with command and result, run with command, location and output, live result `live/results-<k>.md:<line>`. `verified fact` needs the defect demonstrated; otherwise `unverified assumption` capped at medium; `convention` rests on a ranked source. Digests and maps are pointers, never evidence. Check: review.
167. **Finding schema.** `### <scope>-F<n>: <title>` with severity, question, label, claims, evidence, demonstrated, inferred, what the code does, what breaks and for whom, recommended change, alternatives, live check, work-item impact; ids `-F`, `-P`, `-T`, `X`, `L` by origin, and `C<n>` for a converged item. Check: review; test (ledger parsing).
168. **Counting a contested item.** Equal severities count at that severity; with one `dropped` position the item counts only if the keeping position is `verified fact`; otherwise the higher severity counts when its position is `verified fact`, else the lower; `provisional` and `dismissed` never count. Check: review; test.
169. **Outward trace.** One hop per changed symbol, at most 15 symbols per scope, per symbol 5 siblings, 5 callees, 10 consumers, overflow listed; a sibling is a finding only with a cited shared contract. The second opinion traces at most 10 symbols. Check: review.
170. **Leads, not findings.** A weak-test flag becomes a finding only when the regression the test would miss is named. A run-once script edited in place is `unverified assumption` with a live check; it is judged by repeated work per step, not end state. Decision points of a widened input's consumer are listed, at most eight, uncovered first. A test running as an account with more rights than it uses is flagged; a grant gives `verified fact`, a pointer `unverified assumption` plus a live check. Check: review; test (ground-truth fixture).
171. **Producers at head and base.** The producer of each matched literal is read at head and at base; the lead is the merge-base-to-base commit range, not author dates. Check: review.
172. **Open pull request collisions.** Run-once names are checked against the first 100 open pull requests with `collisions.sh`, which prints `collision`, `cut` and `cut-list` rows; a candidate is a lead. Check: test.
173. **Audit-only rules live apart.** Rules that only the auditor and adversary need are in `audit-evidence.md`, not `common.md`. Check: review.
174. **Brief errata.** Errors in the brief that an adversary notices go to `brief_errata`. Check: review.

### Run directory and read-only boundary

175. **Scratch resolution.** The manifest `scratch` key (inside the primary repository and ignored, or inside the main checkout of a linked worktree with the same `--git-common-dir`); else `scratch/`, `tmp/` or `.scratch/` when present and ignored; else `.reimagine/` when already ignored; else `${CLAUDE_PLUGIN_DATA}/runs/`. The audit never writes to `.git/info/exclude`, and the only writes it makes under a git directory are the ones requirement 162's read-only boundary discloses: the remote-tracking refs of a fetch the user approved, and the loose objects `working-tree.sh build` adds for a `head: working-tree` bundle. Check: review; acceptance.
176. **Run directory.** `<scratch>/audit/<run-id>/`, id `<YYYY-MM-DD-HHMM>-<slug>` with `-2`, `-3` on collision, the slug being the first bundle's repository name, then its pull request number for a pull request bundle or its branch for a branch bundle, joined with `-`, slugged and cut at 40 characters (decision 200); `<scratch>/audit/` is made with `mkdir -p` and the run directory itself with `mkdir` without `-p`, so an existing id moves to the next suffix; parent and child are compared as whole resolved paths. Check: review.
177. **Registry.** `${CLAUDE_PLUGIN_DATA}/runs.json`, an array of `{run_id, path, primary_repo, created, state}`, written under a lock directory `runs.json.lock/<owner>` acquired with `mkdir`, retried every five seconds, stale after about a minute (asked interactively, removed headless, never one's own), replaced and released in one command. Check: review.
178. **Read-only check after every stage.** `readonly.sh snapshot` in stage 1, after the fetch and before any other work on the repositories, and `readonly.sh check` after every stage, walking nested repositories and submodules with `GIT_OPTIONAL_LOCKS=0` and refusing a partial clone at the top level or among them (decision 260). Exit 1 (a `blocked` line) ends the run `blocked`; exit 3 (only `remote-ref`, `local-branch` or `ignored` lines) is judged: an approved fetch, a user-confirmed `background-fetch` or `local-branch`, another audit run's file, or an agent's logged run; a `local-branch` line is a refs line for `refs/heads/<name>` present only now, `<name>` not the checkout's own branch of the baseline's `# branch.head` line, or a `+` config line `branch.<name>.<key>=<value>` for such a name, since refs and config are shared by every worktree of a repository (decision 146); a moved `refs/heads/<name>` checked out in a worktree other than the audited one, as `git worktree list --porcelain` names it at check time, is a `local-branch` pair, `-` the old line and `+` the new, and its config lines are `local-branch` lines (decision 189); a deleted branch, a moved branch no other worktree has checked out, any other config line, and the index and the tree stay `blocked`; exit 2 ends `blocked`; a quoted path is unsupported. The `touched` walk is advisory; the hash walk is fatal. Ignored-file writes from a logged run are accepted per run, never blanket. Check: test; acceptance.
179. **Moved remote-tracking ref and new local branch.** A moved remote-tracking ref asks whether a background fetch explains it; a yes is recorded as `background-fetch` with old and new commits. A `local-branch` line passes when a `local-branch` approval for the same branch and commit explains it; otherwise it asks whether the user's own work in another worktree explains the branch, naming it and its commit and recommending no answer; a yes is recorded as `local-branch` with target `<repo name>:<branch>`, decision, time and commit; a later line for the same branch at another commit asks again; no, or no answer, ends the run `blocked`. A moved branch's `local-branch` pair is judged the same way, the pair passing when an approval for the branch and its new commit explains the `+` line, except that it ends the run `blocked` when the branch is a bundle's branch or base. Check: review; test (`readonly.sh` prints the lines).
180. **Per-agent scratch.** Each agent gets `<run dir>/tmp/agents/<stage>-<scope>[-<n>]/`; `sed -i` is barred; agents may use read-only pipe stages with a `runs:` log. An agent may make its own scratch folder with `mkdir -p`, runs no interpreter with an inline program or a heredoc (`python3 - <<EOF`, `node -e`, `perl -e` and the like) and no command that waits on input, while a repository's own test or lint command stays as hard rule 2 allows it. An output file is final once its last line is `status: complete`: the agent writes nothing after it, and a completion notice for an agent whose stage entry is already `complete` or `failed`, or for an agent this session did not launch, such as one an earlier session launched, is noted in the check file of the stage then running, or of the last stage when none runs, and changes nothing (decision 148). Check: review.
181. **Message stability.** Parsed lines (`blocked <kind>`, `readonly:`, `status:`, `ledger:`, `handoff <file>:<line>:`, `working-tree: refused:`) are byte-stable; wording changes go around them. Check: test.
182. **Group names.** Custom group names are slugged; reserved names (`tests`, `hygiene`, `tests-hygiene`, `interactions`, `combined`, `unticketed`) and `-topup` or `-maptopup` collisions stop the run. Check: review; test.
183. **Headless runs.** Never end the turn while a background command runs; `revert-tests.sh bg` plus `wait` in at most eight nine-minute loops; after the eighth exit 3 the run stops with the elapsed time. Check: review.

### Scripts

184. **Eleven scripts with their suites.** `readonly.sh`, `handoff.sh`, `ledger.sh`, `working-tree.sh`, `revert-tests.sh`, `live.sh`, `memory.sh`, `work-items.sh`, `collisions.sh`, `run-copies.sh`, `report.sh`, each POSIX sh plus awk that runs on mawk, gawk and BSD awk (`revert-tests.sh` re-executes under bash), exit codes 0 ok, 1 validation error, 2 usage or IO failure, and 3 where a script documents a pending or judged state (`readonly.sh check`, `revert-tests.sh wait`). Check: test.

Check: test.

Check: test.

283. **Run copies by script.** `run-copies.sh <run dir> <run id> <tier> <questions file>` finds `skills/audit/common.md` and `skills/audit/audit-evidence.md` from its own path, writes `common.md` into the run directory with its header filled (the run id, the run directory as given, the tier, and the `- <id>: <question>` lines of the questions file in place of the header's question line) and `audit-evidence.md` byte for byte, so neither copy passes through the model. Exit 0; 1 on a bad argument (the count, a tier outside `low`, `medium` and `high`, a run directory or questions file that cannot be read, a question line not of the form `- <id>: <question>`); 2 on an IO failure or a template without its header lines. Stage 1 step 10d writes the resolved question list (the four defaults, or the manifest's list with `extends: default` applied) to `<run dir>/questions.md` with the Write tool and runs the script. Check: test (`tests/audit/run-copies.sh`); review.
322. **Report parts by script.** `report.sh` builds the report's copied sections from the run directory's files, so no copy passes through the model and no body passes through a shell argument (decision 147). `report.sh parts <run dir>` writes under `<run dir>/report/parts/`: `08-decisions.md`, section 8's heading with its Decision ledger, from the pass-one `## Decisions` lines and the pass-two `## Decisions challenged` lines, and its Raised tickets, from the `## Scope` and `## Scope challenged` lines, a `decision` or `scope` claim with no entry marked `not assessed` and an entry with no challenge line `not challenged`; `10-claims.md`, section 10, from `claims.md`, the pass-one `## Claims` lines and the `## Claims challenged` lines; and `claims-verdicts.body.md`, the entries of `claims-verdicts.md`. It reads three short lists the orchestrator writes first: `claims-files.txt` (per claims file, the name `claims.md` gives it, its absolute path, `handoff` or `prose`, and the hash the stage 1 entry records), `items.txt` (per report item, `C<n>: ` and the ids it absorbs), and, when needed, `claims-override.txt` (`claim <n>: <verdict>` for a claim whose verdict the files do not give, a live claim or one that cites an item a `REVIEW.md` rule skipped, and `claim <n> correction: <text>` for each `false` claim). `report.sh assemble <run dir>` joins every `report/parts/*.md` but `claims-verdicts.body.md`, in byte order of name, into `<run dir>/report.body.tmp`. `report.sh claims-verdicts <run dir> <hex>` writes `claims-verdicts.md`: the title with the run id, the revision, the `generated:` time, the fixed paragraph and the body part. The shapes are fixed in `report.md` and `stages/8-report.md`. Sections 3 and 9 stay the orchestrator's: no format fixes the pass-two line that marks a Verified OK item challenged, and a Live checks status joins approvals, gate reasons and result copies. It reads only a pass file whose last nonblank line, without trailing blanks, is `status: complete`, as `ledger.sh` reads it, since `common.md` makes any other a failed output, and never a `.pre-topup.md` copy; it reads every input with a CR before the LF removed and a heading with trailing blanks removed; a finished pass-one file without `## Claims`, or a finished pass-two file without `## Claims challenged` other than a map-correction `-topup.md` file, which holds findings only, is a failed output, as stages 4 and 5 count it, and is skipped as if absent; a claim number `claims.md` lists twice and a false claim with no correction are malformed inputs; a blank line in the three lists is skipped. A `contested` claim's verdicts line names, as `finding:`, the items its pass-one evidence names. POSIX sh plus awk that runs on mawk, gawk and BSD awk; exit 0; 1 for a malformed input, each line `report: <file>:<line>: <message>` with the run-relative file; 2 for usage or IO. On a nonzero exit stage 8 writes the parts the script did not write with the Write tool and names the failure in Coverage. Check: test (`tests/audit/report.sh`); review.
188. **Reverted tests.** Every exit status of a reverted run is a result, 127 included; only setup failure, timeout, path conflict or a cap gives `not run`; one verdict per test file with names from the output tail; caps 20 files, 30 minutes per bundle, no run over 1 GB; the stated limit that reverting by path cannot show the point when a needed non-test file is also reverted. Check: test; review.

### Live checks

189. **Supplied by the user, never mid-run.** A needed check becomes a report block `#### live <id>` with item, query, where or env, results, status. Results return through `/audit:resume <id> --live <file>` with frontmatter `reimagine-live: 1`, `run`, `report: sha256:<hex>`, validated by `live.sh check` against the revision and exact query, imported with `live.sh import`, derived with `active`, `carry`, `assemble`, retired with `retire` when rerunning from stage 5 or earlier. A finding result reruns stages 6 to 8; a claim-only result reruns 7 and 8. `result_file` contents are copied and hashed. Check: test; review.

### Act (stage 9)

190. **Bind.** The revision is recomputed and compared before act starts and before every commit, rebase or merge; an unknown item id stops act; each item is shown with its gate; open live checks warn. Check: review.

## The `gate` plugin

### Purpose and name

287. **Purpose.** `gate` takes one pull request, several, or a loop manifest, reviews the whole change from the merge-base with `code-review`, fixes what each pass found, lets the record decide whether another pass runs and at what level, and stops at a verdict. It runs after the loop and before the audit, which it leaves untouched except that the audit's manifest tolerates the `gate` key (requirement 145). Check: review.
288. **Skill name.** The plugin is `gate` and its one skill is `gate`, answering as `/gate` and `/gate:gate` (decision 120). The skill is user-invocable, has no `paths`, and its description names "reimagine gate", "gate this branch", "gate PR [n]" and "gate the manifest [path]", the placeholders in square brackets since the host escapes angle brackets in a description (decision 174). There is no command and no hook. Check: test (frontmatter); lint (no `hooks.json`).

### Invocation

289. **Prose invocation.** The request has no flags; a token starting with `--` is prose. The phrases read are the targets ("PR <n>", "<n> and <m>", a pull request URL, "the manifest <path>", "this branch"), "repo <path>", "no fixes", "budget <n> minutes", "base <branch>" and "checks <command>[; <command>]", which runs to the next comma that another phrase follows, else to the end of the request. With no target the current branch is gated against its base. Check: test (the README names each phrase); acceptance.
290. **Targets.** A pull request must be open, in the session's repository and not from a fork. Several run one after another, each with its own record. A manifest runs one record per bundle that has a `pr` or a `branch`, in bundle order. A branch or a bundle on a host other than GitHub runs as on GitHub; a pull request number there is unresolved. An unresolved target gets one line in the reading block and the run goes on with the others; with none left it ends `stopped`. Check: acceptance.
291. **Reading block first.** After only the read-only calls that resolve the targets and the engine, and before any other tool call, the skill prints one block of five lines: Targets, Mode, Budget, Engine and Scripts. Budget names the run budget with its source, `max-passes`, `split`, `parallel` and the three call budgets; Engine names `subprocess` or the stand-in with its reason, and the models of the reviewer and the stand-in (decision 205); Scripts is the absolute path of the plugin's scripts directory, resolved with no tool call. Check: test (the block's lines and its sample of the defaults); eval; acceptance.
292. **Base and merge-base.** A pull request's base is its `baseRefName`, and "base <branch>" naming another ends `blocked`. A branch target's base is the request's, else the bundle's `base`, read without a leading remote name, else `.reimagine.json` `base`, else the remote's default branch. The base is fetched with an explicit refspec, and every review target and line count is the three-dot range from the merge-base, as a full sha. Check: acceptance.
323. **Roots.** Every target runs against the toplevel of its repository: a bundle's `repo`, the toplevel that "repo <path>" names, else the toplevel of the session's folder. A target whose root is not the session's folder, a session started in a subfolder included, runs its git commands as `git -C "<root>"` and every other command as `cd "<root>" && <command>` in one call, and its record, `.reimagine.json`, instruction files and exclude file are the root's (decisions 153 and 233). "repo <path>" must be a git toplevel or a linked worktree, checked without comparing path strings, and is unresolved beside a pull request or a manifest. Check: acceptance (items 65 and 87).

### Approval scope

293. **What invoking approves.** For that run only: fix commits on each target's branch, and pushing that branch. Nothing else. Check: review.
294. **Instruction files win; always ask; denial.** Before changing anything the gate reads the user's instruction files from the one directory the session loads, the repository's, those of each folder above its root, and `.reimagine.json`, records every ask-first rule and prompts for any approved action a rule covers. A permission statement says, before the first fetch, what the run will prompt at. Force push, `--no-verify`, merge, rebase, amend, reset, a deploy, a push that triggers one (judged before each push from the workflow files of the base branch and of the commit pushed, a yes covering that push only; decision 216), repository settings and a new issue always prompt. A denial is final: never retried, never done another way. Check: acceptance (items 67 and 82).
295. **Blocked, never repaired.** A dirty tree, a merged or closed pull request, a `gh` that is not authenticated on GitHub, a failed fetch, a local branch ahead of or diverged from its remote, a slug collision, and a remote head before a push that is neither preflight's nor the run's own each end the run `blocked`. The gate never stashes, resets, cleans, rebases, amends, forces or stages a path it did not change. Check: test (no git command the skill shows does); acceptance.

### Passes

296. **A pass.** One review of the whole change from the merge-base at one level, then the triage, the fix round and the decision. Nothing is edited while a review runs. Check: review.
297. **Size and split.** `split.mjs` reads the numstat of the change and prints the changed lines and the reviews of the pass. At or under `split` the pass is one review. Over it, files are grouped by folder at the shallowest depth that gives more than one group, a group still over `split` is grouped again one level deeper, and sibling groups under a fifth of `split` are merged; each group's slug names its files in the record (decisions 145, 150, 194 and 232). At most `parallel` reviews run at once. Check: test (`split.mjs`, literal cases).
298. **Levels.** Pass 1 runs at `xhigh`, and a run types only `xhigh`, `high` and `medium` (decisions 122 and 134). Check: test.
299. **Triage.** Before any fix, every finding of the pass gets one bucket with a one-line reason: fix (a correctness finding inside the change, or a regression), defer (reuse, simplification, efficiency, or an issue the change did not introduce) or reject (a false positive). Only the fix bucket leads to code. Over 30 findings, read-only readers return evidence per finding, and the earlier finding a new one restates, never a bucket (decisions 195 and 238). Check: acceptance.
300. **Fix round.** One implementer per group of files that no other implementer touches. The tree is recorded before and after each call; after a failed call only the paths that were clean before it are restored, and the run ends `blocked`. The run's checks, from the request, else the bundle, else `.reimagine.json` (decision 144), run after the fixes, and a failing check is fixed at most three times. A round that changed anything ends with one commit, staged by name in the repository's convention and recorded in the pass before it is pushed (decision 234). Check: acceptance.
301. **Next level and stop.** `next.mjs` reads `passes.json` and returns a stop or the next level with the rule that gave it, the first that matches: `nothing-to-fix`, the latest pass has no fix finding; `fix-of-fix`, the latest pass follows another of the run and has at most 3 fix findings, all in files that pass's fix round changed, and its own round was not wide, made a commit and passed every check, each by its last result, of which there is at least one; `docs-only`, `medium` after a round that changed only documentation (decision 187); `wide-fix`, `xhigh` after a round that changed an exported signature, a schema or migration, or a file outside the diff, once per run after its first pass; `otherwise`, `high`. A stop is `pass`, or `pass-with-deferred` when a pass of that run deferred something. A level is marked `capped` at `max-passes`, else when the run budget cannot hold another pass (decision 188). The skill lists the rules and the change kinds the script has (decision 231). Check: test (one case per rule; the two lists compared).
302. **Identity across passes.** A finding's identity is its repository-relative path, written with forward slashes, and its normalized summary; the line is not part of it. `findings.json` keeps one entry per identity with its state. A fixed finding that returns is a regression and goes to the fix bucket; a rejected one is carried and counts as nothing; a deferred one stays deferred. A new finding is printed with its candidates, and the triage may match it to one, recording it under the earlier id (decisions 143, 154, 185 and 206). Check: test (`findings.mjs`).
303. **Caps.** `max-passes` bounds the passes of one run, and the run budget its time, waits for an answer left out. Each review, implementer call and check has its own budget, read from the configuration; the steps state no fixed minutes. A cap on passes, the run budget or a review past its budget ends the run `unconverged` with every open finding listed; an implementer call or a check past its budget ends it `blocked`. The first pass of a run says how many passes the budget holds (decision 236). A cap that ends a run is always named. Check: test (`next.mjs` capped cases; no fixed minutes in the steps); acceptance.
304. **No fixes.** With "no fixes" the run makes pass 1 only: the review and the triage run, nothing is edited, committed or pushed, and the report names what a fix run would do. The verdict is `pass` or `pass-with-deferred` on an empty fix bucket, else `unconverged`, under the rule `no-fixes`, which the orchestrator writes and `next.mjs` never returns (decision 131). Check: acceptance.

### Engine

305. **Child session.** Each review is a headless child session, `claude -p "/code-review <level> <range>"`, at `models.reviewer` passed as `--model` (decision 205), with `CLAUDECODE` unset, no standard input, `--permission-mode default` and an allow list of read tools, `git status`, `git ls-files` and the run's checks, with no form requirement 356 bans (decision 258). Its output is saved in the record before it is parsed. It never carries `--comment`, `--fix` or `--max-findings`. Check: test (the command's flags and allow list; the prompt reaches the child unchanged under Git Bash); acceptance.
306. **Review output.** `findings.mjs` reads the saved outputs of a pass: the first fenced json array of findings in each result, the notes around it, the models, the cost, and the calls the review was refused, each by tool and first line (decision 235). A finding needs `file`, `summary` and `failure_scenario`; its line is optional (decision 240). A result with no array, or an error, is a failed review, which ends the run `unconverged`. A usage limit is a failed review that the record and the report name `usage limit`, and a later run resumes the pass with its finished reviews kept (decision 241). The script warns of a match written without its link, and `--check` prints the same warnings and writes nothing (decision 154). Check: test (`findings.mjs`, fixtures).
307. **Stand-in.** When `claude` is not on the PATH, or a child session reports the `code-review` skill missing, reviews run through a subagent at `models.fallback-reviewer` over a saved patch for the rest of the run, and the reading block and the report name it with the reason. Check: test (`findings.mjs` reads a stand-in's text); acceptance.
308. **The remembered level is untouched.** The gate never calls `code-review` through the Skill tool, and a level typed in a child session does not change the user's own (decision 119); the report says so. Check: acceptance.

### Record

309. **Location.** `.reimagine/gate/<branch-slug>/` under the target's root, excluded through the git exclude file, never `.gitignore`, and never staged. A record whose branch differs from the run's is a slug collision. Check: acceptance.
310. **Files.** `passes.json`, `findings.json`, `report.md`, each review's saved output, a stand-in's patch, the snapshots before and after each implementer call, and a manifest when the run did not come from one. Pass numbers and snapshot counters run across runs, so no run rewrites an earlier run's file except the three first named and the reviews of a repeated pass. Check: test (the sample of `passes.json` is a record `next.mjs` reads; the keys of a pass entry).
311. **Completion record.** `passes.json` is the only record of completion: the branch, base, merge-base, targets and engine, one entry per run with its state, and one per pass with its level, status, reviews, findings by bucket, change kinds, changed files, commit, head, checks and next. Every write goes through a temporary file and a rename. Check: test (`next.mjs` exits 1 naming the key of a malformed record).
312. **Resume.** A second invocation on the same branch adds a run, and `resume.mjs` reads the record with the head, the remote head, the merge-base and the mode and returns where the run starts (decision 242). With the merge-base unchanged and the head the one the pass recorded as `reviewed`, or its commit, it resumes the record's last pass when that pass is not complete, keeping its finished reviews (decision 232); with every pass complete and the head unchanged it continues at the level the last pass was given, with `max-passes` and the budget counted afresh; a record that ends in a stop rewrites the report, except that a `no-fixes` stop met by a run with fixes starts a new sequence. With a new head or a changed merge-base it starts a new sequence at `xhigh` with the ledger kept, so earlier rejections carry. A commit that an earlier run made and did not push is pushed first, under the checks of any push (decisions 219 and 234), and a "no fixes" run that meets one ends `blocked`. Check: test (`resume.mjs`); acceptance (items 49, 82 and 88).

### Configuration

313. **Configuration.** `.reimagine.json` at the root may hold a `gate` key with `split`, `parallel`, `max-passes`, `budget`, `timeouts` and `models`, every value optional. A timeout absent there takes the root `timeouts` value of the same name (decision 151). ### Outputs

350. **The gate posts nothing.** No comment, review or edit on a pull request or a ticket (decision 222). Fixes that no review saw after them are marked so (decision 231). Check: test (the template's header keys and sections); eval.
