# Requirements

Architecture is in architecture.md, the hand-run checks in acceptance.md, and the choices with their evidence in decisions.md. Where this document and the architecture disagree, this document wins until it is amended.

Each requirement ends with how it is checked:

- **test**: an automated test under `tests/`, run by `npm test` and CI.
- **lint**: a rule in `tools/lint.mjs`, run by `npm run lint` and CI.
- **acceptance**: a hand-run item in acceptance.md, which holds the item's last result.
- **review**: checked by reading, once, in the pull request that merges it.

A requirement that rests on a spike names the spike in decisions.md. If a later run of that spike fails, the requirement is amended before the change that depends on it merges.

Numbers are never reused, and 19, 20, 70, 119, 197 to 212, 232 to 236, 269, 280, 284, 314, 319, 321, 325 and 345 are not in use.

## Suite

1. **One repository, one marketplace.** The marketplace is named `reimagine-engine` and lists exactly seven plugins: `rules`, `loop`, `audit`, `primer`, `gate`, `guard` and `review`, each at `plugins/<name>/`. Before a release a prerelease catalog may list a plugin that is built at a prerelease version (requirement 14), so a second machine can install it from `main` before its release. Check: lint.
2. **Plugin directories hold only what a user installs.** Under `plugins/<name>/` there are the manifest, the skills, commands, agents, hooks, scripts, output styles and reference files the plugin uses at run time, plus `README.md` and `LICENSE`. No tests, no design documents, no fixtures. Check: lint.
3. **ASCII.** Every shipped file under `plugins/` is ASCII. Check: lint.
4. **License per plugin.** The root `LICENSE` and each `plugins/<name>/LICENSE` is the Apache License 2.0 text with the holder line `Copyright 2026 vibecodedapps.net`. Check: lint.
5. **Prerequisites.** Node 22 or later and, on Windows, Git for Windows. The audit plugin's live checks, work-item validation and collision check also need `jq`; the README says so and says what runs without it. No other tool is required. `guard` also needs `git` and the `claude` command on the PATH, since its script runs both as child processes (decision 181), and `review` needs `git` for its scratch worktree and, on GitHub, `gh` with a login; it needs the `claude` command only once a child session is started for its first reading (requirement 371). Check: review.
6. **Prompt first.** The only executable files under `plugins/` are `plugins/rules/scripts/rules.mjs`, the twelve audit scripts (`readonly.sh`, `handoff.sh`, `ledger.sh`, `working-tree.sh`, `revert-tests.sh`, `live.sh`, `memory.sh`, `work-items.sh`, `collisions.sh`, `run-copies.sh`, `report.sh`, `registry.sh`), the two primer hooks `plugins/primer/hooks/drift.sh` and `plugins/primer/hooks/notice.sh`, the four gate scripts `plugins/gate/scripts/findings.mjs`, `plugins/gate/scripts/next.mjs`, `plugins/gate/scripts/resume.mjs` and `plugins/gate/scripts/split.mjs` (requirement 318), `plugins/guard/scripts/guard.mjs` (requirement 334), `plugins/primer/scripts/primer.mjs` (requirement 387) and `plugins/review/scripts/posts.mjs` (requirement 379). Every one of them has a test under `tests/`. A new script ships only with its test. A workflow script under `plugins/audit/workflows/` is an executable whose check is `node --check`, the lint rule of requirement 219 and acceptance item 43, because its runtime needs a session (decision 95); none ships until requirement 270's gate is met. Check: lint.
7. **No plugin options.** No manifest declares `userConfig`, and no file references `${user_config.*}`. Check: lint.
8. **Seven hooks outside a request.** Only seven hooks run without a session request: the rules SessionStart staleness notice, the primer SessionStart memory notice, the primer drift check, whose entry also runs the staging check of requirement 391, the primer context loader of requirement 388, the primer reach check of requirement 395, the guard SessionStart staleness notice and the guard PermissionDenied denial record. The reach check ships only where the spike of decision 299 leaves a case, and without it the count is six. No other plugin ships a `hooks/hooks.json`. Check: lint.
9. **Independent plugins.** `loop` and `audit` do not require `rules`; no manifest declares `dependencies`. Each plugin works alone after `/plugin install <name>@reimagine-engine`. Check: lint; acceptance.
10. **Reusable files carry nothing owner-specific.** No shipped file names a person, a person's email address (an address at a `.invalid` domain is allowed), an absolute path under a user's home, or a specific repository other than this one. Check: lint.
11. **Nothing external names a model, agent or tool.** Pull request bodies, pull request comments, ticket comments and commit messages name the activity and the date, never the model, the agent type or the tool that produced the text, never a review pass or its level (decision 141), and never another term the suite or a run coined (requirement 349, decision 220). A commit message of `/audit:act` follows the repository's convention (requirement 194) and carries a date only where that convention does (decision 264). Run records and reports kept in a run directory, and a record attached to a ticket, may name them. No plugin types an attribution trailer of its own or removes one the host's attribution setting adds; that setting decides alone (decision 136). Check: review; acceptance.
349. **What leaves a run.** The loop's, the gate's, the audit's and the review's `SKILL.md` each carry the item of requirement 348 word for word, on one line, as the one list item under a `## What leaves the run` heading, since each plugin works alone (requirement 9) and the house rules block may be absent or stale in the user's instruction file (decision 221). Lint fails when a skill has no such section, when the section holds another number of list items than one, whatever their marker, or when the item is not one `- ` line that equals an item of `core.md` with its lines joined and has nothing under it that a Markdown reader would add to it (decision 244); the `rules-feedback` skill names the four copies. A run's working output (verdicts, pass lists, levels, commit ids, manifests, logs, handoff context) stays in the run directory or a record attached to a ticket; a pull request gets what its reviewer needs about its code; a ticket gets what changed for its readers, what happens next and who decides. Primer and guard post nothing and carry no copy. What the item asks before a post is prose in the item and its copies, held by lint, by the loop's tests of its posting text and by the audit's checks that each file which drafts a text points at the rule (decision 269); no hook enforces it (decision 226). Check: lint; test; review.
12. **Commit form.** Commits in this repository and commits the loop makes read `type(scope): subject` in lowercase, with a body that says why. A bare `@token` in a subject or pull request text is written in backticks. Check: review.
13. **Moves and renames apart.** A commit that moves or renames files changes no file content; string renames go in their own commit. Check: review.
14. **Versions and tags.** Each plugin has its own version line in its manifest and its catalog entry, which agree. The first release is 0.1.0; before it a built plugin may ship as `0.1.0-alpha.<n>`, a semver prerelease that sorts below 0.1.0, and the 0.1.0 target of every plugin stands. A release is tagged `<plugin>--v<version>` with `claude plugin tag`. A plugin directory that changed since its last tag carries a version above that tag. There is no shared suite version. Check: lint.
15. **One changelog.** `CHANGELOG.md` has a heading `## <plugin> <version> - <YYYY-MM-DD>` for every tagged version of every plugin, prerelease versions included, newest first; a version not yet tagged needs none, so a bump passes lint before its heading is written. Check: lint.
16. **The repository keeps its own instruction file by its own rules.** The root `CLAUDE.md` is a primer hub (requirement 238), and the primer drift hook runs in sessions on this repository through the tracked `.claude/settings.json`. The same file sets `attribution` to `{"commit": "", "pr": "", "sessionUrl": false}`, the form every host version reads, against the attribution trailer and session link the commit rule forbids; a headless session in a fresh clone still added the trailer with only this file to read it from, so the commit and description checks of CI stay what enforces the rule (decision 172). Check: acceptance.
17. **Windows and POSIX.** Every test and script runs on ubuntu, macOS and Windows with Git for Windows, and the awk-using audit scripts also run on mawk. Check: test (CI matrix).
360. **Specified ahead of the build.** A requirement may describe a state that no change has built yet, so that the documents are settled before the code. This item names each such requirement. A change that builds one takes its number out of this list, a requirement whose sentence names a part built later stays until that part is built, and the change that empties the list takes the item out. The feedback log's reader: the sentence on primer in requirement 362. The files of a context loader: the sentence on them in requirement 383. Primer's profiles, store, loader and staging check: 385, 388 to 391 and 396, with the sentences on the `local` profile in requirements 237, 246, 247, 260, 261 and 266. Primer's budget, placement, search, reach and fold-back: 392 to 395 and 397 to 399, with the sentence of requirement 241. Copies and the transcript reader: 400 and 401. Requirements 386 and 387 and the sentences on primer in requirements 6, 8, 258, 259 and 265 name parts of more than one of these and stay until the last is built. Until a part is built, the catalog, lint's name list and its other literals, the README, the hub, `package.json` and the tests say what is built, and the commit that builds it moves every count they hold: the plugin names and their number, the executables, the hooks outside a request, the `hooks.json` shapes, the skills that carry the item of requirement 348, and the area scripts; so no pushed tree has lint and a shipped file disagree (decision 280). Check: review.

## House rules: the `rules` plugin

### Content

A test holds the digest of the body for options `core` and for `core,windows`, so a change to either file moves a literal, and a decision entry says why. The digests are the one test of the wording: no test asserts a sentence of either file, and the tests that use the shipped text as their fixture hold only its count of rules and the line numbers that follow from its length (decision 243). Check: review; test (digest literals).
324. **Prose written for an agent.** The Code section holds one item on prose written for an agent, after the item on reusable files: it states principles in the fewest words that get the job done, and a procedure or an output shape the request didn't ask for is added only for a failure that happened (decision 159). The chat block of requirement 44 does not carry it, since the block covers replies and not files. The handoff prompt skill carries it word for word (requirement 347, decision 212). Check: test (requirement 347's copy); acceptance (item 81).
346. **The handoff prompt's definition.** One item defines a handoff prompt: it carries work to a later session with enough context and background that the session understands what the work is and why, the owner's settled decisions and open questions as the owner left them, and nothing more specific than the owner was; it suggests nothing, asks nothing of anyone else, and leaves the thinking to that session (decision 211). The handoff prompt skill holds the item (requirement 347), and the chat block of requirement 44 carries it word for word as the last line of Content, since a handoff often starts in chat; the block's list of deliberate differences says so. `core.md` does not hold it: it applies only when a handoff prompt is asked for, which is when the skill loads (decision 243). Check: test (the chat block's line is the skill's); acceptance (item 81).
348. **What leaves the session.** One Working item, after the issue-search item, says what leaves the session is written for its reader: a pull request says only what its reviewer needs about the code at its current head; a ticket or comment says what changed for its readers, what happens next and who decides, at the detail they act on and never how it was reached; working output, such as logs, commit ids, verdicts and terms a plugin or the session coined, stays local or in an attachment; and a session publishes only when that is the task's stated purpose or the owner asked, and only what the reader will act on and would say themselves (decisions 220 and 243). The chat block of requirement 44 does not carry it, since a chat product posts nothing. The loop, the gate, the audit and the review carry it word for word (requirement 349). Check: lint (requirement 349's copies); review.
361. **Credentials in tool output.** The Working item on credentials also covers what a session prints. A credential never lands in tool output, which the host keeps on disk in the session's transcript, any more than in a file. To see what a secret holds, a session prints its key names and never a value, not even one that a filter judged harmless. A query of logs or records selects the fields it needs (decision 281). The chat block does not carry it, as it does not carry the item this extends, and no plugin carries a copy. Check: test (requirement 18's digests); acceptance (item 91).
362. **Feedback log.** One Working item has every session log what it learned about its rules and its context, and change none of them. It logs a rule or a fact that was missing, a rule that was loaded and missed, and a rule that visibly worked, each as what happened with its evidence, appended to a file named for the date in `feedback/` under `$CLAUDE_CONFIG_DIR`, else under `~/.claude`. A session's entry ends with a `Recommended` section that says which of its observations matter. An observation recommended for the house rules names no person, id or path and gives each case by its kind. The session never edits an instruction file, a rule or loaded context to fix what it logged, unless the user asks for that edit (decision 285). The item gives an entry no other form. The chat block does not carry it, since a chat product writes no file. `rules` ships no reader of the logs: primer reads them (requirement 397), and without primer they are the user's to read. The plugin's README says the directory is outside every repository, so a session in the default permission mode asks before its first write there, and that the permission rule which allows it is the user's to add. Check: test (requirement 18's digests); acceptance (item 93).
354. **Shape of `core.md`.** `core.md` is one opening paragraph, then five sections in this order: Working, Code, Tests, Done, Ask first (decision 243). The paragraph says the ask-first rules hold whatever another item says, that an instruction file can add one and none removes one, and that a subagent reads "me" as the session that launched it, which can pass on an approval the user gave and gives none of its own. Every paragraph and item is in a shape requirement 33 reads as a rule. Check: test (the one paragraph and the order of the headings; requirement 33's count of the shipped rules).
21. **No stop removed.** The Ask first section holds eight items: a new dependency; a repository the request doesn't name; anything that could lock the owner out; a dropped table, a migration against a remote database or a file deleted outside the repository; a commit or a push, and a change to work the session didn't make; how long an approval lasts; anything that reaches production or other people; and a call the permission mode or a hook denies. No edit removes or weakens one. Check: test (the eight items by their first words); review.

### Mechanism

22. **One target.** The target file is `$CLAUDE_CONFIG_DIR/CLAUDE.md`, else `~/.claude/CLAUDE.md`. It is created when missing. There is no other target. Check: test.
23. **Bytes outside the block are kept.** Every byte before the begin marker and after the end marker is preserved, including a byte order mark, bytes that are not UTF-8, the file's line ending, and a missing final newline. Check: test.
24. **Symlinks.** A target that is a symlink is written through, at the file it points to. A dangling or hard-linked target is refused without writing. Check: test.
25. **Block format.** The block starts with `<!-- reimagine:house-rules begin version=<v> options=<list> join=<none|blank|newline> digest=<16 hex> -->` and ends with `<!-- reimagine:house-rules end -->`. The digest is of the body in LF form; a CRLF file gets a CRLF block. Check: test.
26. **States.** A target is `absent`, `current`, `stale`, `edited`, `malformed` or `declined`. A version change alone with the same rules is `current`. A malformed block is reported with its line numbers and nothing is written. Check: test.
27. **Plan then apply.** `plan` writes a plan file in the plugin data directory and shows the diff, one hunk per changed run, with three lines of context. `apply` refuses when the target changed after the plan, including a file created where none was. Check: test.
28. **Ask per change.** The skill shows the diff and asks before `apply`, once per target change. Check: review; acceptance.
29. **Backup.** An existing target is copied to `<path>.reimagine-backup-<YYYYMMDDHHMMSS>` before any write; an existing backup is never overwritten and the write does not happen. A created file has no backup and `remove` deletes it unless the user added text, in which case only the block is removed. Check: test.
30. **Atomic writes.** The target is written to `<path>.reimagine-tmp-<pid>` and renamed into place, keeping permissions. Two applies started at once both land in the state and plan files; a lock directory `rules.lock` serializes them and a lock left by a dead run is taken over. Check: test.
31. **Remove.** `remove` takes out the block and the bytes of its join, so install then remove gives back the original bytes for LF, CRLF, BOM and no-final-newline files. Check: test.
32. **Decline.** `decline` records the digest; the next plan says so and the staleness notice stays quiet until the shipped text changes. Check: test.
33. **Adopt.** `plan --adopt` finds rules already present outside the block, as a Markdown reader sees them (items, paragraphs, headings; not fences, HTML comments or indented code), removes a full copy including its headings, and puts the block where the copy was. Text that differs, fenced examples, and user text under a heading are kept. A file holding Markdown that adopt does not handle is left alone and the plan recommends decline. Check: test.
34. **Recommendation.** The plan counts the rules already outside the block and recommends `apply`, `adopt` or `decline`; decline only when every rule is already present. Check: test.
35. **Imports.** `@path` imports in the target are followed read-only: at a line start or after white space, not in code, fences, quotes or the block; relative to the importing file, from `~/`, or absolute; four hops; fifty files; 256 KiB per file; a directory, an oversized file or a missing nested file is a read error, not a skip. The plan names what each import holds. Check: test.
36. **Options.** `core` is always applied; `windows` is added on Windows and refused elsewhere. Recorded options are kept on a rerun unless `--options` overrides them. Check: test.
37. **Script output.** A refusal is one line on stdout starting `rules: ` with exit 1; `status` exits 0. Check: test.
38. **Script size.** `rules.mjs` is at most 700 lines and imports only `node:` built-ins. Check: lint.
39. **The skill never edits the file itself.** `/rules` runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs <verb> ${CLAUDE_PLUGIN_DATA}` with the Bash tool, which its `allowed-tools` pre-approves, and relays its output; it never writes `CLAUDE.md` with the Edit or Write tool. The skill sets `disable-model-invocation: true`. Check: lint; review.
40. **The skill names the output style.** `/rules` ends by printing how to select the output style: `/output-style rules:Concise Plain`, or the equivalent `/config` path. Check: review; acceptance.
41. **Staleness notice.** The SessionStart hook, matcher `startup` only, runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs session-start ${CLAUDE_PLUGIN_DATA}` and prints one `systemMessage` line, `rules: the house rules in <path> are older than this plugin's; run /rules to update them`, when the block is `stale` and not declined. It prints nothing otherwise, writes nothing, and exits 0 even when the state file cannot be read. Check: test; acceptance (the message is visible at startup).
42. **Line-ending changes do not hide staleness.** A block whose file changed line ending still reads as current or stale by its rules, and a hand edit still reads as edited. Check: test.

### Refactor skill

330. **Refactor skill.** `plugins/rules/skills/refactor/SKILL.md` is named `refactor`, takes no arguments, and sets `disable-model-invocation: true`, so only the user invokes it and its description costs no startup context. 331. **What refactor applies.** `${CLAUDE_PLUGIN_ROOT}/rules/core.md`, read at run time, and the repository's own instruction files (hub, rules, nested files, skills, and the files they import) as the rules it set for itself, with the code as the reference where the two disagree; nothing else. The skill quotes no rule. Of `core.md` it applies the items that describe a file, a test or a diff, and not those that describe a session's act, and it states that principle rather than a list, so a new item falls on its side without an edit. It checks an instruction file against the item on prose written for an agent and for truth against the code, never for primer's shapes. One subagent per area of the repository, an area holding tracked files only, as `git ls-files` lists them, reviewers and refuters together at most 20 at a time (requirement 327), reviews it against the applicable items, quoted verbatim in its brief, and returns findings with evidence; a second pass challenges each finding before it is reported, since a first reading can find a case held only by the text it proposes to cut (decision 160), and refutes one that a test or a recorded decision holds, or whose quoted rule does not cover the case and no other item does (decision 172). A finding rests on these sources and the code, never on the reviewing session's own instructions, settings or environment, and each brief says so; a sentence of an instruction file that the tree contradicts throughout is a disagreement for `/primer`, never a note, and each brief names that case (decision 173). Check: review; acceptance (items 73, 74).
332. **What refactor reports.** Recommended findings that quote a rule grouped into bundles, each one cohesive refactor sized for one loop run, holding the files of one area and the tests of that area, with a change to a part the repository versions and releases on its own as its own bundle that names the release it needs, which its ticket carries, ordered by the cost of leaving them (decision 173). A finding the second pass dropped is not shown. An item with no rule behind it is a note, apart. A disagreement between an instruction file and the code names `/primer` for the instruction file's side, and a finding whose change is to an instruction file names `/primer` and stays out of the bundles. A rule the run could not apply, or applied with doubt, is listed once as feedback for the house rules. Check: review; acceptance (items 73, 74).
333. **Ticket files after a yes, and nothing else.** The skill finds the ticket directory before launching any subagent, whether or not the report will have a bundle, the repository's ignored scratch directory, checked with `git check-ignore` on its path with a trailing slash, else `${CLAUDE_PLUGIN_DATA}/refactor/<key>/` with `<key>` as in requirement 256, since its tool grant covers only the invoking turn and a subagent's return starts a new turn; then, when the report has at least one bundle, it asks one question after the report: write the ticket files, naming that directory. On a yes it writes one file per bundle there, each file named `refactor-<time>-<n>.md` with `<time>` from `date -u +%Y%m%d-%H%M%S` and `<n>` the bundle's number, so that no earlier run's ticket has its path, each a self-contained ticket that the loop reads as a file (requirement 47) and that names the repository's checks; then, per bundle, the line `reimagine loop <path>, thorough`, to run one bundle at a time, each on a new branch and never on a merged one. It writes nothing else in the repository or the plugin data directory, never runs the loop and never writes an instruction file. Check: review; acceptance (items 73 to 75).

### Draft skill

363. **Draft skill.** `plugins/rules/skills/draft/SKILL.md` is named `draft` and sets no `disable-model-invocation`, so a session reaches it when it writes a message for someone else; the cost is its description in every session's startup context, against requirement 274's pending cap. The output style keeps what shapes every reply and names the skill in one sentence (requirement 366, decision 282). Check: test (frontmatter, the cap); acceptance (item 92); eval (requirement 273).
364. **The check on a finished draft.** Before a draft to someone else is first shown, the session checks the finished text. The check strikes and verifies, and never adds detail. It strikes a commit id, build number, file name, test id, count or explanation of a mechanism that no named reader acts on; a decision handed to the reader that is the sender's to settle, which includes an invitation to reverse or approve again what the sender already did and a stated plan to go on doing what the message already shows; and a sentence that restates a source the draft names. It verifies each statement the sender has not checked: the session settles those within its reach and lists the rest beside the draft; a draft never asks its reader to verify what the sender can; a statement that something was not done or not covered is a claim about state and is checked against the record; a name or an example is read again at its source, as a location is; and an id in a copy shown for pasting is linked at first mention where its base is verified. A statement about another draft, a post or a check is true at the moment of sending and is read again when either side changes, and a summary whose verdict rests on checks still running waits for them. What another person will do is written as asked, never as agreed, unless they agreed. Notes for the owner stay outside the draft: what was left out and why, what could not be verified, and which sentence to check before sending. A doubt in the notes excuses no sentence of the draft that states it as fact. The session runs the check itself and launches no agent for it, since verifying needs what the session did (decision 282). Check: review; acceptance (item 92).
365. **Email drafts.** An email draft is one HTML file in the scratch directory the house rules name, ready to open in a browser and paste, with its links and tables. It is the only stored copy, and the reply shows the draft as text taken from that file. Every other draft is Markdown, and no draft is kept in two formats (decision 284). Check: review; acceptance (item 92).

## The `loop` plugin

### Invocation

45. **Prose invocation.** The skill is `run` in the `loop` plugin, so it answers as `/loop:run`; it is user-invocable and its description names "reimagine loop" as the primary phrase and "run the loop" as a secondary one. There is no separate command. The bare `/loop` belongs to the host's bundled interval skill and is not ours. There are no flags; a token starting with `--` is read as prose. Check: lint (frontmatter); acceptance (each phrase invokes this skill, not the bundled one).
46. **Reading block first.** After only the read-only calls that resolve ids (`git remote`, `gh`, `az`, an MCP read, a file read) and before any other tool call, the skill states how it read the request in one block with four headings: Tickets, Mode, Scope, Effort. Each ticket line says how the id resolved (`gh`, `az boards`, `mcp:<tool>`, `file`, `text`). An id that cannot be resolved gets one line that says how else to give it, as pasted text or a file, and the run continues with the other inputs. Check: acceptance.
47. **Ticket forms.** Accepted forms: `#123` and an issue or pull request URL (GitHub, resolved with `gh`); `AB#12345` or a bare number on a repository whose remote is Azure DevOps (resolved with the Azure DevOps MCP tool if one is listed, else `az boards work-item show`); a Salesforce case number or record id (resolved with a Salesforce MCP tool if listed); a readable file path; pasted text. Ticket text obtained by any means passes through the credential scan before it is written. Check: review; acceptance.
48. **A pull request reference continues its branch.** A pull request URL or number on GitHub that is open, not cross-repository and in the primary repository sets the branch to continue. Its tickets come from the branch record, else from the pull request's closing references, else the run ends `blocked` asking for a ticket, file or description. A pull request on another host is one line and the run continues without it. Check: acceptance.
49. **Modes.** Mode is one of: build and publish (default); plan only ("plan only" in the request); build without publishing ("do not publish", ending `prepared`); continue (a pull request reference, "continue <branch>", an existing record whose `tickets` list holds one of the request's tickets, or an existing record for the predicted branch). "confirm the plan" adds one pause for a clear yes after the plan review. "budget <n> minutes" sets the run budget. "on branch <name>" names the branch. Check: review; acceptance.
50. **Scope.** The primary repository is the session's, or the checkout that "primary <path>" names (requirement 281). "also edit <path>" adds a writable checkout. A path in ticket text that maps to another checkout is adopted only after the user answers a question with a clear yes or a comma-separated subset; any other answer ends `stopped` with the "also edit <path>" form to rerun without the question. Multi-repository scope is never adopted from prose alone. Check: review; acceptance.
281. **Primary checkout by request.** "primary <path>" sets the primary checkout `<checkout>` for the run. The path must be a git toplevel or a linked worktree: `git -C <path> rev-parse --show-toplevel` prints that path, else preflight ends `blocked` naming it. Every primary git command runs as `git -C <checkout>` and every other command that acts on its tree runs in one Bash call as `cd <checkout> && <command>`, the forms of the worktree run; the permission statement counts them as prompts, since the skill pre-approves only the plain forms. The reading block's Scope line names the checkout in use. When the named checkout is a linked worktree, the record of requirement 82 lives in its main checkout, the first `worktree` line of `git -C <checkout> worktree list --porcelain`, and the detached-worktree run of requirement 80 does not apply: a differing flagged path there ends `blocked`, naming the path and the main checkout, which "primary <main checkout>" runs with the exception. Without the phrase, `<checkout>` is the toplevel of the session's repository, which `git rev-parse --show-toplevel` prints, and preflight ends `blocked` when that command fails; when `git rev-parse --show-prefix` prints a prefix, the session started below the toplevel, and the primary's commands run in the forms above, counted as prompts the same way, since the host returns the shell to the session's start folder after a call that ends outside it; the record root stays that toplevel, the handoff and the manifest name it as the primary's repository, and a relative exclude path that `git rev-parse --git-path info/exclude` prints is read against the folder `git -C` names (decision 218). The word is "primary", not "in", because the remaining request text is joined into the ad-hoc description and "in" occurs in prose; it mirrors the Scope line. Check: review; test (the phrase in SKILL.md and the README, and the checkout the handoff names); acceptance (item 45).
282. **Base branch by request or configuration.** "base <branch>" in the request, else `.reimagine.json` `base`, names the base branch `<b>` of requirement 76 in place of the remote's default branch. Step 0.2 fetches it with the same explicit refspec, a fetch that fails ends `blocked` naming the branch, and `run.md` and the reading block's Mode line record it (`; base <branch>`). It is the review base (requirement 88), the pull request base (requirement 116) and the branch whose workflow files the deploy judgment reads (requirement 56). An open pull request on a continued branch whose base differs from it ends `blocked`, since the loop never retargets a pull request. An additional repository keeps its remote's default branch. Check: review; test (the phrase in SKILL.md and the README; the key in the configuration block); acceptance (item 45).
51. **Effort is a hint.** Words such as "quick", "thorough", "low", "high" set the effort passed to subagents. A floored run (requirement 69) passes effort at least `high` to its reviewers, and no hint lowers that. Check: review.
52. **Echo redaction.** The echoed request text is credential-scanned and redacted before it is printed and capped at 300 characters; the reading block that follows has no cap. Branch slugs come from the redacted text. Check: review.
53. **Credential scan.** Before anything is written to the record, every input is scanned for keys named password, passwd, secret, token, api_key, apikey, client_secret, private_key or connection_string, for blocks under headings containing cred, secret or password, for `AKIA` followed by sixteen uppercase alphanumerics, and for a PEM header. A match asks `keep` or `drop`; `drop` writes `<redacted: key>` in place; any other answer ends `stopped`. Check: review; acceptance.

### Approval scope

54. **What invoking approves.** Invoking the loop by name approves, for that run only: creating a branch, committing, pushing that branch, opening one pull request per repository, editing the body of a pull request this loop opened, commenting once per run on that pull request, commenting on the source tickets, and, for the open items of requirement 351, opening a ticket or commenting on an existing one and attaching a record to each ticket the run comments on or opens (decision 223). Check: review.
55. **Instruction files win.** Before changing anything the loop reads the user's instruction files in `$CLAUDE_CONFIG_DIR` when it is set, else in `~/.claude`, never both, since the session loads only that directory's user instruction files, and the permission statement names the directory it read; then the repository's instruction files at its toplevel, `CLAUDE.md` and `.claude/CLAUDE.md` in each folder from a session folder below the toplevel up to it, and in each folder above the repository's root, which the session loads as project instructions, `~/.claude/CLAUDE.md` among them for a repository under the home folder, and `.reimagine.json`, records every ask-first rule, and prompts for any approved action those rules cover. The loop never removes an ask-first rule. In multi-repository runs the rules of every repository are unioned. Check: review; acceptance.
56. **Always ask.** Force push, `--no-verify`, merging, anything that deploys (including a push or pull request that triggers a deploy, judged before each push from the `.yml` and `.yaml` workflow files directly in `.github/workflows`, listed from the repository root, on the base branch of requirement 76 and on the commit being pushed, with a workflow the files cannot settle counting as one that deploys; decision 217), editing repository settings, and opening an issue other than an open item's ticket, which invoking approves (requirements 54 and 351, decision 223), always prompt. An answer that is not a clear yes is a denial. Check: review.
57. **Denial.** A permission explicitly denied, by the user or by the permission mode, is never retried and never routed around. A denial in steps 0 to 6 or after the first push marks dependent steps not done, runs the independent ones, and ends `blocked`; a step 7 denial before any push ends `prepared`. A denial is a refused tool call or a non-yes to a permission question; the decision questions of requirements 50, 53 and 49 are not permissions; a missing resource is "not run", never a denial. Check: review.
58. **A dropped call is not a denial.** A dropped read is retried once serially; a dropped write only if a check shows it did not take effect; after any drop, preflight commands run serially. A subagent's report is model output, never approval. Check: review.
59. **Pre-approved reads.** `date`, `sleep` for the CI poll and a budget timer, and read-only `git` and `gh` commands are the only commands the skill's `allowed-tools` pre-approves, and none is a form requirement 356 bans: `git diff`, `git log`, `git show` and `git ls-remote` follow the session's permission mode (decision 258). The grant lasts the turn that invokes the skill and clears at the user's next message, so it does not cover a read after a question of the run (decision 215). Check: lint.

### Roles and models

60. **Orchestrator.** The session model orchestrates, judges, reviews each slice diff and decides; it never implements a slice. No fallback: without it the run stops. Check: review.
61. **Implementer.** Each slice is implemented by an Agent subagent at model `sonnet`, one per slice, parallel for slices with disjoint files, serial otherwise. Parallel implementers run no checks and say so; the orchestrator runs each slice's checks afterwards one command at a time, and a command several slices name runs once. Check: review; acceptance.
62. **Plan reviewer.** A fresh-context Agent subagent at model `opus`, given the request text, the file paths and the required reply shape, told to read and report only, reviews the plan in step 3. On a model or tool error the call is retried once at the `fallback-reviewer` model, `sonnet` by default, or, when that model is the reviewer's own, at `sonnet`, or at `opus` for a reviewer on `sonnet`, and the swap is recorded and named in the report; a denial or a timeout is not an error. The reviewer stays swapped for the rest of the run. Step 5 has no fresh reviewer; its one pass is requirement 63. No default selects the top tier, and the retry still changes model (decision 182). Check: review; acceptance.
63. **Final review role.** Every run's step 5 uses the built-in `code-review` skill with an explicit level (requirement 285) and the range `<merge-base>...HEAD` as a full sha, never `--comment` or `--fix`; `code-review` covers the primary whenever it is the session's checkout, a linked worktree included; where that skill is not listed, or the diff lives in a worktree that is not the session's checkout or in an additional repository, an Agent subagent at `opus` reviews a patch file with the acceptance criteria and the same reply shape, with the level word passed as its `effort` (`xhigh` where the word was "max", requirement 285), once, retried once at `sonnet` on an error. The stand-in is not a swap and is named in the report, with its retry, which is one tier down (decision 182). Check: review; acceptance.
64. **Reader.** Read-only work worth splitting out runs on `haiku`; the orchestrator may instead read itself. Check: review.
65. **Model configuration.** `.reimagine.json` `models` accepts `implementer`, `reviewer`, `fallback-reviewer` and `reader`, each one of `sonnet`, `opus`, `haiku`, `fable`. It never changes the risk floor or the step 5 role. Unknown keys and bad values are reported and ignored. Check: review; acceptance.
66. **Agent calls carry the request shape.** A plan review asks for a numbered list of objections ranked by impact, each marked blocking or non-blocking with a confidence of high, medium or low and a one-line reason, ending with `NO BLOCKING OBJECTIONS` when there are none, and asks the reviewer to name the code that reads each contract change and confirm the shapes match, and, for every data change, to confirm that each read-only companion of it, such as a listing kept as its rollback record, reads the same rows the write touches (decision 203). Blocking means the change would ship wrong behavior, break an acceptance criterion, or violate a repository rule. The `opus` stand-in of requirement 63 receives the plan, the inputs, the acceptance criteria and a patch file written from `git diff <merge-base>` after new files are marked with `git add -N`; the `code-review` skill reads its range itself. An empty diff is never sent to review. Check: review.

### Budgets and rounds

67. **Per-call budgets.** Minutes: `subagent` 20 for an implementer call, `review` 30 for a review pass, `check` 15, `ci` 45. `.reimagine.json` `timeouts` overrides any of them; `run` sets the run budget. Where a tool takes a timeout the budget is passed; the Bash foreground cap is 10 minutes, so a longer check runs in the background beside a background `sleep` of its budget, since a background command notifies only when it ends, and whichever ends first stops the other. An Agent or SendMessage call is judged against its budget by the `duration_ms` of its completion notification, and by `date` before and after it only when the notification carries none; when an implementer call returns the orchestrator records its checkout's status and file hashes as `post-<n>`, beside the call's `pre-<n>`; a notification that arrives for an implementer call after that call already returned is not a new call and changes nothing unless a path differs from `post-<n>` that no later call, edit or commit of the run changed, which ends the run `blocked` naming the path; any other late notification, or one for an agent the run did not launch, is logged and changes nothing; the implementer brief tells the implementer to start no background command (decision 149). Check: review.
68. **Run budget.** The default run budget is 240 minutes, overridden by "budget <n> minutes" in the request, then `timeouts.run`, then a session instruction. Waits on questions are excluded. On expiry the output is kept and the run ends `blocked`, naming the budget; after a push the pull request is left as it is. Check: review.
69. **Risk floor.** A change that adds, alters or removes an auth check, a permission rule, a schema or migration, a row-level security policy, a data access path, or a public API's signature or behavior, directly or through shared code or configuration, is floored: reviewers receive effort at least `high`, and the report says which trigger applied. Incidental edits (a typo in a migrations README, a comment in an auth module, a rename with no signature change) do not trigger it. For a schema, migration or data access change, the floor also asks whether every read-only companion of it reads the same rows the write touches (decision 203). The floor is judged at the plan and again on the actual diff after step 4, and never falls. Check: review; acceptance.
71. **Date discipline.** `date -u +%Y-%m-%dT%H:%M:%SZ` runs only at the start of step 0 and of each step, before and after each timed call (for a batch of Agent calls, before and after the batch, while each call's budget is judged by its notification, requirement 67), after each push returns, at the terminal state, and just before and after each question. Times are copied into the record from the command output, never from memory or arithmetic. Check: review.
72. **Round cap.** No step repeats more than three times. A round is one pass by the stage's reviewer plus the fixes it leads to. The orchestrator's single fix after the step 4 cap is not a round; step 5 has one pass per run and no round (requirement 111). Each CI repair cycle gets one step 5 pass and one full step 6 run; cycles are capped at three. Check: review.

### Preflight (step 0)

73. **Nothing written before the record exists.** Until step 0.5 the run writes nothing; a failure before it prints the report only. The one exception is a worktree run, which writes the `.reimagine/` exclude, the record directory and the worktree at step 0.3; from then a failure writes the report to the record. Check: review.
74. **Host detection.** The remote is the one `gh repo view` resolves, else `origin`, else the only remote; several remotes without `origin` is a preflight failure. A GitHub host where `gh` fails ends with "gh not authenticated". On a non-GitHub host steps 0 to 6 run, the end of step 6 writes the run's body file from `pr-body.md`, and the run ends `prepared` with the push commands and the body file to paste. A remote is Azure DevOps when its host is `dev.azure.com`, `ssh.dev.azure.com` or `vs-ssh.visualstudio.com`, or ends in `.visualstudio.com`; preflight records that and the remote's organization and project. Check: review; test; acceptance.
75. **Permission statement.** Step 0.1 prints the approved actions, the carve-outs, and for each action whether a prompt will occur, from the permission mode, the settings files and the allow rules; an undeterminable permission counts as a prompt. It predicts the worktree, credential, adoption, plan-confirmation and branch questions, and prints "this run will prompt at: ..." or "this run is unattended", naming the request forms that avoid each question. Check: review; acceptance.
76. **Base branch and base commit.** Step 0.2 resolves the base branch `<b>`: "base <branch>" in the request, else `.reimagine.json` `base`, else the remote's default branch (requirement 282); fetches it with the explicit refspec `+refs/heads/<b>:refs/remotes/<r>/<b>`; and records the base commit, and the start commit, the commit the build starts from: the base commit for a branch that does not exist yet, the tip for a continued one. A continued branch equal to the base branch is rejected. Check: review.
77. **Continue checks.** A continued branch must pass `git check-ref-format --branch` and must not be checked out in another worktree (the failure names the three ways around it: start the run inside that worktree, "primary <that path>", or "also edit <that path> on <branch>"). A branch named in the request without a record must exist as the exact ref `refs/heads/<branch>` on the remote. A branch with a record may exist locally only, as after a `prepared` run, or nowhere, as after a plan-only run, and is then created like a new branch; when it also exists on the remote, the local tip must be at or behind the remote head and is fast-forwarded to it. A local branch that diverged ends `blocked`. The session HEAD ends at the branch tip. Check: review; acceptance.
78. **Open pull requests.** On GitHub, `gh pr list --head <branch> --state open --limit 100 --json number,state,baseRefName,url,isCrossRepository`, filtered on `isCrossRepository`; 100 entries counts as incomplete and fails; one open pull request is recorded; several end `blocked`. Check: review.
79. **Clean tree.** `git status --porcelain` must be empty and `git diff --cached --quiet` must pass, else `blocked`; the loop never stashes, resets or cleans. Check: review; acceptance.
80. **Flagged files.** Paths marked skip-worktree or assume-unchanged are compared against HEAD with `git cat-file --filters`; a difference with a clean status creates a worktree, detached at the start commit, at `<checkout-parent>/<checkout-name>-reimagine-<branch-slug>`, beside the checkout and never inside it. Dependencies are installed in the worktree before the baseline, else the check is "not run". A switch in a worktree detaches in place and fast-forwards with `git fetch .`. Check: review.
81. **Malformed configuration.** A `.reimagine.json` that does not parse ends `blocked`. All of its keys are optional: `commit`, `checks`, `timeouts`, `models` and `base`. The `gate` key belongs to the gate plugin (requirement 313) and is skipped without a report; any other unknown key, and a bad value, is reported and ignored. Check: review; test (the configuration block in the skill is byte-identical to the README's and has exactly those keys).

### Record and idempotency

82. **Record location.** The record lives at `.reimagine/loop/<branch-slug>/` in the primary repository's record root of requirement 281, a toplevel and never a folder below it, where the slug is the branch name lowercased with every run of characters outside `[a-z0-9]` replaced by `-`, at most 60 characters, then trailing `-` removed, which the name of a record attached to a ticket relies on (decision 228). `.reimagine/` is added to `.git/info/exclude`, never to `.gitignore`. Nothing under `.reimagine/` is ever staged. `steps.json` records the exact branch name; a record whose branch differs from the run's branch is a slug collision and ends `blocked`. Check: review; acceptance.
83. **Branch known at preflight.** The branch is the continued one, the "on branch" one, the branch of the one existing record whose `tickets` list holds one of the request's tickets (several such records stop the run), or the predicted name: `fix/<ids>-<slug>` when a ticket is labeled bug or titled "fix", else `feat/<ids>-<slug>`, else `work/<slug>`; a collision with an existing local or remote branch that has no record ends `blocked`. A record whose pull request merged or closed ends `blocked`, naming the pull request and the "on branch" form that starts a new branch. Check: review.
84. **Record files.** `inputs.md` (invocation block with time, each ticket as fetched, files and text, verification notes, drift corrections, buildable status, risk floor), `plan.md` (plan plus a review log per round), `run.md` (the durable log), `steps.json` (the completion record), `report.md` (every terminal state), `handoff.md` and `audit-manifest.json` with the exports it names (when the run has its own commit, requirement 355), patch and snapshot files, and `pr-body.md` and comment bodies, which are never committed. Check: review.
85. **Completion record.** `steps.json` holds the branch, a list of runs with number, start, end and terminal state, and one entry per step with `status` (`running`, `complete`, `failed`, `skipped`), the run number, start and end, the hashes of its inputs (for Steps 1 and 2, each open input's version: an issue's `updatedAt`, a work item's `rev`, a case's `SystemModstamp`, or the hash of a file or description), and its output paths. The entry is written `running` when the step starts and `complete` only after its outputs exist; it is written through a temporary file and a rename; it is the only record of completion. Check: review; acceptance.
86. **Second run appends.** A second invocation on the same branch appends run `n+1` to the same record; `run.md` and `inputs.md` gain a dated section per run; nothing from a prior run is modified except `steps.json`, `plan.md` (appended), and `report.md`, `handoff.md`, `audit-manifest.json` and the exports (rewritten). Per-run files without a counter (the pull request body, ticket comments, patches) take a `-run<n>` suffix from run 2 on, so none is overwritten. Check: acceptance.
87. **Preflight reads the branch state.** On an existing record the loop lists `git log <merge-base>..<tip>`, where the tip is the remote head when the branch exists on the remote, marks every commit either as its own (named by a commit line the loop wrote in `run.md`) or foreign, writes the list to `inputs.md`, and judges tickets done by their recorded closing commit. Check: acceptance.
88. **Review base.** Every diff review and every "changed lines" count uses the merge-base with the base branch of requirement 76, so foreign commits are reviewed with the loop's own. Check: review.
89. **Built slices are not rebuilt.** A slice whose closing commit is on the branch is skipped; a ticket with a closing commit is marked done. A slice the loop built to `complete` and did not commit records its file hashes, and a slice whose call failed or that is still `running` records none, so its partial edits never count as committed, each `git hash-object --no-filters -- <path>` of the working copy, the `--` keeping a path that starts with `-` from being read as an option, and counts as committed when the branch tip holds them, as after a `prepared` run that the user committed: for each path, `git cat-file -e <tip>:<path>` succeeds, since a path the tip lacks would hash as the empty blob, and the recorded hash equals either `git rev-parse <tip>:<path>`, the blob as committed, or `git cat-file --filters <tip>:<path> | git hash-object --stdin --no-filters`, the blob as a checkout writes it; under `core.autocrlf` the first matches a working copy whose line endings the commit kept and the second one whose endings it converted (decision 152). Check: test (the hash command and the `steps.json` example in `record.md`); acceptance (item 60).
90. **Same tickets, no new work.** An input is done when the plan names a slice that serves it, every such slice has a commit on the branch, and its text is the text it was last planned from: a ticket whose title or the fields that say what it asks for changed, or a file whose text changed, since the latest run whose part of the plan holds it is open again, and the run takes it up like a new input (decision 245). When every ticket is done and the plan has no open slice, the run verifies the checks (step 6). When the work is published (the run that last reached step 7 ended `done` and a pull request is open on the branch), it rewrites the report, posts nothing, commits nothing, and ends `done`, except that it writes the body of its own pull request again when the branch tip is a commit no run made and no logged body describes it (decision 251); otherwise step 7 publishes the committed work. Check: acceptance.
91. **New tickets extend the plan.** New tickets add slices to `plan.md`, which goes through plan review again; the new slices are built and reviewed; the pull request this loop opened gets its body updated once per run with `gh pr edit --body-file <absolute path>` and one comment per run; a pull request the loop did not open gets a comment only and its body is never edited. Check: acceptance.
92. **Interruption safe.** Every step records completion before the next starts. A rerun recomputes the input hashes, reuses every step whose inputs are unchanged and whose outputs exist (step 4 only when its slices are committed), rechecks the tree, and resumes at the first incomplete or changed step. Step 3.7 sets up the checkout in every run that builds or checks. A post is logged when it returns: the pull request in `steps.json` before any other call, a ticket when its filing or comment returns and again when its attach does, a body edit and a pull request comment with the head each describes. A run with nothing to push and no ticket newly filed or found repeats no body edit and no comment that `run.md` logs for that head (decision 246). Check: acceptance.
93. **Never rewrite.** The loop never force pushes, rebases, resets or amends. Before each push it reads the remote head with `git ls-remote`; a head that differs from the one preflight fetched ends the run `blocked` (fast-forwarding belongs to preflight, requirement 77). Check: review; acceptance.
94. **Terminal states.** `done` (pull request open, CI green or not applicable, report written); `plan-only`; `prepared` (every step through 6 complete, publication withheld before any push, with the publish commands); `blocked` (a blocking defect, a denied permission, a budget exceeded, a preflight failure); `stopped` (a question the run cannot decide, before any branch is created). After `blocked` nothing more is published; pushed work stays and is linked. Check: review.
95. **Snapshot before an implementer call.** Before each implementer or fix call the loop records `git status`, a patch and file hashes. After a failed call it restores only paths that were clean before the call; anything else ends `blocked`. Check: review.
96. **Commit snapshot option.** With `.reimagine.json` `commit: true`, each run that publishes commits `docs/runs/<branch-slug>/plan.md` and `report-<n>.md` with state `publishing`. The report is not posted, since it is run output and the snapshot already carries it (decision 225): the run posts on the pull request what it posts without `commit: true`. Check: review; acceptance.
359. **Compaction recovery.** After a compaction, or whenever it cannot account for its state, the session that runs the loop reads `SKILL.md` again before any other action (decision 277), then `record.md`, the record's `steps.json` and the run's section of `run.md`, which give the current step, then every file Supporting files names for that step; before Step 0.5, with no record yet, it reads `steps/0-preflight.md` again. The section that says so ends within the first 15,000 characters of `SKILL.md`, inside the part the host keeps across a compaction. Check: test (the section's place, and that it names the read of `SKILL.md`); review.

### Plan (steps 1 to 3)

97. **Verification before planning.** For each ticket the loop reads the inputs, verifies claims (for a bug it reproduces or runs a check that confirms or rejects the explanation), records drift between the ticket and the code in `inputs.md`, and marks each input buildable, partial or blocked. Check: review.
98. **Repository gate.** A candidate checkout (an absolute path in the inputs that `git -C <dir> rev-parse --show-toplevel` maps to a checkout other than the primary, its submodules or the adopted ones, and that the inputs ask to change) triggers the adoption question of requirement 50; one found later ends `blocked`. A submodule path is not a separate repository. Check: review.
99. **Plan content.** `plan.md` holds, per input, scope, acceptance criteria and buildable status; across inputs, shared changes, migrations and API changes, tests, checks, order of work, and slices with disjoint files; per slice, the files owned, the change, criteria, tests, checks and the implementer. Slice count is a plan property. A slice is sized to fit one implementer call within the subagent budget in force (requirement 67), and the plan step names that budget and its source where it says when to split, since a call past it ends the run `blocked`. Check: review.
100. **Plan review rounds.** Each round verifies every objection, revises, appends a review log to `plan.md`, and is done when the reply ends `NO BLOCKING OBJECTIONS` and the orchestrator finds none. A disagreement that is the user's call ends `stopped`; the cap with a blocking objection ends `blocked`. Check: review.
101. **Plan only.** In plan-only mode the run ends `plan-only` after the review, having changed nothing in the tree. A plan confirmation not answered with a clear yes also ends `plan-only`; a change request is another round within the cap; after a yes the clean-tree, flagged-file, branch, remote-head and pull request checks run again. Check: review; acceptance.
102. **Execution setup.** After the plan is final the loop reverifies against the start commit when the planning snapshot differs from it, creates or switches to the branch, discovers the checks and runs the baseline once, and installs plan-added dependencies after the ask-first yes and before any implementer. Check: review.
103. **No comment before the plan.** Nothing is published before the plan is final, and nothing new is published on a blocked run. Check: review.

### Build (step 4)

104. **Slice brief.** Each implementer receives its slice from `plan.md`, the files it owns, the acceptance criteria, the checks, the repository's line-ending convention, the subagent budget in force, and the instruction to change nothing outside its files, add nothing the brief does not ask for, and start no background command. Check: review.
105. **Slice review.** The orchestrator reviews each slice diff with `git add -N` then `git diff <merge-base> -- <slice files>`, checks line endings with `git ls-files --eol`, and sends findings back; three rounds per slice, then one orchestrator fix; a still-blocking finding ends `blocked`. Check: review.
106. **Re-evaluation.** After step 4 the risk floor is judged on the actual diff. Check: review.
107. **Baseline failures.** A check failing on the base is matched by test names, not counts, since some failures are timing-dependent. Check: review.

### Final review (step 5)

108. **Integrate first.** Step 5.1 runs the full suite on the integrated tree and fixes regressions; every later edit is logged. Check: review.
109. **One pass.** Step 5.2 is one pass of the `code-review` skill (requirement 63) over the complete diff from the merge-base, at the level of requirement 285, after `git diff <merge-base> --stat` shows a change; an empty diff is recorded as "no changes" and sent to nothing. The pass has the review budget of requirement 67; a pass past it ends the run `blocked` naming the budget. Check: review.
110. **Triage.** The orchestrator sorts every finding of the pass into one of three buckets with a one-line reason, the buckets of requirement 299: fix (a correctness finding inside the change), defer (reuse, simplification, efficiency, or a pre-existing issue the change did not introduce) and reject (a false positive). A finding matching a rejection recorded in `run.md` or `plan.md` keeps its disposition unless it brings new evidence. The fix bucket is applied in one batch through the implementer of the slice that owns the code, after a snapshot (requirement 95); the orchestrator reads the fix diff as step 4.3 reads a slice, and a fix the read finds wrong goes back to its implementer once, then is restored from the snapshot and its finding deferred with the reason; deferred findings join the open items of requirement 351, or the report's notes when they are not open items (decision 223), and rejected ones the report's rejected list, and neither touches code. Check: review.
111. **No second pass.** The skill does not review the fixes again in the same run: step 6 verifies the checks, and the report suggests the gate for a converged review (requirement 120). A CI repair cycle runs one more pass (requirement 127). Check: review.
285. **Step 5 level.** The level typed to the `code-review` skill is the effort word's level in force (`low`, `medium`, `high`, `xhigh`), `high` with no effort word, at least `high` on a floored run (requirement 69), and never above `xhigh`: the word "max" gives `xhigh` to the skill while Agent calls keep `max`, and `ultra` is never typed (decision 122). The level is recorded in `run.md` and in the manifest's `reviews` key (requirement 286). Check: review; test (the level table in `risk.md`).

### Checks (step 6)

112. **Discovery order.** `.reimagine.json` `checks` first, then manifest-defined test, lint, typecheck and build commands (npm scripts, Makefile, pyproject pytest, ruff and mypy, cargo test and clippy, go test and vet, gradlew check), then CI jobs that run those; a CI job not mappable to a local command is deferred to CI, not guessed. With a `checks` key those commands are the ones run, and the manifests and the CI jobs are still read: each CI job that no configured check covers is named as deferred to CI in `run.md` and the report, so a gap shows before publishing. Check: review; test (the key's entry in `SKILL.md` and the README).
113. **Reuse.** Step 6 reuses the step 5.1 run when no edit was logged since. Each failure not matching the baseline is fixed through the owning implementer after a snapshot, as step 5.1 fixes a regression, and step 6 runs again, at most three times before publication, plus one run per CI repair cycle (requirement 127). Check: review.
114. **Not run versus denied.** A check without its resource is "not run" with its exact command and directory; "denied" means only a refused permission. Check: review.

### Publish (step 7)

115. **Commit.** Paths are staged by name, never `git add -A` or `.`; nothing under `.reimagine/` is staged; after a run's first push, that run commits only CI repairs. Check: review.
116. **Push and pull request.** `git push -u <remote> <branch>`, never forced, then `gh pr create --title "<title>" --body-file <absolute path>` against the base branch of requirement 76, each body file written with the Write tool in its own call and each publishing command run alone in its own Bash call, naming only that file (decision 197), where the title is the single ticket's title or the plan's one-line summary, at most 70 characters; every `--body-file` is an absolute path. A pull request opened on a continued branch lists the commits from before the run and says they were reviewed as part of this run's diff. Check: review; acceptance.
117. **Body sections.** `pr-body.md` has, in order: What changed (per input, complete or partial, and what changed, with no remainder or deferred item), Where the ticket and the code differ, Decisions for the reviewer (with any commit on the branch that is not the loop's, and whether its review covered it), Checks not run (a check someone must still run names the ticket that tracks it), Follow-ups (one line per ticket filed or commented on for an open item of requirement 351, from the latest line for it across every run of the record, items that share a ticket sharing its line, with its ticket reference, else "none"; the continued comment's Follow-ups lists only the tickets its run filed or commented on), Related pull requests, Closes (decisions 223 and 225). The continued comment's Issues lines are `<ref>: complete` or `<ref>: partial`. `Closes <ref>` only when every acceptance criterion is confirmed met, else `Refs <ref>`; one line per ticket; file and text inputs get no closing line; across repositories only the ticket's own repository closes it. An Azure DevOps ticket is `Refs AB#<n>` on GitHub and `Refs [<type> <n>](https://dev.azure.com/<org>/<project>/_workitems/edit/<n>)` on an Azure DevOps remote, with `<type>` and `<project>` from the work item read (`System.WorkItemType`, else `Work item`; `System.TeamProject`, else the remote's project, spaces as `%20`) and `<org>` from the remote; a `Refs` line does not attach the work item, so a `prepared` report asks the user to link it. On an Azure DevOps remote the description is capped at 4,000 characters, so the body is always the short form (Related pull requests, Closes, and "Details are in the first comment.") and the full body, What changed included, is a comment file to post first. On a non-GitHub host the body covers every input of every run of the record. Check: review; test.
118. **Ticket comments.** After the pull request is open, one status comment per ticket the run took up, where a ticket done at preflight gets none unless no run has commented on it, written for the ticket's readers as requirement 352 says: what changed for them, stated plainly as complete or partial, what happens next and who it waits on, the pull request link as where to follow it, and what is not done with the ticket that tracks each. The criteria met, not met or not confirmed, each with its evidence, go in the ticket's record, attached as requirement 352 says (decision 225). GitHub through `gh issue comment`, run alone after its body file is written (requirement 116); Azure DevOps through the MCP tool, else `az boards work-item update --discussion`; Salesforce through its MCP tool; a host without a tool gets the comment text in the report instead. No comment is posted on a blocked run. The text names no run-internal path, model, agent, tool, review pass, level or other term the loop coined (decision 141). Check: review; acceptance.
351. **Open items.** Once per run, before any pull request body or comment is written, after the first push or, on a run that ends `prepared`, before its body file is written, each open item of the run is one of three things, recorded in `run.md` with its evidence (decision 223). An open item a CI repair pass adds is settled the same way. On a pull request this loop opened, the body is edited once more when 7.3 ends without a block, if a repair cycle pushed a commit that makes the body untrue of the new head or its pass filed a ticket; otherwise a ticket it files is named in the report. Open items are deferred findings that affect correctness or risk or cost more to leave than to fix, remainders of partial inputs, checks not run that someone must still run, open plan objections, and questions the run raised; any other deferred finding is a note, in the report only, and a check deferred to CI is settled by the CI watch. (1) Settled by the run, when the same stretch of work can settle it: inside the plan's files and acceptance criteria, needing no input the run lacks, within the budget and with no edit in Step 7, with its evidence recorded; an item already resolved elsewhere (an open or merged pull request that resolves it, or a ticket that already holds everything the item would add) is settled by naming where, and is not listed in Follow-ups. (2) A decision for the user, when the answer is the user's call: put in full in the report's Decisions for you, with the assumption every option shares, each option, the recommendation first and what would overturn it. Decisions do not hold back publishing; a later run on the branch takes up the answer. (3) Filed to a ticket: everything else someone still owes. The tracker is searched first, closed tickets included; an open ticket that covers the same symptom but lacks what the item adds gets a comment and a record, a closed one is not commented on and the new ticket's body links it, else a new ticket is opened, one symptom each. A source ticket's own remainder stays on that ticket, whose closing line is then `Refs`, and gets no new ticket. No ticket that a run of the record took up is the ticket of an open item: one the search finds gets no comment for the item, and the new ticket's body links it (decision 247). A later run never files a second ticket for an item the record shows filed, and logs as a ticket a draft whose title it finds on the tracker, so that ticket keeps its Follow-ups line (decision 248). The body and the continued comment carry at most one line per ticket, what it holds and its ticket reference; a settled item and a decision are not listed in Follow-ups. A run that ends `prepared` files nothing: each ticket it would file is a draft in the record, listed in the report with the command or tool that files it, before the publish commands. An ask-first rule of the instruction files that covers a new issue or a comment asks once for every ticket of the run, listing each with its title and tracker and the record attached to it, never once per ticket, and any question an ask-first rule raises for a ticket comment, a source ticket's included, names the record attached with it, a yes covers what the question listed and nothing more, a record no question of the run named gets its own question before it is attached, and a non-yes to that question keeps the record local without ending the run (decision 255); an answer that is not a clear yes leaves them drafts and the run goes on. A filing or comment that fails (a non-zero exit) or is refused is handled like a non-yes and never retried or done another way: the item stays a draft, the body carries no line for it, the report names the failure or the refused call in full, and the run goes on; it is not a denial, so the run does not end `blocked` for it. A run that ends `blocked` or `stopped` before the open items are settled lists each in the report's Open items as open, with its description and why it is owed, for a later run on the branch to settle. Every draft, on any run, is logged in `run.md` and listed in the report's Open items with its files and the commands that file it and attach its record. Check: review; test; acceptance.
352. **Ticket text and records.** A ticket body or comment the loop writes is for the ticket's readers (decision 224): what changed for them, what happens next and who it waits on, and what is not done with the ticket that tracks each; a file or a line only where the reader opens it to act (decision 249); never a branch, check output, commit id, criterion evidence, or a run, step, pass, level, verdict or other term the loop coined; a pull request link is allowed as where to follow the change. Technical detail goes in a record: a Markdown file written in the record first, which stays the source of truth, then attached to the ticket as a copy. A new ticket's record is the handoff context a later session needs: what the item is, why it matters, where the evidence is, and what done looks like. A source ticket's record holds its criteria, each met, not met or not confirmed with its evidence. `tickets.md` holds the one operation, attach a record to a ticket, with one form per tracker: on GitHub an issue artifact through the REST API, `gh api --method POST repos/<owner>/<repo>/issues/<n>/artifacts` with the record as its body and the name `Record for <branch-slug>`, since GitHub refuses a `/` in an artifact name, one per ticket and branch, updated on a later run with `PATCH .../artifacts/<number>`, which keeps a version; on Azure DevOps the MCP server's attachment tools, upload then link, when listed. A failed, refused or impossible attach is not retried and not done another way; the report names the local record and why it was not attached. Tickets are filed on the tracker of the source tickets an item came from, else on the primary repository's GitHub issues; Salesforce takes comments only. Each body and record file is written first and its command runs alone (requirement 116). Check: review; test; acceptance.
120. **Handoff and manifest.** When the run has its own commit, `handoff.md` (requirement 137) and `audit-manifest.json` (requirement 286) are written in the record. When the run has its own commit, the report's `Gate:` line suggests `/gate PR <n>`, or `/gate this branch` when no pull request exists, for a three-dot diff of 500 or more changed lines, noting that the command needs the gate plugin, and its `Audit:` line suggests `/audit:run "<absolute manifest path>"` when the work spans more than one repository or more than one ticket, and after the gate when the line count alone called for one. A pull request is named in the manifest only when the live remote head equals the local HEAD. Check: review; acceptance.

### CI watch

121. **Reads name the host.** Every `gh api` call passes `--hostname`, is spelled out as one endpoint, runs one read per Bash call, and never inside a shell loop. A failed read ends `blocked`, except an HTTP 403 whose message says to upgrade or make the repository public, which means no rulesets. Check: lint (backtick spans); review.
122. **Required checks.** Read from `repos/{owner}/{repo}/branches/<base>` `.protection` and from `rules/branches/<base>` with pagination, including required workflows, never from `/protection`. Check: review.
123. **Pull request state at every poll.** `gh pr view --json headRefOid,mergeable,baseRefName,state` plus the merge commit sha. Not OPEN ends `blocked`; a retarget ends `blocked`; the live remote head must equal the last pushed sha, with a stale `headRefOid` pending for two minutes; `CONFLICTING` ends `blocked` at once. Check: review.
124. **Results.** Latest result per context and per check suite, from check-runs with `filter=latest`, statuses, and `actions/runs?head_sha=` for required workflows. Pass is success, neutral or skipped. The gated commit is the test merge commit when it has results, else the head. A status-only check that names an app ends `blocked`. Check: review.
125. **Applicability.** `pull_request_target` is judged from the base branch's file; branch, path and type filters apply; skip markers make a workflow not applicable but required checks stay required; a deferred check whose filters exclude the pull request is not expected. Check: review.
126. **Green.** Every required check, every deferred check and every applicable workflow reported, and every latest result passed. CI is not judged before two minutes after the push; polls are about thirty seconds apart, each wait one `sleep 30` run in the background, since the host blocks a standalone `sleep` in the foreground (decision 140); pending past the `ci` budget ends `blocked`. Not applicable only when nothing is required, applicable, expected or seen within two minutes. Check: review; test (the wait in `ci-watch.md`).
127. **Repair.** A red result re-enters step 5 for one pass (the fix through the owning implementer after a snapshot, then one `code-review` pass over the whole diff and its triage) and step 6, at most three cycles; still red ends `blocked` with the pull request linked. Check: review.

### Multi-repository

128. **One pull request per repository with a diff**, each on its own branch and base, with its own baseline and checks; no slice spans repositories. Bodies carry "Related pull requests" with "pending" first, then each body the loop opened is edited once with the sibling links. `done` needs every pull request green; a block in any repository stops publication in all, except the sibling-link edit. Check: review; acceptance.
129. **Commands per repository.** Git uses `git -C <path>`; gh uses `-R <host>/<owner>/<repo>` or runs inside the checkout. A host mismatch between repositories ends `blocked`. Check: review.
130. **Skip-worktree paths.** No slice may edit a skip-worktree path of an additional repository, since the edit is invisible to diff, `add -N` and staging. An additional repository's review reads a patch from `git -C <path> diff`. Check: review.
131. **Branch suggestion.** When a continued branch must be chosen among candidates, the suggestion uses the shared-stem rule: the longest common prefix of the names, not cut at `/`, never a default-branch prefix. Check: review.
132. **Handoff bundle order.** The first bundle is the primary, then the "also edit" order; a verified check is listed only for the first bundle. Check: review.

### Reporting

133. **Report compiled from the record.** `report.md` is written at every terminal state from `run.md`, never from memory. Every section is present; an empty one says "none". Check: review.
134. **Header.** Run number, branch, record path, terminal state, host, run budget and its source, base commit, merge-base, worktree, repositories, pull request, CI state, handoff, gate and audit lines. Check: review.
135. **Sections.** Attended or unattended (prompts predicted and seen, question waits); Risk (floor trigger, step 5 level, stand-in, swaps); What changed (per input, completion, changes, criteria with evidence, drift); Decisions (choice, reason, who decided: user, plan confirmation, review or run); Findings rejected and why; Checks (run, not run with command and directory, deferred to CI, failing at baseline with evidence); Open items (decision 223; each open item of requirement 351 with what became of it: settled, with its evidence or where it was already resolved; filed, with its ticket link, new or existing, and whether its record was attached; a draft, with its files and the command that files it; or put to the user; then the notes with their reasons); Decisions for you (each decision put to the user, in full); Blocked, stopped or prepared (what, steps not done, where the work is, what would unblock it, the exact commands, and for a `blocked` run that left slice edits uncommitted the `git add <paths>` per slice whose status is `complete`, `git commit` and, when the branch exists on the remote, `git push <remote> <branch>`, with the note that a rerun then finds those slices committed, and each other slice named as not done with its paths left out, with the note that the rerun's Step 0.3 stops on those paths until they are committed, restored or moved out of the tree); Log (implementer per slice, rounds, elapsed against budget). Check: review.
136. **Headless reports.** Text asked of the model before a Skill call is not shown in a headless session, so the report header carries everything a reader needs to find the record. Check: review.

### Handoff format

137. **Typed handoff.** `handoff.md` starts with frontmatter `reimagine-handoff: 1` and `generated: <ISO 8601>`, then the sections Bundles, Tickets, Decisions, Raised tickets, once each in that order; the audit's `handoff.sh check` validates it when the audit reads it, and the loop runs no check of its own. Raised tickets holds one item per filed open item of requirement 351, its `ticket` the filed ticket's reference, and a draft keeps a local id (decision 223). Check: review; test (audit `handoff.sh`).
138. **Ticket entries.** Each `### <ticket id>` carries, in order, type, state, iteration, owner, parent (optional), links (optional), bundles, problem, decision, commits (`- <bundle> <sha>: <text>`), verified (`<statement>; check: <check|not recorded>`). Ids are normalized to `github:owner/repo#n`, `ado:<org>/<project>#<n>`, `sf:<case number>` or `file:<path>`. `<ticket>` in file names is the id slugged, except for a `file:` ticket, whose `<ticket>` is the export's `id` slugged, else the file's base name without its extension slugged, the normalized id staying its identity (decision 201). Check: review; test.
139. **Decisions.** Each `### D<n>` carries ticket, decision, rationale, options (`chosen:` or `rejected: ...; why: ...` or `none recorded`), decided_by (`role: <role>`, `checkpoint (recommended option taken)` or `not recorded`; never a person's name and never a model, agent or tool), recorded_at, status. The record's four deciders map to decided_by in one table that the loop's `handoff.md` and the audit's `handoff.md` carry word for word: user to `role: session user`, plan confirmation to `role: session user (plan confirmation)`, review to `checkpoint (recommended option taken)`, run to `role: orchestrator`. Check: review; test (the two tables are identical).
140. **Parent and links.** The GitHub parent is read through GraphQL with `--hostname`, late in the run so the run's own pull request is included; a failed read writes no key, never `links: none`. Check: review.
141. **Written only with a commit.** The handoff is written only after the run's own commit, in any terminal state; the loop never commits in order to write one. Check: review.
355. **Manifest tickets.** A bundle's `tickets` names each ticket in a form the audit reads (decision 250): a GitHub issue by its id; an Azure DevOps or Salesforce ticket as the `file:` path of an export the loop writes in the record, `export-<id-slug>.md`, in the audit's format (requirement 146) from the latest copy of the ticket in `inputs.md`, with the ticket's handoff id as its `id`; a file or text input is left out and stays in the handoff as claims. Check: review; test (the keys of the export against the audit's rule).
286. **Manifest `reviews` key.** `audit-manifest.json` gains `reviews`, the step 5 level and its findings by bucket: `{"level": "<level>", "fixed": [...], "deferred": [...], "rejected": [...]}`, each finding as `{"file": "<repository-relative path>", "summary": "<one line>"}`, with empty lists when the pass found nothing. The audit ignores the key (requirement 145); the gate writes beside it (requirement 315) and does not read it. Check: review; test (the shape in `handoff.md` equals the README's).

## The `audit` plugin

### Invocation

142. **Prose invocation.** The skill `audit` is user-invocable and its description names "reimagine audit". Requests such as "reimagine audit PR 123 and 124 in app, tickets AB#4567 and AB#4580" are read into bundles; a manifest file path is accepted and is what the loop handoff writes. Thin commands `/audit:run`, `/audit:resume`, `/audit:act` and `/audit:handoff` forward to the skill. Each command holds `$ARGUMENTS` unquoted, so a manifest path and the words after it are separate tokens, and only quotes the user typed keep text together. Check: lint (frontmatter); test (`tests/audit/lint.sh` fails on a command file that quotes `$ARGUMENTS`); acceptance (item 68).
143. **Reading block.** After only the read-only calls that resolve ids and before any other tool call, the skill states bundles (repository, pull request or branch and base, tickets), references, sources of truth, claims files, effort hint, budget and model overrides, and how each ticket resolved, naming each ticket whose body was not read. Check: acceptance.
144. **Effort is a hint; size sets the default.** The default tier is `low` for one bundle, one ticket and under 500 changed lines; `medium` up to three bundles, five tickets and under 5,000 lines; `high` otherwise. A hint ("effort high") overrides it. The tier sets the pass-one scopes, how much pass two attacks, and whether the late adversary runs. Check: review.
145. **Manifest.** Keys: `bundles[]` (`repo`, `pr` or `branch` plus `base`, `tickets[]`, `ticket_token`, `run_once`, `head`, `test_command`, `test_run`, `test_paths`, `test_setup`, `test_timeout`), `references[]`, `sources_of_truth[]`, `claims[]`, `scratch`, `forge_exports`, `groups[]`, `questions`, `models`, `budget`, `max_agents`, `_test`. `reviews` (written by the loop, requirement 286) and `gate` (written by the gate, requirement 315) are ignored and not an error, since stage 1 reads only the keys it names (decision 129). A bundle's `checks` (read by the gate, requirement 300) is ignored the same way: stage 1 reads only the bundle keys it names, so a key it does not name is neither read nor an error. Validation messages name the key. Check: review; test (fixture manifests).
146. **Exported forge files.** A ticket or pull request on a host without a tool is supplied as a `file:` export in markdown with frontmatter or JSON; a ticket requires id, url, title, state and description, a pull request id, url, title and body, every file source, exported_by and exported_at; a missing key stops the run with a sentence saying what an export holds and where its format is shown. `forge_exports.command` is recorded, never run. A ticket id takes a form of requirement 138 or stays as the user wrote it; how the ticket resolved, an Azure DevOps or Salesforce MCP tool as `mcp:<tool>`, is recorded beside the id and never as it (decision 261). Check: review; test.
147. **Pause background fetch.** After the reading block the skill tells the user to pause background fetch, for example VS Code `git.autofetch`; `/audit:run` adds no sentence of its own (decision 264). Check: review.

### Stage model

148. **Nine stages.** Orient, digest, domain map, pass one, pass two, second opinion, converge, report, act, in that order with these dependencies: 1 alone; 2, 3 and 4 together; a per-group barrier opens stage 5 when 2 and 3 are done and top-ups finished; 6 after every pass two; 7 the late adversary and the merger; 8 always. A stage whose input is absent is `not_applicable`; a failed stage counts as satisfied and the run ends `partial`. Check: review; acceptance.
149. **Completion record.** `stages.json` holds `plugin_version`, `approvals[]` (`fetch`, `live`, `export-over-1gb`, `background-fetch`, `local-branch`) and per-stage entries with `status` (`running`, `complete`, `failed`, `not_applicable`, `superseded`), `inputs` as file hashes from `git hash-object --no-filters`, `outputs`, `agents[]` (type, requested model, scope, start, end, tokens labeled "task notification, subagent_tokens; scope not documented", duration, result), `swaps`, `superseded`. It is written through a temporary file and `mv -f`, the entry goes `running` at start and final only after the outputs exist and the read-only check passed, and it is the only record of completion. Check: review; acceptance.
150. **Roles.** Digester `haiku`; mapper and merger `sonnet`; auditor and adversary `opus`; second opinion a fresh `adversary` at `opus` (decision 182). The manifest `models` key overrides any role with `opus`, `sonnet`, `haiku` or `fable`. Agents are launched with the Agent tool as `audit:<role>`, in the background, never as a fork, never general-purpose, each with its own scratch folder. Check: review; acceptance.
151. **Failure ladder.** Digester, mapper, auditor and adversary: relaunch on the same model, then on `opus`, or on `sonnet` for a role already on `opus`, as a swap, then the scope fails. Merger: the orchestrator merges, a second failure fails stage 7. Second opinion, per batch: relaunch on `sonnet`, or on `opus` for a second opinion already on `sonnet`, as a swap, then stage 6 fails. An agent fails when it returns an error, when its last line is not `status: complete`, or when fault injection marks it failed. Before the ladder relaunches an agent the session moves the output file the failed attempt left into that attempt's scratch folder as `failed-output.md`, since an agent leaves a complete file at its path as final (decision 278); a top-up that appends to a pass-one report gets the report restored from the saved copy instead, and no agent reads anything in another agent's scratch folder. Swaps are recorded and named in the report. The swap rung changes model, since a swap recovered a usage-limit failure that a same-model retry would not (decision 182). Check: test (the move in Roles, no rule of another file for it, the sentence in `common.md`); review.

Without a yes, stop. Instruction files decide where a documented fact goes. Check: review.
194. **Apply.** Groups by ticket and repository, or per item with `--per-item`; a rebase or merge item first, with the publication tip recorded and `force push owed` computed; then one commit per group: show each item's defect first, where the item's evidence is reading rather than a run and a covering check or the test its demonstration describes can show the defect within the check budget, by running it at baseline, logging the command and result, and stopping to ask whether to skip an item whose premise the result contradicts (decision 148); record line endings, edit, restore endings, stage (a shared file by byte-exact patch through `apply --cached --check`), rerun checks and each demonstration command, so the commit body has an after result for every before result, classify failures introduced or preexisting, show the staged diff, ask, commit with `-F`, following repository convention, with the before and after results in the body, no tool names, no skipped hooks. Act never pushes and never edits tickets unless told per item. A post the user names, and every drafted ticket or pull request text in the report and in `work-items.jsonl`, is written for its reader as requirement 349 says, with no audit id, stage, verdict or other term the audit coined; the evidence and the ids stay in the run directory, and the audit attaches no record to a ticket (decision 227). Check: review; acceptance.
195. **Close.** What was and was not committed, force-push status, the log path, and one live line. Check: review.

### Handoff command

196. **`/audit:handoff`** writes a typed handoff from a build session with `--out <path>` outside every repository or ignored, never overwriting; `--verdicts <claims-verdicts.md>` applies only lines whose file hash and claim text match, turning mismatches and `contested` lines into reconciliation work; `--memory <dir>` runs `memory.sh find` and edits nothing. Ids are normalized as in requirement 138. Check: review; test.

## The `gate` plugin

### Purpose and name

287. **Purpose.** `gate` takes one pull request, several, or a loop manifest, reviews the whole change from the merge-base with `code-review`, fixes what each pass found, lets the record decide whether another pass runs and at what level, and stops at a verdict. It runs after the loop and before the audit, which it leaves untouched except that the audit's manifest tolerates the `gate` key (requirement 145). Check: review.
288. **Skill name.** The plugin is `gate` and its one skill is `gate`, answering as `/gate` and `/gate:gate` (decision 120). The skill is user-invocable, has no `paths`, and its description names "reimagine gate", "gate this branch", "gate PR [n]" and "gate the manifest [path]", the placeholders in square brackets since the host escapes angle brackets in a description (decision 174). There is no command and no hook. Check: test (frontmatter); lint (no `hooks.json`).

### Invocation

289. **Prose invocation.** The request has no flags; a token starting with `--` is prose. The phrases read are the targets ("PR <n>", "<n> and <m>", a pull request URL, "the manifest <path>", "this branch"), "repo <path>", "no fixes", "budget <n> minutes", "base <branch>" and "checks <command>[; <command>]", which runs to the next comma that another phrase follows, else to the end of the request. With no target the current branch is gated against its base. Check: test (the README names each phrase); acceptance.
290. **Targets.** A pull request must be open, in the session's repository and not from a fork. Several run one after another, each with its own record. A manifest runs one record per bundle that has a `pr` or a `branch`, in bundle order. A branch or a bundle on a host other than GitHub runs as on GitHub; a pull request number there is unresolved. An unresolved target gets one line in the reading block and the run goes on with the others; with none left it ends `stopped`. Check: acceptance.
291. **Reading block first.** After only the read-only calls that resolve the targets and the engine, and before any other tool call, the skill prints one block of five lines: Targets, Mode, Budget, Engine and Scripts. Budget names the run budget with its source, `max-passes`, `split`, `parallel` and the three call budgets; Engine names `subprocess` or the stand-in with its reason, and the models of the reviewer and the stand-in (decision 205); Scripts is the absolute path of the plugin's scripts directory, resolved with no tool call. Check: test (the block's lines and its sample of the defaults); eval; acceptance.
292. **Base and merge-base.** A pull request's base is its `baseRefName`, and "base <branch>" naming another ends `blocked`. A branch target's base is the request's, else the bundle's `base`, read without a leading remote name, else `.reimagine.json` `base`, else the remote's default branch. The base is fetched with an explicit refspec, and every review target and line count is the three-dot range from the merge-base, as a full sha. Check: acceptance.
323. **Roots.** Every target runs against the toplevel of its repository: a bundle's `repo`, the toplevel that "repo <path>" names, else the toplevel of the session's folder. A target whose root is not the session's folder, a session started in a subfolder included, runs its git commands as `git -C "<root>"` and every other command as `cd "<root>" && <command>` in one call, and its record, `.reimagine.json`, instruction files and exclude file are the root's (decisions 153 and 233). "repo <path>" must be a git toplevel or a linked worktree, checked without comparing path strings, and is unresolved beside a pull request or a manifest. Check: acceptance (items 65 and 87).

### Approval scope

293. **What invoking approves.** For that run only: fix commits on each target's branch, and pushing that branch. Nothing else. Check: review.
294. **Instruction files win; always ask; denial.** Before changing anything the gate reads the user's instruction files from the one directory the session loads, the repository's, those of each folder above its root, and `.reimagine.json`, records every ask-first rule and prompts for any approved action a rule covers. A permission statement says, before the first fetch, what the run will prompt at. Force push, `--no-verify`, merge, rebase, amend, reset, a deploy, a push that triggers one (judged before each push from the workflow files of the base branch and of the commit pushed, a yes covering that push only; decision 216), repository settings and a new issue always prompt. A denial is final: never retried, never done another way. Check: acceptance (items 67 and 82).
295. **Blocked, never repaired.** A dirty tree, a merged or closed pull request, a `gh` that is not authenticated on GitHub, a failed fetch, a local branch ahead of or diverged from its remote, a slug collision, and a remote head before a push that is neither preflight's nor the run's own each end the run `blocked`. The gate never stashes, resets, cleans, rebases, amends, forces or stages a path it did not change. Check: test (no git command the skill shows does); acceptance.

### Passes

296. **A pass.** One review of the whole change from the merge-base at one level, then the triage, the fix round and the decision. Nothing is edited while a review runs. Check: review.
297. **Size and split.** `split.mjs` reads the numstat of the change and prints the changed lines and the reviews of the pass. At or under `split` the pass is one review. Over it, files are grouped by folder at the shallowest depth that gives more than one group, a group still over `split` is grouped again one level deeper, and sibling groups under a fifth of `split` are merged; a changed file that is also the folder of other changed files is in that folder's group, which is not grouped again, since its path selects them all (decision 265); each group's slug names its files in the record (decisions 145, 150, 194 and 232). At most `parallel` reviews run at once. Check: test (`split.mjs`, literal cases; what git selects for the paths on a built repository).
298. **Levels.** Pass 1 runs at `xhigh`, and a run types only `xhigh`, `high` and `medium` (decisions 122 and 134). Check: test.
299. **Triage.** Before any fix, every finding of the pass gets one bucket with a one-line reason: fix (a correctness finding inside the change, or a regression), defer (reuse, simplification, efficiency, or an issue the change did not introduce) or reject (a false positive). Only the fix bucket leads to code. Over 30 findings, read-only readers return evidence per finding, and the earlier finding a new one restates, never a bucket (decisions 195 and 238). Check: acceptance.
300. **Fix round.** One implementer per group of files that no other implementer touches. The tree is recorded before and after each call; after a failed call only the paths that were clean before it are restored, and the run ends `blocked`. The run's checks, from the request, else the bundle, else `.reimagine.json` (decision 144), run after the fixes, and a failing check is fixed at most three times. A round that changed anything ends with one commit, staged by name in the repository's convention and recorded in the pass before it is pushed (decision 234). Check: acceptance.
301. **Next level and stop.** `next.mjs` reads `passes.json` and returns a stop or the next level with the rule that gave it, the first that matches: `nothing-to-fix`, the latest pass has no fix finding; `fix-of-fix`, the latest pass follows another of the run and has at most 3 fix findings, all in files that pass's fix round changed, and its own round was not wide, made a commit and passed every check, each by its last result, of which there is at least one; `docs-only`, `medium` after a round that changed only documentation (decision 187); `wide-fix`, `xhigh` after a round that changed an exported signature, a schema or migration, or a file outside the diff, once per run after its first pass; `otherwise`, `high`. A stop is `pass`, or `pass-with-deferred` when a pass of that run deferred something. A level is marked `capped` at `max-passes`, else when the run budget cannot hold another pass (decision 188). The skill lists the rules and the change kinds the script has (decision 231). Check: test (one case per rule; the two lists compared).
302. **Identity across passes.** A finding's identity is its repository-relative path, written with forward slashes, and its normalized summary; the line is not part of it. `findings.json` keeps one entry per identity with its state. A fixed finding that returns is a regression and goes to the fix bucket; a rejected one is carried and counts as nothing; a deferred one stays deferred. A new finding is printed with its candidates, and the triage may match it to one, recording it under the earlier id (decisions 143, 154, 185 and 206). Check: test (`findings.mjs`).
303. **Caps.** `max-passes` bounds the passes of one run, and the run budget its time, waits for an answer left out. Each review, implementer call and check has its own budget, read from the configuration; the steps state no fixed minutes. A cap on passes, the run budget or a review past its budget ends the run `unconverged` with every open finding listed; an implementer call or a check past its budget ends it `blocked`. The first pass of a run says how many passes the budget holds (decision 236). A cap that ends a run is always named. Check: test (`next.mjs` capped cases; no fixed minutes in the steps); acceptance.
304. **No fixes.** With "no fixes" the run makes pass 1 only: the review and the triage run, nothing is edited, committed or pushed, and the report names what a fix run would do. The verdict is `pass` or `pass-with-deferred` on an empty fix bucket, else `unconverged`, under the rule `no-fixes`, which the orchestrator writes and `next.mjs` never returns (decision 131). Check: acceptance.

### Engine

305. **Child session.** Each review is a headless child session, `claude -p "/code-review <level> <range>"`, at `models.reviewer` passed as `--model` (decision 205), with `CLAUDECODE` unset, no standard input, `--permission-mode default` and an allow list of read tools, `git status`, `git ls-files` and the run's checks, each shell entry once for the Bash tool and once for the PowerShell tool (decision 266), with no form requirement 356 bans (decision 258). Its output is saved in the record before it is parsed. It never carries `--comment`, `--fix` or `--max-findings`. Check: test (the command's flags and allow list; the prompt reaches the child unchanged under Git Bash); acceptance.
306. **Review output.** `findings.mjs` reads the saved outputs of a pass: the first fenced json array of findings in each result, the notes around it, the models, the cost, and the calls the review was refused, each by tool and first line (decision 235). A finding needs `file`, `summary` and `failure_scenario`; its line is optional (decision 240). A result with no array, or an error, is a failed review, which ends the run `unconverged`. A usage limit is a failed review that the record and the report name `usage limit`, and a later run resumes the pass with its finished reviews kept (decision 241). The script warns of a match written without its link, and `--check` prints the same warnings and writes nothing (decision 154). Check: test (`findings.mjs`, fixtures).
307. **Stand-in.** When `claude` is not on the PATH, or a child session reports the `code-review` skill missing, reviews run through a subagent at `models.fallback-reviewer` over a saved patch for the rest of the run, and the reading block and the report name it with the reason. The patch of a split pass is made with the group's paths read as names, not as patterns (decision 265). Check: test (`findings.mjs` reads a stand-in's text; the diff the step shows selects only the group's files); acceptance.
308. **The remembered level is untouched.** The gate never calls `code-review` through the Skill tool, and a level typed in a child session does not change the user's own (decision 119); the report says so. Check: acceptance.

### Record

309. **Location.** `.reimagine/gate/<branch-slug>/` under the target's root, excluded through the git exclude file, never `.gitignore`, and never staged. A record whose branch differs from the run's is a slug collision. Check: acceptance.
310. **Files.** `passes.json`, `findings.json`, `report.md`, each review's saved output, a stand-in's patch, the snapshots before and after each implementer call, and a manifest when the run did not come from one. Pass numbers and snapshot counters run across runs, so no run rewrites an earlier run's file except the three first named and the reviews of a repeated pass. Check: test (the sample of `passes.json` is a record `next.mjs` reads; the keys of a pass entry).
311. **Completion record.** `passes.json` is the only record of completion: the branch, base, merge-base, targets and engine, one entry per run with its state, and one per pass with its level, status, reviews, findings by bucket, change kinds, changed files, commit, head, checks and next. Every write goes through a temporary file and a rename. Check: test (`next.mjs` exits 1 naming the key of a malformed record).
312. **Resume.** A second invocation on the same branch adds a run, and `resume.mjs` reads the record with the head, the remote head, the merge-base and the mode and returns where the run starts (decision 242). With the merge-base unchanged and the head the one the pass recorded as `reviewed`, or its commit, it resumes the record's last pass when that pass is not complete, keeping its finished reviews (decision 232); with every pass complete and the head unchanged it continues at the level the last pass was given, with `max-passes` and the budget counted afresh; a record that ends in a stop rewrites the report, except that a `no-fixes` stop met by a run with fixes starts a new sequence. With a new head or a changed merge-base it starts a new sequence at `xhigh` with the ledger kept, so earlier rejections carry. A commit that an earlier run made and did not push is pushed first, under the checks of any push (decisions 219 and 234), and a "no fixes" run that meets one ends `blocked`. Check: test (`resume.mjs`); acceptance (items 49, 82 and 88).

### Configuration

313. **Configuration.** `.reimagine.json` at the root may hold a `gate` key with `split`, `parallel`, `max-passes`, `budget`, `timeouts` and `models`, every value optional. A timeout absent there takes the root `timeouts` value of the same name (decision 151). An unknown key or a bad value is reported in the reading block and ignored; a file that does not parse ends `blocked`. The block is the same in `SKILL.md` and the README and holds the defaults. Check: test.

### Outputs

350. **The gate posts nothing.** No comment, review or edit on a pull request or a ticket (decision 222). The verdict, the findings, the checks and the commits stay in the record, and the report is printed as the run's last message. After a fix push the report says that a pull request's description was written before those commits (decision 237). `SKILL.md` carries the house-rules item on what leaves a session word for word (requirement 349). Check: test (no file of the plugin holds a posting command); acceptance (item 83).
315. **Manifest.** A run from a manifest sets that file's top-level `gate` key, per bundle: `{"verdict": "<state>", "passes": <n>, "record": "<absolute path of passes.json>"}`, every other key kept. Otherwise the run writes a minimal manifest in the record, so the report can suggest `/audit:run` on it. Check: test (the value in the step that ends a run); acceptance (item 52).
316. **Terminal states.** Every run ends in exactly one of `pass`, `pass-with-deferred`, `unconverged`, `blocked` and `stopped`, named the same in the skill, the report template and the README. After `blocked` nothing more is pushed, and pushed commits stay and are named. Check: test.
317. **Report.** `report.md` is written at every terminal state from the record, never from memory, and printed as the last message: a header that lets a headless reader find the record, then Findings, Checks, Commits and pushes, Open findings, Blocked or stopped and Log, each present. Fixes that no review saw after them are marked so (decision 231). Check: test (the template's header keys and sections); eval.

### Scripts and tests

318. **Scripts.** `split.mjs`, `findings.mjs`, `next.mjs` and `resume.mjs` under `plugins/gate/scripts/`: Node 22 ESM, no dependencies, LF endings, exit 0, 1 for a validation failure and 2 for usage or IO, with messages on stderr. The session's shell has no `${CLAUDE_PLUGIN_ROOT}`, so every command the skill shows names a script by the path of the reading block's Scripts line, and each such command runs. Check: test; lint.
353. **Tests hold structure and contracts.** The gate's suites compare the scripts' output with literals, and check of the skill only what a run needs from its files: the frontmatter, the defaults, the lists the scripts share with the prose, the commands shown, the report template and a word budget. No case asserts a sentence. What only a model run can show is an eval case (requirement 273) or an acceptance item (decision 239). Check: review.

### Out of scope

320. **Non-goals.** A dynamic workflow engine; a second model provider; the `low`, `max` and `ultra` levels and cloud review; reading earlier review comments or CI results as input; opening or editing a pull request or an issue; ticket comments; reading the loop's `reviews` key. Check: review.

## The `review` plugin

Review applies the suite's review quality to a pull request that someone else wrote. It never writes to the author's branch, and its output is comments.

### Purpose and name

367. **Purpose.** `review` takes a pull request that someone else wrote, or a pair of them, and ends in drafted comments for the author and a summary for the person who gates the merge; "findings listed" is a successful end. It never commits, pushes, rebases or edits on the author's branch, and it writes nothing in the work tree of the repository it reviews, a record or an ignore entry included (requirement 370). It carries little review logic of its own: the first reading comes from the host's review or from a gate or audit report (requirement 371), and the plugin owns what comes after. It is its own plugin for three reasons: the gate exists to fix and push on the user's own branch and ends a run that fixes nothing and found something to fix as `unconverged`; the audit's act stage and ticket edits take the branch and the tickets to be the user's; and the suite has no finding engine the three could share (decision 286). It works alone (requirement 9). Check: review; acceptance (items 94 and 98).
368. **Skill and invocation.** The plugin is `review` and its one skill is `run`, answering as `/review:run` and to the prose "reimagine review", since the bare `/review` is the host's own review (decisions 35 and 286). The skill is user-invocable, has no `paths`, and its description names "reimagine review" and says the pull request is someone else's; there is no command and no hook, and its `allowed-tools` hold no entry that writes to a forge. A request names one pull request by number or URL, or two as a pair, each in a repository with a local clone, the session's own or one the request names by path. A pull request on a forge the session has no tool for is given as an export file: the form of requirement 146 with the keys `head` and `base`, full shas, and, required for a follow-up, `threads`, each with `id`, `path`, `line`, `status` and `comments`. The request's words choose the run: a first review; a follow-up, when the record holds an earlier round or the request says so; or `post`, the step of requirement 377. Other words set the review level, else `xhigh`, as the gate's first pass has it; name the person who gates the merge; name files that hold the team's conventions, precedent or a sample of its review comments (requirement 374); and name a gate record or an audit report to read first. The first lines of the reply are a reading block that says what the run took each of these to be. Check: test (frontmatter); lint; eval (requirement 273); acceptance (item 94).
369. **Approval scope.** Invoking the skill approves reads of the repository and the forge, a fetch of the pull request's head and of its base branch, a scratch worktree outside the repository, and the first reading: its child review session, or the agent that stands in for it (requirement 371). Running code from the pull request's head, the repository's checks among it, is asked for by name before the first such run, since that code is the author's and runs with what the user's machine can reach. Invoking approves nothing outward: every comment, vote, thread resolution, ticket edit and merge is approved by name in the posting step (requirement 377). The reply says so before the first read. Check: review; acceptance (item 94).

### Record and workspace

370. **Record and workspace.** The record of a review is `${CLAUDE_PLUGIN_DATA}/reviews/<repo>/<target>/`. `<repo>` is the remote of the repository that holds the pull request, written as requirement 340 writes it and kept as nested directories, so another clone of the repository finds the earlier round, and `<target>` is the forge's id of the pull request; a pair keeps its shared summary in the record whose path sorts first. The record holds the reading, the notes, the drafts, one file each, and what was posted, and forge text is scanned for credentials before it is written there, as requirement 217 has the loop do. Code runs only in a scratch worktree at the pull request's head, made detached under the record from a ref the run fetched for it. The head is the author's and is untrusted: the child session loads no configuration from it (requirement 371); every `git` command the run makes in the scratch worktree, its creation and the trial merge of requirement 376 included, runs with `core.hooksPath` set to an empty directory under the record, so no hook of the repository runs, with `core.longpaths=true`, so a deep tree checks out on Windows, and with the LFS filter's commands set empty, so a checkout starts no program that contacts a server the head names; a worktree an earlier round made from another clone is not moved, and the run stops and names the command that removes it; and the team's conventions are read at the base commit (requirement 374). The worktree reaches the packages installed in the user's checkout only where the head changes no dependency manifest or lockfile; otherwise a check that needs them is `not run`. The run uses no command that reaches a package registry, and ends by listing every file, worktree and ref it created so they can be removed; it removes none without a yes. Nothing is written in the reviewed repository's work tree, and no agent writes a file of its own outside the record: each brief says so, and the run compares `git status --porcelain --ignored` of the reviewed work tree before and after (decision 287). Check: review; acceptance (item 98).

### First review

371. **First reading.** The first reading of a first review is the host's `code-review` over the change from the merge-base to the pull request's head, at the level of requirement 368 and with the session's model, passed as `--model` (decision 205). It runs in a child session under `--permission-mode default` with an allow-list of read-only tools and no check of the repository, so a call outside the list is denied and counted, and never with `--comment` or `--fix`. The child session loads no configuration from the head: no settings, hooks, instruction files, skills or server definitions. How it is started so is settled by the spike of decision 287; where no start holds that, the first reading is a stand-in, as the gate has one: an agent of the session is given a patch of the change, written in the record, and the scratch worktree's path, and reads the head there. That spike has not been made, so the skill takes the stand-in and starts no child session until one is (decision 287). When the request names a gate record or an audit report whose head is the pull request's head, that is the first reading and no review is run; a report for another head is refused with both shas. The reading's findings are leads: none is drafted before the checks of requirements 372 and 373. Check: review; acceptance (item 94).
372. **One complete round.** A first review aims to leave no second batch of findings once the author has fixed the first. Before any draft, three checks run on every lead and on the change itself. Siblings: the shared name is searched alone, every hit is classified as the same defect, not the defect or not determined, and the finding records the search and the full list of sites. One hop out from the diff: the consumers of each changed output, in the other repositories the request names too; the tests, documents and comments that state the rule the change alters; and each acceptance criterion of the linked tickets. Citations: every location a draft names is read again at the head before the draft is shown (decision 288). Check: review; acceptance (item 94).
373. **Basis, runs and scope.** Every finding and every proposed fix states its basis, `read`, `run` or `not run`, and the label goes into the comment. A proposed fix is run before it is recommended, or marked `not run`. For a defect seen only at run time, the finding names the path the author most likely ran, why that path hides the defect, and the run that shows it. The review asks what the repository's test suite cannot see, such as a defect of a shared library that the suite replaces with a mock. A disagreement between two readers about run-time behavior is settled by a run. A check the review could not run is listed with its exact steps, and a result the user brings back is taken in before the drafts are final. A read or a call that was refused is reported, in the agent's report and in the run's. A point outside the review's scope that could affect correctness gets a short trace before it is filed as a note: whether a user can reach it, and what happens when they do. Check: review; acceptance (item 94).
374. **The team's conventions, and a disposition for every point.** The team's conventions and precedent are an input and override a generic checklist. They come from the reviewed repository's instruction and contribution files at the base commit, from the files the request names, and from what the session's context holds, and each brief sent to an agent carries them, by path or in full. A sample of the team's review comments, when given, sets the register of the drafts. Every point ends with a disposition, `post`, `note` (kept in the record) or `drop`, with its reason. Severity comes from what breaks and for whom, never from how many readers raised the point. Check: review; acceptance (item 94).
375. **Two texts.** Comments for the author take the findings form of requirement 366, which the skill states in its own words since the plugin works alone: the general point first and its instances after, one recommended change with what would overturn it, the change and whether it blocks in the title, and the small points and scope points in one summary comment. A second, short text is for the person who gates the merge: the verdict, what blocks, and the merge order of a pair. It is sent after the comments, and its verdict is rewritten when the evidence changes. Before the posting step, the reviewer's own open questions are settled by a read or a run, or listed as checks not run under requirement 373, and a test handed to the author has been shown three ways: it passes on the head, it fails when the change it guards is undone, and it passes when pasted where the comment says. Each draft is one file in the record and is shown whole. Check: review; acceptance (items 94 and 96).

### Follow-up review

376. **Follow-up review.** A follow-up starts from the ask and the reviewer's role: what was asked, what the reviewer said in the earlier round, read from the record and the forge's threads, and who holds the vote that gates the merge. Each earlier item is reported as landed or open, from a read or a run at the new head. The author's reply is a claim and is followed to the place it names. The forge's conflict status is not taken as read: a trial merge in the scratch worktree decides. A merge commit gets its own read, of the parts that differ from both parents, since a file that merges with no conflict can still need a change by hand. A pair of pull requests is reviewed as a pair: the comments on both, and the summary, state the dependency and the merge order. Check: review; acceptance (item 95).

### Posting

377. **Posting.** Posting is a step of its own, run only on a request that says `post`, after the drafts were shown in full. Each outward action is approved by name before it runs: each comment, the vote, each thread resolution, each ticket edit, and a merge. The summary for the gating person is posted only as a comment approved by name; otherwise the user sends it. Beside each draft the reply shows its effect on the merge gate, whether it blocks, counts as a vote or changes nothing, and the summary agrees with it. Just before posting, the head and the threads are read again; a head that moved after the drafts were checked stops the step and names the citations to read again. Each post is made from its draft's file, one at a time, and is recorded with the forge's id for it before the next. A draft whose text a thread already holds is not posted again, one whose thread holds another text is reported and left for the user, and the vote is cast only when the user's vote on the forge, read just before, differs from it; so a step that stopped part way can be run again. After posting, every post is read back and compared with its draft by `posts.mjs` (requirement 379), and a difference is reported with both texts. Posted text names no model, agent, tool or run term (requirement 11) and holds nothing of the reviewer's machine: no path, user name or host name (decision 289).
