Architecture is in architecture.md, the order of work in build-plan.md, the hand-run checks in acceptance.md, and the choices with their evidence in decisions.md. Where this document and the architecture disagree, this document wins until it is amended. Nothing here is implemented.

Each requirement ends with how it is checked:

- **test**: an automated test under `tests/`, run by `npm test` and CI.
- **lint**: a rule in `tools/lint.mjs`, run by `npm run lint` and CI.
- **acceptance**: a hand-run item in acceptance.md, recorded with date, machine and CLI versions.
- **review**: checked by reading, once, in the pull request that merges it.

A requirement that rests on a spike names the spike in decisions.md. If a later run of that spike fails, the requirement is amended before the milestone that depends on it merges.

Numbers are never reused. A retired requirement keeps its number with the word "Retired" and the reason.

## Suite

1. **One repository, one marketplace.** The marketplace is named `reimagine-engine` and lists exactly five plugins: `rules`, `loop`, `audit`, `primer` and `gate`, each at `plugins/<name>/`. Before a release a prerelease catalog may list a plugin that is built at a prerelease version (requirement 14), so a second machine can install it from `main` before its release, and may list `repo-docs` until requirement 268 retires it. Until the gate's scaffold milestone the catalog, lint's name list, the README and the repository's hub say four plugins, and that milestone moves all of them to five in one commit (decision 132). Check: lint.
2. **Plugin directories hold only what a user installs.** Under `plugins/<name>/` there are the manifest, the skills, commands, agents, hooks, scripts, output styles and reference files the plugin uses at run time, plus `README.md` and `LICENSE`. No tests, no design documents, no fixtures. Check: lint.
3. **ASCII.** Every shipped file under `plugins/` is ASCII. Check: lint.
4. **License per plugin.** The root `LICENSE` and each `plugins/<name>/LICENSE` is the Apache License 2.0 text with the holder line `Copyright 2026 vibecodedapps.net`. Check: lint.
5. **Prerequisites.** Node 22 or later and, on Windows, Git for Windows. The audit plugin's live checks, work-item validation and collision check also need `jq`; the README says so and says what runs without it. No other tool is required. Check: review.
6. **Prompt first.** The only executable files under `plugins/` are `plugins/rules/scripts/rules.mjs`, the eleven audit scripts (`readonly.sh`, `handoff.sh`, `ledger.sh`, `working-tree.sh`, `revert-tests.sh`, `live.sh`, `memory.sh`, `work-items.sh`, `collisions.sh`, `run-copies.sh`, `report.sh`), the two primer hooks `plugins/primer/hooks/drift.sh` and `plugins/primer/hooks/notice.sh`, and the two gate scripts `plugins/gate/scripts/findings.mjs` and `plugins/gate/scripts/next.mjs` (requirement 318). Every one of them has a test under `tests/`. A new script ships only with its test. A workflow script under `plugins/audit/workflows/` is an executable whose check is `node --check`, the lint rule of requirement 219 and acceptance item 43, because its runtime needs a session (decision 95); none ships until requirement 270's gate is met. Check: lint.
7. **No plugin options.** No manifest declares `userConfig`, and no file references `${user_config.*}`. Check: lint.
8. **Three hooks outside a request.** Only three hooks run without a session request: the rules SessionStart staleness notice, the primer SessionStart memory notice and the primer drift check. No other plugin ships a `hooks/hooks.json`. Check: lint.
9. **Independent plugins.** `loop` and `audit` do not require `rules`; no manifest declares `dependencies`. Each plugin works alone after `/plugin install <name>@reimagine-engine`. Check: lint; acceptance.
10. **Reusable files carry nothing owner-specific.** No shipped file names a person, a person's email address (an address at a `.invalid` domain is allowed), an absolute path under a user's home, or a specific repository other than this one. Check: lint.
11. **Nothing external names a model, agent or tool.** Pull request bodies, pull request comments, ticket comments and commit messages name the activity and the date, never the model, the agent type or the tool that produced the text, and never a review pass or its level. Run records and reports kept in a run directory may name them. Amended 2026-10-27: review passes and levels are added (decision 141). No plugin types an attribution trailer of its own or removes one the host's attribution setting adds; that setting decides alone (decision 136). Check: review; acceptance.
12. **Commit form.** Commits in this repository and commits the loop makes read `type(scope): subject` in lowercase, with a body that says why. A bare `@token` in a subject or pull request text is written in backticks. Check: review.
13. **Moves and renames apart.** A commit that moves or renames files changes no file content; string renames go in their own commit. Check: review.
14. **Versions and tags.** Each plugin has its own version line in its manifest and its catalog entry, which agree. The first release is 0.1.0; before it a built plugin may ship as `0.1.0-alpha.<n>`, a semver prerelease that sorts below 0.1.0, and the 0.1.0 target of every plugin stands. A release is tagged `<plugin>--v<version>` with `claude plugin tag`. A plugin directory that changed since its last tag carries a version above that tag. There is no shared suite version. Check: lint.
15. **One changelog.** `CHANGELOG.md` has a heading `## <plugin> <version> - <YYYY-MM-DD>` for every tagged version of every plugin, prerelease versions included, newest first; a version not yet tagged needs none, so a bump passes lint before its heading is written. Check: lint.
16. **The repository keeps its own instruction file by its own rules.** The root `CLAUDE.md` is a primer hub (requirement 238), and the primer drift hook runs in sessions on this repository through the tracked `.claude/settings.json`. Check: acceptance.
17. **Windows and POSIX.** Every test and script runs on ubuntu, macOS and Windows with Git for Windows, and the awk-using audit scripts also run on mawk. Check: test (CI matrix).

### Mechanism

22. **One target.** The target file is `$CLAUDE_CONFIG_DIR/CLAUDE.md`, else `~/.claude/CLAUDE.md`. It is created when missing. There is no other target. Check: test.
23. **Bytes outside the block are kept.** Every byte before the begin marker and after the end marker is preserved, including a byte order mark, bytes that are not UTF-8, the file's line ending, and a missing final newline. Check: test.
24. **Symlinks.** A target that is a symlink is written through, at the file it points to. A dangling or hard-linked target is refused without writing. Check: test.
25. **Block format.** The block starts with `<!-- reimagine:house-rules begin version=<v> options=<list> join=<none|blank|newline> digest=<16 hex> -->` and ends with `<!-- reimagine:house-rules end -->`. The digest is of the body in LF form; a CRLF file gets a CRLF block. Check: test.
26. **States.** A target is `absent`, `current`, `stale`, `edited`, `malformed` or `declined`. A version change alone with the same rules is `current`. A malformed block is reported with its line numbers and nothing is written. Check: test.
27. **Plan then apply.** `plan` writes a plan file in the plugin data directory and shows the diff, one hunk per changed run, with three lines of context. `apply` refuses when the target changed after the plan, including a file created where none was. Check: test.
28. **Ask per change.** The skill shows the diff and asks before `apply`, once per target change. Check: review; acceptance.
29. **Backup.** An existing target is copied to `<path>.reimagine-backup-<YYYYMMDDHHMMSS>` before any write; an existing backup is never overwritten and the write does not happen. A created file has no backup and `remove` deletes it unless the user added text, in which case only the block is removed. Check: test.
30. **Atomic writes.** The target is written to `<path>.reimagine-tmp-<pid>` and renamed into place, keeping permissions. Two applies started at once both land in the state and plan files; a lock directory `rules.lock` serializes them and a lock left by a dead run is taken over. Check: test.
31. **Remove.** `remove` takes out the block and the bytes of its join, so install then remove gives back the original bytes for LF, CRLF, BOM and no-final-newline files. Check: test.
32. **Decline.** `decline` records the digest; the next plan says so and the staleness notice stays quiet until the shipped text changes. Check: test.
33. **Adopt.** `plan --adopt` finds rules already present outside the block, as a Markdown reader sees them (items, paragraphs, headings; not fences, HTML comments or indented code), removes a full copy including its headings, and puts the block where the copy was. Text that differs, fenced examples, and user text under a heading are kept. A file holding Markdown that adopt does not handle is left alone and the plan recommends decline. Check: test.
34. **Recommendation.** The plan counts the rules already outside the block and recommends `apply`, `adopt` or `decline`; decline only when every rule is already present. Check: test.
35. **Imports.** `@path` imports in the target are followed read-only: at a line start or after white space, not in code, fences, quotes or the block; relative to the importing file, from `~/`, or absolute; four hops; fifty files; 256 KiB per file; a directory, an oversized file or a missing nested file is a read error, not a skip. The plan names what each import holds. Check: test.
36. **Options.** `core` is always applied; `windows` is added on Windows and refused elsewhere. Recorded options are kept on a rerun unless `--options` overrides them. Check: test.
37. **Script output.** A refusal is one line on stdout starting `rules: ` with exit 1; `status` exits 0. Check: test.
38. **Script size.** `rules.mjs` is at most 700 lines and imports only `node:` built-ins. Check: lint.
39. **The skill never edits the file itself.** `/rules` runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs <verb> ${CLAUDE_PLUGIN_DATA}` and relays its output; it never writes `CLAUDE.md` with the Edit or Write tool. The skill sets `disable-model-invocation: true`. Check: lint; review.
40. **The skill names the output style.** `/rules` ends by printing how to select the output style: `/output-style rules:Concise Plain`, or the equivalent `/config` path. Check: review; acceptance.
41. **Staleness notice.** The SessionStart hook, matcher `startup` only, runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs session-start ${CLAUDE_PLUGIN_DATA}` and prints one `systemMessage` line, `rules: the house rules in <path> are older than this plugin's; run /rules to update them`, when the block is `stale` and not declined. It prints nothing otherwise, writes nothing, and exits 0 even when the state file cannot be read. Check: test; acceptance (the message is visible at startup).
42. **Line-ending changes do not hide staleness.** A block whose file changed line ending still reads as current or stale by its rules, and a hand edit still reads as edited. Check: test.

## The `loop` plugin

### Invocation

45. **Prose invocation.** The skill is `run` in the `loop` plugin, so it answers as `/loop:run`; it is user-invocable and its description names "reimagine loop" as the primary phrase and "run the loop" as a secondary one. There is no separate command. The bare `/loop` belongs to the host's bundled interval skill and is not ours. There are no flags; a token starting with `--` is read as prose. Check: lint (frontmatter); acceptance (each phrase invokes this skill, not the bundled one).
46. **Reading block first.** After only the read-only calls that resolve ids (`git remote`, `gh`, `az`, an MCP read, a file read) and before any other tool call, the skill states how it read the request in one block with four headings: Tickets, Mode, Scope, Effort. Each ticket line says how the id resolved (`gh`, `az boards`, `mcp:<tool>`, `file`, `text`). An id that cannot be resolved gets one line and the run continues with the other inputs. Check: acceptance.
47. **Ticket forms.** Accepted forms: `#123` and an issue or pull request URL (GitHub, resolved with `gh`); `AB#12345` or a bare number on a repository whose remote is Azure DevOps (resolved with the Azure DevOps MCP tool if one is listed, else `az boards work-item show`); a Salesforce case number or record id (resolved with a Salesforce MCP tool if listed); a readable file path; pasted text. Ticket text obtained by any means passes through the credential scan before it is written. Check: review; acceptance.
48. **A pull request reference continues its branch.** A pull request URL or number on GitHub that is open, not cross-repository and in the primary repository sets the branch to continue. Its tickets come from the branch record, else from the pull request's closing references, else the run ends `blocked` asking for a ticket, file or description. A pull request on another host is one line and the run continues without it. Check: acceptance.
49. **Modes.** Mode is one of: build and publish (default); plan only ("plan only" in the request); build without publishing ("do not publish", ending `prepared`); continue (a pull request reference, "continue <branch>", an existing record whose `tickets` list holds one of the request's tickets, or an existing record for the predicted branch). "confirm the plan" adds one pause for a clear yes after the plan review. "budget <n> minutes" sets the run budget. "on branch <name>" names the branch. Check: review; acceptance.
50. **Scope.** The primary repository is the session's, or the checkout that "primary <path>" names (requirement 281). "also edit <path>" adds a writable checkout. A path in ticket text that maps to another checkout is adopted only after the user answers a question with a clear yes or a comma-separated subset; any other answer ends `stopped` with the "also edit <path>" form to rerun without the question. Multi-repository scope is never adopted from prose alone. Check: review; acceptance.
281. **Primary checkout by request.** "primary <path>" sets the primary checkout `<checkout>` for the run. The path must be a git toplevel or a linked worktree: `git -C <path> rev-parse --show-toplevel` prints that path, else preflight ends `blocked` naming it. Every primary git command runs as `git -C <checkout>` and every other command that acts on its tree runs in one Bash call as `cd <checkout> && <command>`, the forms of the worktree run; the permission statement counts them as prompts, since the skill pre-approves only the plain forms. The reading block's Scope line names the checkout in use. When the named checkout is a linked worktree, the record of requirement 82 lives in its main checkout, the first `worktree` line of `git -C <checkout> worktree list --porcelain`, and the detached-worktree run of requirement 80 does not apply: a differing flagged path there ends `blocked`, naming the path and the main checkout, which "primary <main checkout>" runs with the exception. The word is "primary", not "in", because the remaining request text is joined into the ad-hoc description and "in" occurs in prose; it mirrors the Scope line. Check: review; test (the phrase in SKILL.md and Step 0); acceptance (item 45).
282. **Base branch by request or configuration.** "base <branch>" in the request, else `.reimagine.json` `base`, names the base branch `<b>` of requirement 76 in place of the remote's default branch. Step 0.2 fetches it with the same explicit refspec, a fetch that fails ends `blocked` naming the branch, and `run.md` and the reading block's Mode line record it (`; base <branch>`). It is the review base (requirement 88), the pull request base (requirement 116) and the branch whose workflow files the deploy judgment reads (requirement 56). An open pull request on a continued branch whose base differs from it ends `blocked`, since the loop never retargets a pull request. An additional repository keeps its remote's default branch. Check: review; test (the phrase in SKILL.md and Step 0; the key in the configuration block); acceptance (item 45).
51. **Effort is a hint.** Words such as "quick", "thorough", "low", "high" set the effort passed to subagents. A floored run (requirement 69) passes effort at least `high` to its reviewers, and no hint lowers that. Check: review.
52. **Echo redaction.** The echoed request text is credential-scanned and redacted before it is printed and capped at 300 characters; the reading block that follows has no cap. Branch slugs come from the redacted text. Check: review.
53. **Credential scan.** Before anything is written to the record, every input is scanned for keys named password, passwd, secret, token, api_key, apikey, client_secret, private_key or connection_string, for blocks under headings containing cred, secret or password, for `AKIA` followed by sixteen uppercase alphanumerics, and for a PEM header. A match asks `keep` or `drop`; `drop` writes `<redacted: key>` in place; any other answer ends `stopped`. Check: review; acceptance.

### Approval scope

54. **What invoking approves.** Invoking the loop by name approves, for that run only: creating a branch, committing, pushing that branch, opening one pull request per repository, editing the body of a pull request this loop opened, commenting once per run on that pull request, and commenting on the source tickets. Check: review.
55. **Instruction files win.** Before changing anything the loop reads the user's instruction files in `$CLAUDE_CONFIG_DIR` when it is set, else in `~/.claude`, never both, since the session loads only that directory's user instruction files, and the permission statement names the directory it read; then the repository's instruction files, `CLAUDE.md` and `.claude/CLAUDE.md` in each folder above the repository's root, which the session loads as project instructions, `~/.claude/CLAUDE.md` among them for a repository under the home folder, and `.reimagine.json`, records every ask-first rule, and prompts for any approved action those rules cover. The loop never removes an ask-first rule. In multi-repository runs the rules of every repository are unioned. Check: review; acceptance.
56. **Always ask.** Force push, `--no-verify`, merging, anything that deploys (including a push or pull request that triggers a deploy, judged from the workflow files on the base branch of requirement 76 and on the branch being pushed), editing repository settings, and opening a new issue always prompt. An answer that is not a clear yes is a denial. Check: review.
57. **Denial.** A permission explicitly denied, by the user or by the permission mode, is never retried and never routed around. A denial in steps 0 to 6 or after the first push marks dependent steps not done, runs the independent ones, and ends `blocked`; a step 7 denial before any push ends `prepared`. A denial is a refused tool call or a non-yes to a permission question; the decision questions of requirements 50, 53 and 49 are not permissions; a missing resource is "not run", never a denial. Check: review.
58. **A dropped call is not a denial.** A dropped read is retried once serially; a dropped write only if a check shows it did not take effect; after any drop, preflight commands run serially. A subagent's report is model output, never approval. Check: review.
59. **Pre-approved reads.** `date`, `sleep` for the CI poll and a budget timer, and read-only `git` and `gh` commands are the only commands the skill's `allowed-tools` pre-approves. Check: lint.

### Roles and models

60. **Orchestrator.** The session model orchestrates, judges, reviews each slice diff and decides; it never implements a slice. No fallback: without it the run stops. Check: review.
61. **Implementer.** Each slice is implemented by an Agent subagent at model `sonnet`, one per slice, parallel for slices with disjoint files, serial otherwise. Parallel implementers run no checks and say so; the orchestrator runs each slice's checks afterwards one command at a time, and a command several slices name runs once. Check: review; acceptance.
62. **Plan reviewer.** A fresh-context Agent subagent at model `fable`, given the request text, the file paths and the required reply shape, told to read and report only, reviews the plan in step 3. On a model or tool error the call is retried once at `opus` and the swap is recorded and named in the report; a denial or a timeout is not an error. The reviewer stays swapped for the rest of the run. Step 5 has no fresh reviewer; its one pass is requirement 63. Check: review; acceptance.
63. **Final review role.** Every run's step 5 uses the built-in `code-review` skill with an explicit level (requirement 285) and the range `<merge-base>...HEAD` as a full sha, never `--comment` or `--fix`; `code-review` covers the primary whenever it is the session's checkout, a linked worktree included; where that skill is not listed, or the diff lives in a worktree that is not the session's checkout or in an additional repository, an Agent subagent at `opus` reviews a patch file with the acceptance criteria and the same reply shape, with the level word passed as its `effort` (`xhigh` where the word was "max", requirement 285), once. The stand-in is not a swap and is named in the report. Check: review; acceptance.
64. **Reader.** Read-only work worth splitting out runs on `haiku`; the orchestrator may instead read itself. Check: review.
65. **Model configuration.** `.reimagine.json` `models` accepts `implementer`, `reviewer`, `fallback-reviewer` and `reader`, each one of `sonnet`, `opus`, `haiku`, `fable`. It never changes the risk floor or the step 5 role. Unknown keys and bad values are reported and ignored. Check: review; acceptance.
66. **Agent calls carry the request shape.** A plan review asks for a numbered list of objections ranked by impact, each marked blocking or non-blocking with a confidence of high, medium or low and a one-line reason, ending with `NO BLOCKING OBJECTIONS` when there are none, and asks the reviewer to name the code that reads each contract change and confirm the shapes match. Blocking means the change would ship wrong behavior, break an acceptance criterion, or violate a repository rule. The `opus` stand-in of requirement 63 receives the plan, the inputs, the acceptance criteria and a patch file written from `git diff <merge-base>` after new files are marked with `git add -N`; the `code-review` skill reads its range itself. An empty diff is never sent to review. Check: review.

### Budgets and rounds

67. **Per-call budgets.** Minutes: `subagent` 20 for an implementer call, `review` 30 for a review pass, `check` 15, `ci` 45. `.reimagine.json` `timeouts` overrides any of them; `run` sets the run budget. Where a tool takes a timeout the budget is passed; the Bash foreground cap is 10 minutes, so a longer check runs in the background beside a background `sleep` of its budget, since a background command notifies only when it ends, and whichever ends first stops the other. An Agent or SendMessage call is judged against its budget by the `duration_ms` of its completion notification, and by `date` before and after it only when the notification carries none; when an implementer call returns the orchestrator records its checkout's status and file hashes as `post-<n>`, beside the call's `pre-<n>`; a notification that arrives for an implementer call after that call already returned is not a new call and changes nothing unless a path differs from `post-<n>` that no later call, edit or commit of the run changed, which ends the run `blocked` naming the path; any other late notification, or one for an agent the run did not launch, is logged and changes nothing; the implementer brief tells the implementer to start no background command (decision 149). Check: review.
68. **Run budget.** The default run budget is 240 minutes, overridden by "budget <n> minutes" in the request, then `timeouts.run`, then a session instruction. Waits on questions are excluded. On expiry the output is kept and the run ends `blocked`, naming the budget; after a push the pull request is left as it is. Check: review.
69. **Risk floor.** A change that adds, alters or removes an auth check, a permission rule, a schema or migration, a row-level security policy, a data access path, or a public API's signature or behavior, directly or through shared code or configuration, is floored: reviewers receive effort at least `high`, and the report says which trigger applied. Incidental edits (a typo in a migrations README, a comment in an auth module, a rename with no signature change) do not trigger it. The floor is judged at the plan and again on the actual diff after step 4, and never falls. Check: review; acceptance.
70. **Higher-risk rule.** Retired 2026-10-25 (decision 128): the rule selected only the step 5 role, which requirement 63 now fixes for every run; the risk floor of requirement 69 alone sets the step 5 level (requirement 285). Check: review.
71. **Date discipline.** `date -u +%Y-%m-%dT%H:%M:%SZ` runs only at the start of step 0 and of each step, before and after each timed call (for a batch of Agent calls, before and after the batch, while each call's budget is judged by its notification, requirement 67), after each push returns, at the terminal state, and just before and after each question. Times are copied into the record from the command output, never from memory or arithmetic. Check: review.
72. **Round cap.** No step repeats more than three times. A round is one pass by the stage's reviewer plus the fixes it leads to. The orchestrator's single fix after the step 4 cap is not a round; step 5 has one pass per run and no round (requirement 111). Each CI repair cycle gets one step 5 pass and one full step 6 run; cycles are capped at three. Check: review.

### Preflight (step 0)

73. **Nothing written before the record exists.** Until step 0.5 the run writes nothing; a failure before it prints the report only. The one exception is a worktree run, which writes the `.reimagine/` exclude, the record directory and the worktree at step 0.3; from then a failure writes the report to the record. Check: review.
74. **Host detection.** The remote is the one `gh repo view` resolves, else `origin`, else the only remote; several remotes without `origin` is a preflight failure. A GitHub host where `gh` fails ends with "gh not authenticated". On a non-GitHub host steps 0 to 6 run, the end of step 6 writes the run's body file from `pr-body.md`, and the run ends `prepared` with the push commands and the body file to paste. A remote is Azure DevOps when its host is `dev.azure.com`, `ssh.dev.azure.com` or `vs-ssh.visualstudio.com`, or ends in `.visualstudio.com`; preflight records that and the remote's organization and project. Check: review; test; acceptance.
75. **Permission statement.** Step 0.1 prints the approved actions, the carve-outs, and for each action whether a prompt will occur, from the permission mode, the settings files and the allow rules; an undeterminable permission counts as a prompt. It predicts the worktree, credential, adoption, plan-confirmation and branch questions, and prints "this run will prompt at: ..." or "this run is unattended", naming the request forms that avoid each question. Check: review; acceptance.
76. **Base branch and base commit.** Step 0.2 resolves the base branch `<b>`: "base <branch>" in the request, else `.reimagine.json` `base`, else the remote's default branch (requirement 282); fetches it with the explicit refspec `+refs/heads/<b>:refs/remotes/<r>/<b>`; and records the base commit. A continued branch equal to the base branch is rejected. Check: review.
77. **Continue checks.** A continued branch must pass `git check-ref-format --branch` and must not be checked out in another worktree (the failure names the three ways around it: start the run inside that worktree, "primary <that path>", or "also edit <that path> on <branch>"). A branch named in the request without a record must exist as the exact ref `refs/heads/<branch>` on the remote. A branch with a record may exist locally only, as after a `prepared` run, or nowhere, as after a plan-only run, and is then created like a new branch; when it also exists on the remote, the local tip must be at or behind the remote head and is fast-forwarded to it. A local branch that diverged ends `blocked`. The session HEAD ends at the branch tip. Check: review; acceptance.
78. **Open pull requests.** On GitHub, `gh pr list --head <branch> --state open --limit 100 --json number,state,baseRefName,url,isCrossRepository`, filtered on `isCrossRepository`; 100 entries counts as incomplete and fails; one open pull request is recorded; several end `blocked`. Check: review.
79. **Clean tree.** `git status --porcelain` must be empty and `git diff --cached --quiet` must pass, else `blocked`; the loop never stashes, resets or cleans. Check: review; acceptance.
80. **Flagged files.** Paths marked skip-worktree or assume-unchanged are compared against HEAD with `git cat-file --filters`; a difference with a clean status creates a detached worktree at `<checkout-parent>/<checkout-name>-reimagine-<branch-slug>`, beside the checkout and never inside it. Dependencies are installed in the worktree before the baseline, else the check is "not run". A switch in a worktree detaches in place and fast-forwards with `git fetch .`. Check: review.
81. **Malformed configuration.** A `.reimagine.json` that does not parse ends `blocked`. All of its keys are optional: `commit`, `checks`, `timeouts`, `models` and `base`. The `gate` key belongs to the gate plugin (requirement 313) and is skipped without a report; any other unknown key, and a bad value, is reported and ignored. Check: review; test (the configuration block in the skill is byte-identical to the README's and has exactly those keys).

### Record and idempotency

82. **Record location.** The record lives at `.reimagine/loop/<branch-slug>/` in the primary repository, where the slug is the branch name lowercased with every run of characters outside `[a-z0-9]` replaced by `-`, at most 60 characters. `.reimagine/` is added to `.git/info/exclude`, never to `.gitignore`. Nothing under `.reimagine/` is ever staged. `steps.json` records the exact branch name; a record whose branch differs from the run's branch is a slug collision and ends `blocked`. Check: review; acceptance.
83. **Branch known at preflight.** The branch is the continued one, the "on branch" one, the branch of the one existing record whose `tickets` list holds one of the request's tickets (several such records stop the run), or the predicted name: `fix/<ids>-<slug>` when a ticket is labeled bug or titled "fix", else `feat/<ids>-<slug>`, else `work/<slug>`; a collision with an existing local or remote branch that has no record ends `blocked`. A record whose pull request merged or closed ends `blocked`, naming the pull request and the "on branch" form that starts a new branch. Check: review.
84. **Record files.** `inputs.md` (invocation block with time, each ticket as fetched, files and text, verification notes, drift corrections, buildable status, risk floor), `plan.md` (plan plus a review log per round), `run.md` (the durable log), `steps.json` (the completion record), `report.md` (every terminal state), `handoff.md` and `audit-manifest.json` (when the run has its own commit), patch and snapshot files, and `pr-body.md` and comment bodies, which are never committed. Check: review.
85. **Completion record.** `steps.json` holds the branch, a list of runs with number, start, end and terminal state, and one entry per step with `status` (`running`, `complete`, `failed`, `skipped`), the run number, start and end, the hashes of its inputs (for Steps 1 and 2, each open input's version: an issue's `updatedAt`, a work item's `rev`, a case's `SystemModstamp`, or the hash of a file or description), and its output paths. The entry is written `running` when the step starts and `complete` only after its outputs exist; it is written through a temporary file and a rename; it is the only record of completion. Check: review; acceptance.
86. **Second run appends.** A second invocation on the same branch appends run `n+1` to the same record; `run.md` and `inputs.md` gain a dated section per run; nothing from a prior run is modified except `steps.json`, `plan.md` (appended), and `report.md`, `handoff.md` and `audit-manifest.json` (rewritten). Per-run files without a counter (the pull request body, ticket comments, patches) take a `-run<n>` suffix from run 2 on, so none is overwritten. Check: acceptance.
87. **Preflight reads the branch state.** On an existing record the loop lists `git log <merge-base>..<tip>`, where the tip is the remote head when the branch exists on the remote, marks every commit either as its own (named by a commit line the loop wrote in `run.md`) or foreign, writes the list to `inputs.md`, and judges tickets done by their recorded closing commit. Check: acceptance.
88. **Review base.** Every diff review and every "changed lines" count uses the merge-base with the base branch of requirement 76, so foreign commits are reviewed with the loop's own. Check: review.
89. **Built slices are not rebuilt.** A slice whose closing commit is on the branch is skipped; a ticket with a closing commit is marked done. A slice the loop built to `complete` and did not commit records its file hashes, and a slice whose call failed or that is still `running` records none, so its partial edits never count as committed, each `git hash-object --no-filters -- <path>` of the working copy, the `--` keeping a path that starts with `-` from being read as an option, and counts as committed when the branch tip holds them, as after a `prepared` run that the user committed: for each path, `git cat-file -e <tip>:<path>` succeeds, since a path the tip lacks would hash as the empty blob, and the recorded hash equals either `git rev-parse <tip>:<path>`, the blob as committed, or `git cat-file --filters <tip>:<path> | git hash-object --stdin --no-filters`, the blob as a checkout writes it; under `core.autocrlf` the first matches a working copy whose line endings the commit kept and the second one whose endings it converted (decision 152). Check: test (the three commands in `record.md`); acceptance (item 60).
90. **Same tickets, no new work.** When every ticket is done and the plan has no open slice, the run verifies the checks (step 6). When the work is published (the run that last reached step 7 ended `done` and a pull request is open on the branch), it rewrites the report, posts nothing, commits nothing, and ends `done`; otherwise step 7 publishes the committed work. Check: acceptance.
91. **New tickets extend the plan.** New tickets add slices to `plan.md`, which goes through plan review again; the new slices are built and reviewed; the pull request this loop opened gets its body updated once per run with `gh pr edit --body-file <absolute path>` and one comment per run; a pull request the loop did not open gets a comment only and its body is never edited. Check: acceptance.
92. **Interruption safe.** Every step records completion before the next starts. A rerun recomputes the input hashes, reuses every step whose inputs are unchanged and whose outputs exist (step 4 only when its slices are committed), rechecks the tree, and resumes at the first incomplete or changed step. Step 3.7 sets up the checkout in every run that builds or checks. Check: acceptance.
93. **Never rewrite.** The loop never force pushes, rebases, resets or amends. Before each push it reads the remote head with `git ls-remote`; a head that differs from the one preflight fetched ends the run `blocked` (fast-forwarding belongs to preflight, requirement 77). Check: review; acceptance.
94. **Terminal states.** `done` (pull request open, CI green or not applicable, report written); `plan-only`; `prepared` (every step through 6 complete, publication withheld before any push, with the publish commands); `blocked` (a blocking defect, a denied permission, a budget exceeded, a preflight failure); `stopped` (a question the run cannot decide, before any branch is created). After `blocked` nothing more is published; pushed work stays and is linked. Check: review.
95. **Snapshot before an implementer call.** Before each implementer or fix call the loop records `git status`, a patch and file hashes. After a failed call it restores only paths that were clean before the call; anything else ends `blocked`. Check: review.
96. **Commit snapshot option.** With `.reimagine.json` `commit: true`, each run that publishes commits `docs/runs/<branch-slug>/plan.md` and `report-<n>.md` with state `publishing`, and the terminal report is posted as a pull request comment in its external form: the header without the lines that name local paths, What changed, Checks, Deferred items, and Blocked, stopped or prepared, without the Risk, Decisions, Findings rejected and Log sections, so that it names no model, agent or tool. Check: review; acceptance.

### Plan (steps 1 to 3)

97. **Verification before planning.** For each ticket the loop reads the inputs, verifies claims (for a bug it reproduces or runs a check that confirms or rejects the explanation), records drift between the ticket and the code in `inputs.md`, and marks each input buildable, partial or blocked. Check: review.
98. **Repository gate.** A candidate checkout (an absolute path in the inputs that `git -C <dir> rev-parse --show-toplevel` maps to a checkout other than the primary, its submodules or the adopted ones, and that the inputs ask to change) triggers the adoption question of requirement 50; one found later ends `blocked`. A submodule path is not a separate repository. Check: review.
99. **Plan content.** `plan.md` holds, per input, scope, acceptance criteria and buildable status; across inputs, shared changes, migrations and API changes, tests, checks, order of work, and slices with disjoint files; per slice, the files owned, the change, criteria, tests, checks and the implementer. Slice count is a plan property. A slice is sized to fit one implementer call within the subagent budget in force (requirement 67), and the plan step names that budget and its source where it says when to split, since a call past it ends the run `blocked`. Check: review; test (the budget in Step 2).
100. **Plan review rounds.** Each round verifies every objection, revises, appends a review log to `plan.md`, and is done when the reply ends `NO BLOCKING OBJECTIONS` and the orchestrator finds none. A disagreement that is the user's call ends `stopped`; the cap with a blocking objection ends `blocked`. Check: review.
101. **Plan only.** In plan-only mode the run ends `plan-only` after the review, having changed nothing in the tree. A plan confirmation not answered with a clear yes also ends `plan-only`; a change request is another round within the cap; after a yes the clean-tree, flagged-file, branch, remote-head and pull request checks run again. Check: review; acceptance.
102. **Execution setup.** After the plan is final the loop reverifies against the base when the base moved, creates or switches to the branch, discovers the checks and runs the baseline once, and installs plan-added dependencies after the ask-first yes and before any implementer. Check: review.
103. **No comment before the plan.** Nothing is published before the plan is final, and nothing new is published on a blocked run. Check: review.

### Build (step 4)

104. **Slice brief.** Each implementer receives its slice from `plan.md`, the files it owns, the acceptance criteria, the checks, the repository's line-ending convention, the subagent budget in force, and the instruction to change nothing outside its files, add nothing the brief does not ask for, and start no background command. Check: review; test (the budget and background items of the brief).
105. **Slice review.** The orchestrator reviews each slice diff with `git add -N` then `git diff <merge-base> -- <slice files>`, checks line endings with `git ls-files --eol`, and sends findings back; three rounds per slice, then one orchestrator fix; a still-blocking finding ends `blocked`. Check: review.
106. **Re-evaluation.** After step 4 the risk floor is judged on the actual diff. Check: review.
107. **Baseline failures.** A check failing on the base is matched by test names, not counts, since some failures are timing-dependent. Check: review.

### Final review (step 5)

108. **Integrate first.** Step 5.1 runs the full suite on the integrated tree and fixes regressions; every later edit is logged. Check: review.
109. **One pass.** Step 5.2 is one pass of the `code-review` skill (requirement 63) over the complete diff from the merge-base, at the level of requirement 285, after `git diff <merge-base> --stat` shows a change; an empty diff is recorded as "no changes" and sent to nothing. The pass has the review budget of requirement 67; a pass past it ends the run `blocked` naming the budget. Check: review.
110. **Triage.** The orchestrator sorts every finding of the pass into one of three buckets with a one-line reason, the buckets of requirement 299: fix (a correctness finding inside the change), defer (reuse, simplification, efficiency, or a pre-existing issue the change did not introduce) and reject (a false positive). A finding matching a rejection recorded in `run.md` or `plan.md` keeps its disposition unless it brings new evidence. The fix bucket is applied in one batch through the implementer of the slice that owns the code, after a snapshot (requirement 95); the orchestrator reads the fix diff as step 4.3 reads a slice, and a fix the read finds wrong goes back to its implementer once, then is restored from the snapshot and its finding deferred with the reason; deferred findings join the deferred items of requirement 119 and rejected ones the report's rejected list, and neither touches code. Check: review.
111. **No second pass.** The skill does not review the fixes again in the same run: step 6 verifies the checks, and the report suggests the gate for a converged review (requirement 120). A CI repair cycle runs one more pass (requirement 127). Check: review.
285. **Step 5 level.** The level typed to the `code-review` skill is the effort word's level in force (`low`, `medium`, `high`, `xhigh`), `high` with no effort word, at least `high` on a floored run (requirement 69), and never above `xhigh`: the word "max" gives `xhigh` to the skill while Agent calls keep `max`, and `ultra` is never typed (decision 122). The level is recorded in `run.md` and in the manifest's `reviews` key (requirement 286). Check: review; test (the level table in `risk.md`).

### Checks (step 6)

112. **Discovery order.** `.reimagine.json` `checks` first, then manifest-defined test, lint, typecheck and build commands (npm scripts, Makefile, pyproject pytest, ruff and mypy, cargo test and clippy, go test and vet, gradlew check), then CI jobs that run those; a CI job not mappable to a local command is deferred to CI, not guessed. With a `checks` key those commands are the ones run, and the manifests and the CI jobs are still read: each CI job that no configured check covers is named as deferred to CI in `run.md` and the report, so a gap shows before publishing. Check: review; test (the sentence in `SKILL.md`, the README and Step 6.1).
113. **Reuse.** Step 6 reuses the step 5.1 run when no edit was logged since. Each failure not matching the baseline is fixed through the owning implementer after a snapshot, as step 5.1 fixes a regression, and step 6 runs again, at most three times before publication, plus one run per CI repair cycle (requirement 127). Check: review.
114. **Not run versus denied.** A check without its resource is "not run" with its exact command and directory; "denied" means only a refused permission. Check: review.

### Publish (step 7)

115. **Commit.** Paths are staged by name, never `git add -A` or `.`; nothing under `.reimagine/` is staged; after a run's first push, that run commits only CI repairs. Check: review.
116. **Push and pull request.** `git push -u <remote> <branch>`, never forced, then `gh pr create --title "<title>" --body-file <absolute path>` against the base branch of requirement 76, where the title is the single ticket's title or the plan's one-line summary, at most 70 characters; every `--body-file` is an absolute path. A pull request opened on a continued branch lists the commits from before the run and says they were reviewed as part of this run's diff. Check: review; acceptance.
117. **Body sections.** `pr-body.md` has, in order: What changed (per input, complete or partial), Drift corrections, Decisions for the reviewer, Checks not run, Related pull requests, Closes. `Closes <ref>` only when every acceptance criterion is confirmed met, else `Refs <ref>`; one line per ticket; file and text inputs get no closing line; across repositories only the ticket's own repository closes it. An Azure DevOps ticket is `Refs AB#<n>` on GitHub and `Refs [<type> <n>](https://dev.azure.com/<org>/<project>/_workitems/edit/<n>)` on an Azure DevOps remote, with `<type>` and `<project>` from the work item read (`System.WorkItemType`, else `Work item`; `System.TeamProject`, else the remote's project, spaces as `%20`) and `<org>` from the remote; a `Refs` line does not attach the work item, so a `prepared` report asks the user to link it. On an Azure DevOps remote the description is capped at 4,000 characters, so the body is always the short form (Related pull requests, Closes, and "Details are in the first comment.") and the full body, What changed included, is a comment file to post first. On a non-GitHub host the body covers every input of every run of the record. Check: review; test.
118. **Ticket comments.** After the pull request is open, one status comment per ticket the run took up, where a ticket done at preflight gets none unless no run has commented on it: state (complete, partial, blocked), the pull request link, criteria met, not met or not confirmed with evidence, not done, deferred. GitHub through `gh issue comment`; Azure DevOps through the MCP tool, else `az boards work-item update --discussion`; Salesforce through its MCP tool; a host without a tool gets the comment text in the report instead. No comment is posted on a blocked run and no issue is opened. The text names no run-internal path, model, agent, tool, review pass or level. Amended 2026-10-27: review passes and levels are added (decision 141). Check: review; acceptance.
119. **Deferred items.** Each deferred item is listed with its reason in the report and the pull request body, or, on an Azure DevOps remote, in the full body written to the comment file to post first; none becomes an issue. Check: review.
120. **Handoff and manifest.** When the run has its own commit, `handoff.md` (requirement 137) and `audit-manifest.json` (requirement 286) are written in the record. When the run has its own commit, the report's `Gate:` line suggests `/gate PR <n>`, or `/gate this branch` when no pull request exists, for a three-dot diff of 500 or more changed lines, noting that the command needs the gate plugin, and its `Audit:` line suggests `/audit:run "<absolute manifest path>"` when the work spans more than one repository or more than one ticket, and after the gate when the line count alone called for one. A pull request is named in the manifest only when the live remote head equals the local HEAD. Check: review; acceptance.

### CI watch

121. **Reads name the host.** Every `gh api` call passes `--hostname`, is spelled out as one endpoint, runs one read per Bash call, and never inside a shell loop. A failed read ends `blocked`, except an HTTP 403 whose message says to upgrade or make the repository public, which means no rulesets. Check: lint (backtick spans); review.
122. **Required checks.** Read from `repos/{owner}/{repo}/branches/<base>` `.protection` and from `rules/branches/<base>` with pagination, including required workflows, never from `/protection`. Check: review.
123. **Pull request state at every poll.** `gh pr view --json headRefOid,mergeable,baseRefName,state` plus the merge commit sha. Not OPEN ends `blocked`; a retarget ends `blocked`; the live remote head must equal the last pushed sha, with a stale `headRefOid` pending for two minutes; `CONFLICTING` ends `blocked` at once. Check: review.
124. **Results.** Latest result per context and per check suite, from check-runs with `filter=latest`, statuses, and `actions/runs?head_sha=` for required workflows. Pass is success, neutral or skipped. The gated commit is the test merge commit when it has results, else the head. A status-only check that names an app ends `blocked`. Check: review.
125. **Applicability.** `pull_request_target` is judged from the base branch's file; branch, path and type filters apply; skip markers make a workflow not applicable but required checks stay required; a deferred check whose filters exclude the pull request is not expected. Check: review.
126. **Green.** Every required check, every deferred check and every applicable workflow reported, and every latest result passed. CI is not judged before two minutes after the push; polls are about thirty seconds apart, each wait one `sleep 30` run in the background; pending past the `ci` budget ends `blocked`. Not applicable only when nothing is required, applicable, expected or seen within two minutes. Amended 2026-10-27: the wait runs in the background, since the host blocks a standalone `sleep` in the foreground (decision 140). Check: review; test (the wait in `ci-watch.md`).
127. **Repair.** A red result re-enters step 5 for one pass (the fix through the owning implementer after a snapshot, then one `code-review` pass over the whole diff and its triage) and step 6, at most three cycles; still red ends `blocked` with the pull request linked. Check: review.

### Multi-repository

128. **One pull request per repository with a diff**, each on its own branch and base, with its own baseline and checks; no slice spans repositories. Bodies carry "Related pull requests" with "pending" first, then each body the loop opened is edited once with the sibling links. `done` needs every pull request green; a block in any repository stops publication in all, except the sibling-link edit. Check: review; acceptance.
129. **Commands per repository.** Git uses `git -C <path>`; gh uses `-R <host>/<owner>/<repo>` or runs inside the checkout. A host mismatch between repositories ends `blocked`. Check: review.
130. **Skip-worktree paths.** No slice may edit a skip-worktree path of an additional repository, since the edit is invisible to diff, `add -N` and staging. An additional repository's review reads a patch from `git -C <path> diff`. Check: review.
131. **Branch suggestion.** When a continued branch must be chosen among candidates, the suggestion uses the shared-stem rule: the longest common prefix of the names, not cut at `/`, never a default-branch prefix. Check: review.
132. **Handoff bundle order.** The first bundle is the primary, then the "also edit" order; a verified check is listed only for the first bundle. Check: review.

### Reporting

133. **Report compiled from the record.** `report.md` is written at every terminal state from `run.md`, never from memory. Every section is present; an empty one says "none". Check: review.
134. **Header.** Run number, branch, record path, terminal state, host, run budget and its source, base commit, merge-base, worktree, repositories, pull request, CI state, handoff, gate and audit lines. Check: review.
135. **Sections.** Attended or unattended (prompts predicted and seen, question waits); Risk (floor trigger, step 5 level, stand-in, swaps); What changed (per input, completion, changes, criteria with evidence, drift); Decisions (choice, reason, who decided: user, plan confirmation, review or run); Findings rejected and why; Checks (run, not run with command and directory, deferred to CI, failing at baseline with evidence); Deferred items; Blocked, stopped or prepared (what, steps not done, where the work is, what would unblock it, the exact commands, and for a `blocked` run that left slice edits uncommitted the `git add <paths>` per slice whose status is `complete`, `git commit` and, when the branch exists on the remote, `git push <remote> <branch>`, with the note that a rerun then finds those slices committed, and each other slice named as not done with its paths left out, with the note that the rerun's Step 0.3 stops on those paths until they are committed, restored or moved out of the tree); Log (implementer per slice, rounds, elapsed against budget). Check: review.
136. **Headless reports.** Text asked of the model before a Skill call is not shown in a headless session, so the report header carries everything a reader needs to find the record. Check: review.

### Handoff format

137. **Typed handoff.** `handoff.md` starts with frontmatter `reimagine-handoff: 1` and `generated: <ISO 8601>`, then the sections Bundles, Tickets, Decisions, Raised tickets, once each in that order; the audit's `handoff.sh check` validates it when the audit reads it, and the loop runs no check of its own. Check: review; test (audit `handoff.sh`).
138. **Ticket entries.** Each `### <ticket id>` carries, in order, type, state, iteration, owner, parent (optional), links (optional), bundles, problem, decision, commits (`- <bundle> <sha>: <text>`), verified (`<statement>; check: <check|not recorded>`). Ids are normalized to `github:owner/repo#n`, `ado:<org>/<project>#<n>`, `sf:<case number>` or `file:<path>`. Check: review; test.
139. **Decisions.** Each `### D<n>` carries ticket, decision, rationale, options (`chosen:` or `rejected: ...; why: ...` or `none recorded`), decided_by (`role: <role>`, `checkpoint (recommended option taken)` or `not recorded`; never a person's name and never a model, agent or tool), recorded_at, status. The record's four deciders map to decided_by in one table that the loop's `handoff.md` and the audit's `handoff.md` carry word for word: user to `role: session user`, plan confirmation to `role: session user (plan confirmation)`, review to `checkpoint (recommended option taken)`, run to `role: orchestrator`. Check: review; test (the two tables are identical).
140. **Parent and links.** The GitHub parent is read through GraphQL with `--hostname`, late in the run so the run's own pull request is included; a failed read writes no key, never `links: none`. Check: review.
141. **Written only with a commit.** The handoff is written only after the run's own commit, in any terminal state; the loop never commits in order to write one. Check: review.
286. **Manifest `reviews` key.** `audit-manifest.json` gains `reviews`, the step 5 level and its findings by bucket: `{"level": "<level>", "fixed": [...], "deferred": [...], "rejected": [...]}`, each finding as `{"file": "<repository-relative path>", "summary": "<one line>"}`, with empty lists when the pass found nothing. The audit ignores the key (requirement 145); the gate writes beside it (requirement 315) and does not read it. Check: review; test (the shape in `handoff.md` equals the README's).

## The `audit` plugin

### Invocation

142. **Prose invocation.** The skill `audit` is user-invocable and its description names "reimagine audit". Requests such as "reimagine audit PR 123 and 124 in app, tickets AB#4567 and AB#4580" are read into bundles; a manifest file path is accepted and is what the loop handoff writes. Thin commands `/audit:run`, `/audit:resume`, `/audit:act` and `/audit:handoff` forward to the skill. Each command holds `$ARGUMENTS` unquoted, so a manifest path and the words after it are separate tokens, and only quotes the user typed keep text together. Check: lint (frontmatter); test (`tests/audit/lint.sh` fails on a command file that quotes `$ARGUMENTS`); acceptance (item 68).
143. **Reading block.** After only the read-only calls that resolve ids and before any other tool call, the skill states bundles (repository, pull request or branch and base, tickets), references, sources of truth, claims files, effort hint, budget and model overrides, and how each ticket resolved. Check: acceptance.
144. **Effort is a hint; size sets the default.** The default tier is `low` for one bundle, one ticket and under 500 changed lines; `medium` up to three bundles, five tickets and under 5,000 lines; `high` otherwise. A hint ("effort high") overrides it. The tier sets the pass-one scopes, how much pass two attacks, and whether the late adversary runs. Check: review.
145. **Manifest.** Keys: `bundles[]` (`repo`, `pr` or `branch` plus `base`, `tickets[]`, `ticket_token`, `run_once`, `head`, `test_command`, `test_run`, `test_paths`, `test_setup`, `test_timeout`), `references[]`, `sources_of_truth[]`, `claims[]`, `scratch`, `forge_exports`, `groups[]`, `questions`, `models`, `budget`, `max_agents`, `_test`. `reviews` (written by the loop, requirement 286) and `gate` (written by the gate, requirement 315) are ignored and not an error, since stage 1 reads only the keys it names (decision 129). A bundle's `checks` (read by the gate, requirement 300) is ignored the same way: stage 1 reads only the bundle keys it names, so a key it does not name is neither read nor an error. Validation messages name the key. Check: review; test (fixture manifests).
146. **Exported forge files.** A ticket or pull request on a host without a tool is supplied as a `file:` export in markdown with frontmatter or JSON; a ticket requires id, url, title, state and description, a pull request id, url, title and body, every file source, exported_by and exported_at; a missing key stops the run. `forge_exports.command` is recorded, never run. An Azure DevOps or Salesforce MCP tool used for a read is recorded as `mcp:<tool>`. Check: review; test.
147. **Pause background fetch.** After the summary the skill tells the user to pause background fetch, for example VS Code `git.autofetch`. Check: review.

### Stage model

148. **Nine stages.** Orient, digest, domain map, pass one, pass two, second opinion, converge, report, act, in that order with these dependencies: 1 alone; 2, 3 and 4 together; a per-group barrier opens stage 5 when 2 and 3 are done and top-ups finished; 6 after every pass two; 7 the late adversary and the merger; 8 always. A stage whose input is absent is `not_applicable`; a failed stage counts as satisfied and the run ends `partial`. Check: review; acceptance.
149. **Completion record.** `stages.json` holds `plugin_version`, `approvals[]` (`fetch`, `live`, `export-over-1gb`, `background-fetch`, `local-branch`) and per-stage entries with `status` (`running`, `complete`, `failed`, `not_applicable`, `superseded`), `inputs` as file hashes from `git hash-object --no-filters`, `outputs`, `agents[]` (type, requested model, scope, start, end, tokens labeled "task notification, subagent_tokens; scope not documented", duration, result), `swaps`, `superseded`. It is written through a temporary file and `mv -f`, the entry goes `running` at start and final only after the outputs exist and the read-only check passed, and it is the only record of completion. Check: review; acceptance.
150. **Roles.** Digester `haiku`; mapper and merger `sonnet`; auditor and adversary `opus`; second opinion a fresh `adversary` at `fable`. The manifest `models` key overrides any role with `opus`, `sonnet`, `haiku` or `fable`. Agents are launched with the Agent tool as `audit:<role>`, in the background, never as a fork, never general-purpose, each with its own scratch folder. Check: review; acceptance.
151. **Failure ladder.** Digester, mapper, auditor and adversary: relaunch on the same model, then on `fable` as a swap, then the scope fails. Merger: the orchestrator merges, a second failure fails stage 7. Second opinion, per batch: relaunch on `opus`, then stage 6 fails. An agent fails when it returns an error, when its last line is not `status: complete`, or when fault injection marks it failed. Swaps are recorded and named in the report. Check: review.
152. **Queue and budget.** At most `max_agents` (default 8) agents run; launch order digests, maps, pass one; relaunches go first; scope is never merged or dropped to fit. A soft budget applies only to the invocation that gave it; once expired nothing more launches from stages 2 to 7, unstarted stages are recorded `failed` with "not run: budget expired", and the run goes to stage 8. Check: review.
153. **Orient.** Stage 1 refuses partial clones, sets `GIT_NO_LAZY_FETCH=1`, asks once for one `git fetch --no-tags --refmap=` into remote-tracking refs, takes the read-only baseline per repository before any other work, builds a working-tree head with `working-tree.sh` when asked, reads forge data into files without passing it through the model, writes the three-dot diffs with `--no-ext-diff`, exports trees by one `git cat-file --batch` stream, prepares revert keys, writes claims, groups, the brief and the stage entry. Check: review; test.
154. **Digest.** Applicable when a source of truth is a document corpus (more than half of its files have document extensions). Chunks of about 450,000 bytes filled with whole directories; oversized files split at the last LF into byte ranges read in slices of at most 24,000 bytes; an incomplete read ends `status: failed at byte <offset>`. Check: review; test.
155. **Domain map.** Per-ticket questions `<ticket>-M<n>` with group ids; the mapper answers with quotes or `not found` with the search used. Check: review.
156. **Pass one.** Scopes by tier: `low` one `combined`; `medium` one per group plus `tests-hygiene` plus `interactions` with more than one bundle; `high` one per group plus `tests`, `hygiene`, `interactions`. The barrier compares `consumed:` hashes with the digest and map outputs and runs a top-up per miss until none remains. A missing Decisions, Scope or Outward trace section is `not assessed`, not a failure. Check: review; test.
157. **Pass two.** A fresh adversary per complete pass-one report, never a continuation, attacking none, the five riskiest, or all Verified OK and outward-trace entries by tier, writing verdicts, challenged sections, coverage gaps, new findings `<scope>-P<n>` with `origin: pass2`, map corrections (one round of top-ups writing `<scope>-T<n>`), claims challenged. The ledger `ledger/5.md` is built by `ledger.sh build5` from `ledger/inventory.txt` and checked with `ledger.sh check --through 5`, one retry. Check: review; test.
158. **Second opinion.** Stage 6 always runs. A fresh `adversary` at `fable` (then `opus`) receives the request file with every finding including dropped ones, every pass-two file, the brief, evidence rules, claims, diffs, live files, and the audited sources named by absolute path and sha; inputs carry a sentinel line that the answer must acknowledge. The mandatory set from `ledger.sh mandatory` is split into batches of at most 60 ids; one launch per batch; only the first batch carries additions `X<n>` with `origin: second-opinion`. The answer is saved verbatim under `second-opinion/`, never retyped. `ledger/6.md` is written with positions, acknowledgments, `## Seen, no position` from `ledger.sh seen`, and checked with `ledger.sh check --through 6`. Check: review; test.
159. **Converge.** The late adversary runs at medium and high, and at low only with live files, over the ids from `ledger.sh late-ids`, writing `late/adversary.md` checked by `ledger.sh late-check`; its own findings `L<n>` never count. `gate.md` comes from `ledger.sh gate`. The merger writes `converged.md` with items `## C<n>` in the shape fixed in `agents/merger.md` (absorbs, sources, gate, disposition, severity, positions, reason, tickets, recommended change), split by group when a group's slice exceeds 450,000 bytes or the ledgers together exceed three times that, the slices being cut before the mode is chosen unless the ledgers together are under the threshold, where no slice can pass it and none is cut, and `ledger.sh check --through 7` verifies it; each merger reads every file it takes whole to its last line, in pages. `C<n>` is the id form that the report, act and the claims verdicts use. Check: review; test.
160. **Report.** Items come from `converged.md` when its check passed, else the ledgers with recomputed gates, else pass one and two with everything provisional. The verdict is `not ready` with a counted blocker or high, `merge after fixes` with a counted medium, else `ready to merge`; a partial run says `audit incomplete`. `report.md` carries `revision: sha256:<hex>` of its body, `work-items.jsonl` is validated by `work-items.sh check` and never applied, and `claims-verdicts.md` is written. The body is built from part files under `report/parts/`: `report.sh parts` writes the copied ones, `08-decisions.md`, `10-claims.md` and `claims-verdicts.body.md` (requirement 322), the orchestrator writes the others with the Write tool, the header and sections 1 to 7, the rest of section 8, 9, 11 and 12, and `report.sh assemble` joins them into the body the revision hashes. The closing lists `act first`, the exact `/audit:act` line, `your decision`, and a `--live` line when eligible. Check: review; test.
161. **Resume.** `/audit:resume <run-id> [--from <stage>] [--live <file>]` reruns from the earliest of: `--from`; the first stage whose entry is missing, not complete, or lists a missing output; stage 5 without `ledger/inventory.txt`; the first stage whose inputs changed (forge data re-hashed, pinned shas re-resolved, upstream outputs re-hashed, `plugin_version` compared, live inputs compared); stage 1 when a direct tree or a working-tree bundle changed. Superseded outputs move to `superseded/<k>/`. When the first rerun stage is 4 or 5 because its entry is missing or `running`, and its recorded inputs have not changed, a `pass1/<scope>.md` or `pass2/<scope>.md` whose last line is `status: complete` and whose `consumed:` hashes equal the current hashes of those files is kept where it is and not superseded; the stage launches only the scopes with no kept file, and its entry lists the kept files among its outputs (decision 146). A changed head or base asks before restarting from stage 1; with `--live` it refuses. A new report gets a new revision, which voids earlier act approvals. Check: review; test.

### Evidence

162. **Eight hard rules.** Read-only boundary; prevention and detection (no Edit or NotebookEdit, a Bash allow-list by instruction, detection by `readonly.sh`); no model, agent or tool names in anything external; no advisor tool; live data only from a user-supplied `--live` file; evidence cited; disk first; claims are not facts. Each agent definition restates rules 2 and 4 in its own words after its opening paragraph (decision 148): no advisor tool and no second-opinion tool, whatever the host offers, and no tool outside its frontmatter list; the Bash commands of rule 2 and nothing else, with `mkdir -p` of its own scratch folder allowed, no interpreter run with an inline program or a heredoc, and no command that waits on input; every redirect inside its scratch folder; and an output file that is final once it writes `status: complete`, so a later wake-up ends with no write. Check: review; lint (agent tools; the restated rules).
163. **When a finding counts.** Only after a fresh adversary other than its author challenged it and the second opinion saw it: at medium and above a stage 6 position is required; at low a complete stage 6 that requested it suffices; `X<n>` counts once the late adversary gave a verdict; `L<n>` never counts except a carried one under the live rule; when stage 6 failed nothing passes on its account. The gate reason strings are fixed. Check: review; test (`ledger.sh gate`).
164. **Four questions.** Best practice, semantic drift, technical debt, decision quality, replaceable through the manifest `questions` key or extended with `extends: default`. Check: review.
165. **Claims.** Kinds verification, decision, scope, status, code; a verification claim is `true, reproduced` only when the audit reproduced it; `false, contradicted` needs counter-evidence; otherwise `not verified, not reproduced`; environment claims always need a live check. The pass-two adversary writes a claims-challenged line for every verification claim marked true. Stage 1 assigns a claim that names no file to its ticket's group when that group exists and holds a file; else across the bundle's groups that hold a file, in claim order, one claim per group in turn, starting again at the first; else to the first group. Once every claim is assigned, a group holding more than 80 claims that name no file keeps the 80 with the lowest numbers, and the rest move in turn across the bundle's other groups that hold a file; the brief's Claims section records each scope's claim count and each move (decision 148). Check: review; test.
166. **Evidence kinds and labels.** Quote `repo@sha:path:line`, search with command and result, run with command, location and output, live result `live/results-<k>.md:<line>`. `verified fact` needs the defect demonstrated; otherwise `unverified assumption` capped at medium; `convention` rests on a ranked source. Digests and maps are pointers, never evidence. Check: review.
167. **Finding schema.** `### <scope>-F<n>: <title>` with severity, question, label, claims, evidence, demonstrated, inferred, what the code does, what breaks and for whom, recommended change, alternatives, live check, work-item impact; ids `-F`, `-P`, `-T`, `X`, `L` by origin, and `C<n>` for a converged item. Check: review; test (ledger parsing).
168. **Counting a contested item.** Equal severities count at that severity; with one `dropped` position the item counts only if the keeping position is `verified fact`; otherwise the higher severity counts when its position is `verified fact`, else the lower; `provisional` and `dismissed` never count. Check: review; test.
169. **Outward trace.** One hop per changed symbol, at most 15 symbols per scope, per symbol 5 siblings, 5 callees, 10 consumers, overflow listed; a sibling is a finding only with a cited shared contract. The second opinion traces at most 10 symbols. Check: review.
170. **Leads, not findings.** A weak-test flag becomes a finding only when the regression the test would miss is named. A run-once script edited in place is `unverified assumption` with a live check; it is judged by repeated work per step, not end state. Decision points of a widened input's consumer are listed, at most eight, uncovered first. A test running as an account with more rights than it uses is flagged; a grant gives `verified fact`, a pointer `unverified assumption` plus a live check. Check: review; test (ground-truth fixture).
171. **Producers at head and base.** The producer of each matched literal is read at head and at base; the lead is the merge-base-to-base commit range, not author dates. Check: review.
172. **Open pull request collisions.** Run-once names are checked against the first 100 open pull requests with `collisions.sh`, which prints `collision`, `cut` and `cut-list` rows; a candidate is a lead. Check: test.
173. **Audit-only rules live apart.** Rules that only the auditor and adversary need are in `audit-evidence.md`, not `common.md`. Check: review.
174. **Brief errata.** Errors in the brief that an adversary notices go to `brief_errata`. Check: review.

### Run directory and read-only boundary

175. **Scratch resolution.** The manifest `scratch` key (inside the primary repository and ignored, or inside the main checkout of a linked worktree with the same `--git-common-dir`); else `scratch/`, `tmp/` or `.scratch/` when present and ignored; else `.reimagine/` when already ignored; else `${CLAUDE_PLUGIN_DATA}/runs/`. The audit never writes to `.git/info/exclude`, and the only writes it makes under a git directory are the ones requirement 162's read-only boundary discloses: the remote-tracking refs of a fetch the user approved, and the loose objects `working-tree.sh build` adds for a `head: working-tree` bundle. Check: review; acceptance.
176. **Run directory.** `<scratch>/audit/<run-id>/`, id `<YYYY-MM-DD-HHMM>-<slug>` with `-2`, `-3` on collision; `<scratch>/audit/` is made with `mkdir -p` and the run directory itself with `mkdir` without `-p`, so an existing id moves to the next suffix; parent and child are compared as whole resolved paths. Check: review.
177. **Registry.** `${CLAUDE_PLUGIN_DATA}/runs.json`, an array of `{run_id, path, primary_repo, created, state}`, written under a lock directory `runs.json.lock/<owner>` acquired with `mkdir`, retried every five seconds, stale after about a minute (asked interactively, removed headless, never one's own), replaced and released in one command. Check: review.
178. **Read-only check after every stage.** `readonly.sh snapshot` before stage 1 and `readonly.sh check` after every stage, walking nested repositories and submodules with `GIT_OPTIONAL_LOCKS=0`. Exit 1 (a `blocked` line) ends the run `blocked`; exit 3 (only `remote-ref`, `local-branch` or `ignored` lines) is judged: an approved fetch, a user-confirmed `background-fetch` or `local-branch`, another audit run's file, or an agent's logged run; a `local-branch` line is a refs line for `refs/heads/<name>` present only now, `<name>` not the checkout's own branch of the baseline's `# branch.head` line, or a `+` config line `branch.<name>.<key>=<value>` for such a name, since refs and config are shared by every worktree of a repository (decision 146); a deleted or moved branch, any other config line, and the index and the tree stay `blocked`; exit 2 ends `blocked`; a quoted path is unsupported. The `touched` walk is advisory; the hash walk is fatal. Ignored-file writes from a logged run are accepted per run, never blanket. Check: test; acceptance.
179. **Moved remote-tracking ref and new local branch.** A moved remote-tracking ref asks whether a background fetch explains it; a yes is recorded as `background-fetch` with old and new commits. A `local-branch` line passes when a `local-branch` approval for the same branch and commit explains it; otherwise it asks whether the user's own work in another worktree explains the branch, naming it and its commit and recommending no answer; a yes is recorded as `local-branch` with target `<repo name>:<branch>`, decision, time and commit; a later line for the same branch at another commit asks again; no, or no answer, ends the run `blocked`. Check: review; test (`readonly.sh` prints the lines).
180. **Per-agent scratch.** Each agent gets `<run dir>/tmp/agents/<stage>-<scope>[-<n>]/`; `sed -i` is barred; agents may use read-only pipe stages with a `runs:` log. An agent may make its own scratch folder with `mkdir -p`, runs no interpreter with an inline program or a heredoc (`python3 - <<EOF`, `node -e`, `perl -e` and the like) and no command that waits on input, while a repository's own test or lint command stays as hard rule 2 allows it. An output file is final once its last line is `status: complete`: the agent writes nothing after it, and a completion notice for an agent whose stage entry is already `complete` or `failed`, or for an agent this session did not launch, such as one an earlier session launched, is noted in the check file of the stage then running, or of the last stage when none runs, and changes nothing (decision 148). Check: review.
181. **Message stability.** Parsed lines (`blocked <kind>`, `readonly:`, `status:`, `ledger:`, `handoff <file>:<line>:`, `working-tree: refused:`) are byte-stable; wording changes go around them. Check: test.
182. **Group names.** Custom group names are slugged; reserved names (`tests`, `hygiene`, `tests-hygiene`, `interactions`, `combined`, `unticketed`) and `-topup` or `-maptopup` collisions stop the run. Check: review; test.
183. **Headless runs.** Never end the turn while a background command runs; `revert-tests.sh bg` plus `wait` in at most eight nine-minute loops; after the eighth exit 3 the run stops with the elapsed time. Check: review.

### Scripts

184. **Eleven scripts with their suites.** `readonly.sh`, `handoff.sh`, `ledger.sh`, `working-tree.sh`, `revert-tests.sh`, `live.sh`, `memory.sh`, `work-items.sh`, `collisions.sh`, `run-copies.sh`, `report.sh`, each POSIX sh plus awk that runs on mawk, gawk and BSD awk (`revert-tests.sh` re-executes under bash), exit codes 0 ok, 1 validation error, 2 usage or IO failure, and 3 where a script documents a pending or judged state (`readonly.sh check`, `revert-tests.sh wait`). Each suite compares byte-exact output; a literal sha or hash that depends on an embedded string is produced by running the fixture builder once and pasting the observed value, in its own commit. Check: test.
185. **Embedded literals.** `reimagine-handoff: 1`; `reimagine-live: 1`; `# audit report: `; agent types `audit:auditor` and `audit:adversary` in ledger output; `working-tree.sh` identity `audit`, `audit@example.invalid`, message `audit: working tree`; directory `second-opinion/`; origin `second-opinion`. Check: test.
186. **Fixtures.** `tests/audit/fixture/build.sh <solo|solo-dirty|full|tokens|patterns|ground-truth>` builds deterministic repositories; `verify.sh` checks literals from `expected.md`; the ground-truth fixture holds twenty planted cases documented in `ground-truth-cases.md`; expectations follow observed truth, and ambiguous fixture ticket text is fixed rather than the rule. Check: test.
187. **Fault injection.** Manifest `_test` with `fail`, `drop_ack`, `hold`, `expire_budget_after_stage`, `plant_map_error`, `ledger_split_bytes` is honored as documented in `fault-injection.md`. Check: review.
283. **Run copies by script.** `run-copies.sh <run dir> <run id> <tier> <questions file>` finds `skills/audit/common.md` and `skills/audit/audit-evidence.md` from its own path, writes `common.md` into the run directory with its header filled (the run id, the run directory as given, the tier, and the `- <id>: <question>` lines of the questions file in place of the header's question line) and `audit-evidence.md` byte for byte, so neither copy passes through the model. Exit 0; 1 on a bad argument (the count, a tier outside `low`, `medium` and `high`, a run directory or questions file that cannot be read, a question line not of the form `- <id>: <question>`); 2 on an IO failure or a template without its header lines. Stage 1 step 10d writes the resolved question list (the four defaults, or the manifest's list with `extends: default` applied) to `<run dir>/questions.md` with the Write tool and runs the script. Check: test (`tests/audit/run-copies.sh`); review.
322. **Report parts by script.** `report.sh` builds the report's copied sections from the run directory's files, so no copy passes through the model and no body passes through a shell argument (decision 147). `report.sh parts <run dir>` writes under `<run dir>/report/parts/`: `08-decisions.md`, section 8's heading with its Decision ledger, from the pass-one `## Decisions` lines and the pass-two `## Decisions challenged` lines, and its Raised tickets, from the `## Scope` and `## Scope challenged` lines, a `decision` or `scope` claim with no entry marked `not assessed` and an entry with no challenge line `not challenged`; `10-claims.md`, section 10, from `claims.md`, the pass-one `## Claims` lines and the `## Claims challenged` lines; and `claims-verdicts.body.md`, the entries of `claims-verdicts.md`. It reads three short lists the orchestrator writes first: `claims-files.txt` (per claims file, the name `claims.md` gives it, its absolute path, `handoff` or `prose`, and the hash the stage 1 entry records), `items.txt` (per report item, `C<n>: ` and the ids it absorbs), and, when needed, `claims-override.txt` (`claim <n>: <verdict>` for a claim whose verdict the files do not give, a live claim or one that cites an item a `REVIEW.md` rule skipped, and `claim <n> correction: <text>` for each `false` claim). `report.sh assemble <run dir>` joins every `report/parts/*.md` but `claims-verdicts.body.md`, in byte order of name, into `<run dir>/report.body.tmp`. `report.sh claims-verdicts <run dir> <hex>` writes `claims-verdicts.md`: the title with the run id, the revision, the `generated:` time, the fixed paragraph and the body part. The shapes are fixed in `report.md` and `stages/8-report.md`. Sections 3 and 9 stay the orchestrator's: no format fixes the pass-two line that marks a Verified OK item challenged, and a Live checks status joins approvals, gate reasons and result copies. It reads only a pass file whose last nonblank line, without trailing blanks, is `status: complete`, as `ledger.sh` reads it, since `common.md` makes any other a failed output, and never a `.pre-topup.md` copy; it reads every input with a CR before the LF removed and a heading with trailing blanks removed; a finished pass-one file without `## Claims`, or a finished pass-two file without `## Claims challenged` other than a map-correction `-topup.md` file, which holds findings only, is a failed output, as stages 4 and 5 count it, and is skipped as if absent; a claim number `claims.md` lists twice and a false claim with no correction are malformed inputs; a blank line in the three lists is skipped. A `contested` claim's verdicts line names, as `finding:`, the items its pass-one evidence names. ## The `gate` plugin

### Purpose and name

287. **Purpose.** `gate` takes one pull request, several, or a loop manifest, runs `code-review` passes over the whole change from the merge-base, fixes what each pass found, decides from the record of that pass whether to run another and at what level, and stops at a verdict. It runs after the loop and before the audit: the loop ships a reviewed pull request, the gate converges the reviewer, the audit challenges the result. The audit is untouched except that its manifest tolerates the `gate` key (requirement 145). Check: review.
288. **Skill name.** The plugin is `gate` and its one skill is `gate`, so it answers as `/gate` and `/gate:gate`; no bundled skill owns the name on 2.1.310 (decision 120). The skill is user-invocable, has no `paths`, and its description names "reimagine gate" as the primary phrase and "gate this branch", "gate PR <n>" and "gate the manifest <path>" as secondary ones. There is no separate command and no hook. Check: lint (frontmatter; no `hooks.json`); acceptance.

### Invocation

289. **Prose invocation.** No flags; a token starting with `--` is read as prose. The recognized phrases are "PR <n>", "<n> and <m>" and a pull request URL for targets, "the manifest <path>", "this branch", "repo <path>" (requirement 323), "no fixes" (requirement 304), "budget <n> minutes" (requirement 303), "base <branch>" (requirement 292) and "checks <command>[; <command>]" (requirement 300), which runs to the next comma that another recognized phrase follows, else to the end of the request, since a command may hold a comma, and is split at `;` with each command trimmed. Nothing else is read from the request; with no target the current branch is gated against its base. Check: review; acceptance.
290. **Targets.** A pull request number or URL must be open, in the session's repository and not cross-repository; its head branch is fetched with the explicit refspec and checked out, which needs the clean tree of requirement 295. A branch target runs in the session's repository, or in the one "repo <path>" names (requirement 323). Several pull requests run one after another in the order given, each with its own record. A manifest, the loop's `audit-manifest.json` or one of the same shape, runs one record per `bundles[]` entry that has a `pr` or a `branch`, in bundle order, every git and gh command running against that bundle's `repo` as the loop runs across repositories (requirement 129). A branch target or a manifest bundle on a host other than GitHub runs with the comment skipped and the report saying so; a pull request number there cannot resolve and is the unresolved target of requirement 291. Check: review; acceptance.
291. **Reading block first.** After only the read-only calls that resolve the targets and the engine (`git remote`, `gh pr view`, a manifest read, `command -v claude`, and for "repo <path>" the `git -C <path> rev-parse` calls of requirement 323, which may prompt, since the skill pre-approves only the plain forms) and before any other tool call, the skill prints one block with five headings: Targets (each pull request or branch, how it resolved, its base, and for a branch in a repository "repo <path>" names, its resolved toplevel), Mode (`fix` or `no fixes`), Budget (the minutes and their source, then `max-passes` and `split`, then the subagent, review and check budgets in force of requirement 313, each with its source when it is not the default), Engine (`subprocess`, or the stand-in with its reason; a child session that later reports the skill missing moves the run to the stand-in, which the report names, requirement 307), Scripts (the absolute path of the plugin's scripts directory, resolved with no tool call from the skill's base directory the Skill tool prints: two levels above it, then `scripts`; requirement 318). A target that cannot be resolved gets one line and the run continues with the others; with none left the run ends `stopped`. Check: acceptance.
292. **Base branch and merge-base.** For a pull request target the base is its `baseRefName`; for a branch target it is "base <branch>" in the request, else the manifest bundle's `base`, else `.reimagine.json` `base`, else the remote's default branch, so a release or hotfix branch gated through a manifest is diffed against the base its bundle names. A bundle `base` whose first segment names a remote that `git remote` lists in the bundle's repository is read without that segment and its `/`, since the loop's manifest writes `<remote>/<base branch>` and the gate's own a bare branch. The base is fetched with the explicit refspec `+refs/heads/<b>:refs/remotes/<r>/<b>`; a fetch that fails ends `blocked` naming the branch. The merge-base with the base is recorded, every review target and every line count uses the three-dot range from it, and "base <branch>" on a pull request target whose base differs ends `blocked`, since the gate never retargets a pull request. Check: review; acceptance.
323. **Repository of a branch target by request.** Added 2026-10-29 (decision 153). "repo <path>" names the repository of a branch target in place of the session's, since the host returns the shell to the session's start folder after a call that ends outside it, so a `cd` in one call does not carry to the next. The path must be the top of a git working tree, a linked worktree included: `git -C <path> rev-parse --is-inside-work-tree --show-prefix` exits 0 and prints `true` and then an empty line, else the target is unresolved (requirement 291), since a `.git` folder prints `false` with an empty prefix; the check compares no strings, so a path typed in another case or as `/c/...` resolves, and a leading `~` is written as `$HOME`, since git does not expand a quoted `~`, and `git -C <path> rev-parse --show-toplevel` gives the toplevel the Targets line names. The head branch is the one checked out there. Every git command of the run on it runs as `git -C <path>` and every other command, `gh`, the child session and the run's checks included, as `cd <path> && <command>` in one Bash call with absolute paths, as a manifest bundle's commands run (requirement 290), each path in double quotes since a folder name may hold a space, and the repository's instruction files and `.reimagine.json` are read in `<path>`, not in the session's folder; the permission statement counts these forms as prompts, since the skill pre-approves only the plain forms. The record lives in that repository (requirement 309), and the Targets line names the resolved toplevel. Beside a pull request or a manifest target the phrase is one unresolved line and the run continues with those targets, since they name their own repository. Check: review; test (the phrase in the grammar lists of `SKILL.md` and the README); acceptance (item 65).

### Approval scope

293. **What invoking approves.** Invoking the gate by name approves, for that run only: fix commits on each target's branch, whether or not the loop opened its pull request (decision 127); pushing that branch; and one comment per run on each target pull request. Nothing else: no branch, no pull request, no body edit, no ticket comment, no issue. Check: review.
294. **Instruction files win; always ask; denial.** Before changing anything the gate reads the user's instruction files in `$CLAUDE_CONFIG_DIR` when it is set, else in `~/.claude`, never both, since the session loads only that directory's user instruction files, and the permission statement names the directory it read; then the repository's instruction files, `CLAUDE.md` and `.claude/CLAUDE.md` in each folder above the repository's root, which the session loads as project instructions, `~/.claude/CLAUDE.md` among them for a repository under the home folder, and `.reimagine.json`, records every ask-first rule and prompts for any approved action those rules cover. Force push, `--no-verify`, merge, rebase, amend, reset, editing repository settings and opening an issue always prompt. A denial, by the user or the permission mode, is final: never retried, never routed around; a denied commit or push ends the run `blocked` with the pass recorded `failed` and the tree left as it is, and a denied check is recorded as denied, never run another way. Check: review.
295. **Blocked at preflight and before a push.** A dirty tree (`git status --porcelain` not empty, or `git diff --cached --quiet` failing) ends `blocked`; the gate never stashes, resets or cleans. A merged or closed pull request ends `blocked`. On GitHub a `gh` that is not authenticated ends `blocked`. Before every push the remote head is read with `git ls-remote` and compared with what preflight fetched, or with the last sha this run pushed; a head that is neither ends `blocked` with the local commit kept and named. A record whose branch differs from the run's is a slug collision and ends `blocked`. Check: review; acceptance.

### Passes

296. **A pass.** A pass is one review of the whole change from the merge-base at one typed level, then the triage (requirement 299), the fix round (requirement 300) and the next-level decision (requirement 301). The review target is the range `<merge-base>...HEAD`, the merge-base as a full sha as the loop types it (requirement 63), so the child session reviews the record's range and not one it resolves itself; the spikes typed a branch name (decision 121) and acceptance item 47 records the sha form. Never `--comment` or `--fix`; the skill's own finding cap stands (decision 125). Nothing is edited while a review runs. Check: review.
297. **Size and split.** Changed lines are added plus deleted from `git diff --numstat <merge-base>...HEAD`, summed. At or under `split` (default 1500) the pass has one review. Over it, the changed files are grouped by path at the shallowest depth that gives more than one group (decision 145): the depth `d` starts at 1; a file's key is its first `d` segments when it has more than `d` segments, else the key `.`; while every file has the same key and some file has more than `d` segments, `d` grows by one. The pass runs one review per key at the same level, in parallel, a directory key with the target `<merge-base>...HEAD <key path>` and the `.` key naming its files one by one, since `git diff -- .` would select the whole diff; the pass's findings are the union, deduplicated by identity (requirement 302). A key's slug is its path lowercased with each run of characters outside `[a-z0-9]` replaced by `-` and leading and trailing `-` removed; the `.` key's slug is `root` at depth 1 and `<prefix slug>-root` deeper, `<prefix>` being the segments every file shares. Two keys can give one slug, as `src/root` and the `.` key under `src` both give `src-root`, so the slugs are given in byte order of key path with the `.` key last, and a slug an earlier key already holds takes `-2`, else `-3`, and so on, the first one free, since two reviews of one pass must never write the same file. After grouping, a group still over `split` whose key is a directory is grouped again by the same rule over its own files, its depth starting one segment deeper and growing while all of them share one key, and so on until no group is over `split` or the group over it cannot split, being the `.` key or one file (decision 150). A regrouping that gives a single group, as when every file of the group sits directly in its directory, leaves the group as it was, under its directory key, target and slug. The slugs are made from the final keys as above: a `.` key made by grouping a directory key `<k>` again has the prefix `<k>`, and when several `.` keys remain they come after every directory key, in byte order of their prefixes. A binary file, which `--numstat` reports with `-`, counts as no lines and sits in its group by path. Check: review; test (`findings.mjs` merges the group outputs of one pass); acceptance.
298. **Levels.** Pass 1 runs at `xhigh`. Every level a run types lies between a floor of `medium` and a ceiling of `xhigh`: `xhigh`, `high` or `medium`, never `low`, `max` or `ultra` (decisions 122 and 134), and `next.mjs` returns no other word. Check: test; review.
299. **Triage.** Before any fix the orchestrator sorts every finding of the pass into one bucket with a one-line reason: fix (a correctness finding inside the change, or a regression under requirement 302), defer (reuse, simplification, efficiency, or a pre-existing issue the change did not introduce) or reject (a false positive). Deferred and rejected findings go to the report and the comment, never to code. The buckets and reasons are written to `passes.json` before the fix round starts. Finding issues is a judgment, not a count. Check: review; acceptance.
300. **Fix round.** Implementers are Agent subagents at `sonnet` (`models.implementer`), one per group of files no other implementer touches, parallel when disjoint and serial otherwise, each given its findings with their file paths and reasons, the repository's line-ending convention and the instruction to change nothing else. Before each call the gate records `git status`, a patch and file hashes as `pre-<n>.*`, and when it returns, its status and file hashes as `post-<n>.*`; after a call that fails or passes the subagent budget it restores only the paths that were clean before it and ends the run `blocked`. An implementer call is judged against the subagent budget by its completion notification's `duration_ms`, as the loop judges one (requirement 67, decision 149): `date` before and after a parallel batch is the Log's, a notification that arrives for an implementer call after that call returned is not a new call and is judged against `post-<n>` as the loop judges one, any other late one changing nothing, and the brief tells the implementer to start no background command. After the fixes the run's checks run one command at a time under the check budget. The checks come from the first source that gives any (decision 144): the request's "checks" phrase, else the manifest bundle's `checks`, an array of command strings, else `.reimagine.json` `checks`; the same list feeds the child session's allowed tools (requirement 305), the permission statement and the report's Checks section, which names the source. A failing check is fixed through the owning implementer in the same round, at most three times, then the run ends `blocked` naming the check; with no source the report says no check ran. A pass that changed anything ends with one commit in the repository's convention, staged by name, naming no model, agent or tool, and the push of requirement 295; a pass that changed nothing commits nothing. Check: review; acceptance.
301. **Next level.** After the fix round, `next.mjs` reads `passes.json` and returns the next level or a stop with the rule that produced it, in this order (decision 130): (1) the latest pass's fix bucket is empty and its reject bucket holds nothing new, carried rejections of requirement 302 counting as nothing: stop with verdict `pass`, or `pass-with-deferred` when any pass deferred something; (2) the latest pass ran at `medium`: stop, with `pass` or `pass-with-deferred` when its fix bucket was empty and `unconverged` otherwise, since no pass verifies its fixes; (3) the fix round changed an exported signature, a schema or migration, a file outside the original diff, or more than a quarter of the diff's files: `xhigh`, at most once per run after pass 1; (4) the two latest passes both ran at `high`, each with an empty fix bucket and a reject bucket holding something new: `medium`; (5) otherwise `high`. When the run's passes have reached `max-passes` the script still returns the rule's level and adds `capped` naming the cap, and the orchestrator ends the run `unconverged` (requirement 303); a later run resumes from that level (requirement 312). The orchestrator records the fix round's change kinds in the pass entry, and the script computes from the record alone, never from a schedule. Check: test (one case per rule, each with its literal level or verdict, and the capped case); acceptance.
302. **Identity across passes.** A finding's identity is its repository-relative file path plus its normalized summary: lowercased, backticks and quotes removed, every run of characters outside `[a-z0-9]` replaced by one space, trimmed, cut at 120 characters; the line number is not part of it, since a fix moves lines. `findings.json` keeps one entry per identity with the pass it first appeared in, its bucket per pass and its state: `open`, `new`, `fixed` (in the fix bucket of a pass whose commit exists), `deferred`, `rejected`, `carried` or `regressed`. A finding fixed in an earlier pass that returns is a regression and goes to the fix bucket of the pass that saw it return; a finding rejected in an earlier pass that returns is carried as rejected with its reason and counts as nothing in requirement 301; a finding deferred in an earlier pass that returns keeps its state `deferred` and arrives in the defer bucket with the reason of its last defer pass, so the triage keeps it without a new judgment (decision 143). A returning finding the script cannot match is marked `new` and printed with its candidates (requirement 306), and the orchestrator, who sees that one defect is worded differently by each review (decision 126), may match it to one of its candidates by reading both, writing the match and its reason on the new entry in the same ledger write as its bucket and state, and recording the finding in the pass entry under the earlier id (decision 154); a match takes the bucket and state the script gives a returning entry of the candidate's state: `fix` and `regressed` for a fixed one, `reject` and `carried` for a rejected or carried one, `defer` and `deferred` for a deferred one, and for a regressed one no bucket, the state staying `regressed`, so the triage sorts it as it sorts that entry returning in the same words. Check: test (`findings.mjs`: a regression, a carried reject, a carried deferral, a new finding with its candidates, the normalization); acceptance.
303. **Caps.** `max-passes` (default 4) bounds the passes of one run. The run budget is 120 minutes by default, "budget <n> minutes" in the request winning, then `.reimagine.json` `gate.budget`, then a session instruction; question waits are excluded. Each review has the review budget, the reviews of a split pass running together within it, each implementer call the subagent budget and each check the check budget, 30, 20 and 15 minutes by default, the loop's figures (requirement 67), each read from the configuration as requirement 313 says (decision 151); a check runs with its budget as the shell's timeout, since the default is 2 minutes. Reaching `max-passes` with a level still to run, the run budget or the review budget ends the run `unconverged` with every open finding listed, an open finding being one in a fix bucket that no later pass verified, or a regression; an implementer call or a check past its budget is a failed call under requirement 300 and ends `blocked`; a check whose budget is over the 10-minute foreground limit of the host's shell runs in the background beside a background `sleep` of its budget, since a background command notifies only when it ends, and whichever ends first stops the other; the reviews, which run in the background, wait beside such a `sleep` of the review budget the same way. The output of the pass is kept and a pushed commit stays. Never a silent pass. Check: review; test (`next.mjs` marks the level `capped` at `max-passes`); acceptance.
304. **No fixes.** With "no fixes" in the request the run makes pass 1 only: the review and the triage run, nothing is edited, committed or pushed, and the comment and the report name what a fix run would do, the fix bucket with its reasons beside the deferred and the rejected. The verdict is `pass` or `pass-with-deferred` when the fix bucket is empty, else `unconverged` (decision 131). Check: review; acceptance.

### Engine

305. **Child session engine.** Each review is a child session: `claude -p "/code-review <level> <merge-base>...HEAD[ <path>]" --output-format json`, run from the target repository's root with the environment variable `CLAUDECODE` unset, standard input from `/dev/null`, under `--permission-mode default`, with `--allowedTools` naming Read, Grep, Glob, Skill, Agent, TaskStop, the read-only git forms `Bash(git diff *)`, `Bash(git log *)`, `Bash(git show *)`, `Bash(git status *)` and `Bash(git ls-files *)`, and each command of the run's checks (requirement 300) as `Bash(<command>*)`; nothing else, so a call outside the list is denied without a prompt and appears in `permission_denials`, which the record keeps and the report counts. The command runs with `run_in_background` and the gate waits for its completion notice, since the review budget exceeds the Bash foreground cap; the reviews of a split pass run as parallel background commands; a review past the budget is stopped with TaskStop, recorded `failed`, and ends the run `unconverged`. The output is saved as `review-<n>[-<slug>].json` before it is parsed. On 2.1.310 the typed level reaches the review, `--max-findings` is honored, the result carries repository-relative paths in a fenced JSON array, and the remembered level is untouched (decisions 118 and 119). Check: review; acceptance.
306. **Review output.** `findings.mjs` reads a saved review output: `is_error`, `permission_denials`, `duration_ms`, `total_cost_usd`, and the `result` text, from which it takes the first fenced ```json array of objects with `file`, `line`, `summary` and `failure_scenario`, keeps the text before and after it as notes, and writes the pass's findings in the ledger shape with their identities, deduplicating across the group outputs of one pass. Every `new` finding of the printed summary carries `candidates`: the ledger's entries on the same file whose state is `fixed`, `rejected`, `carried`, `deferred` or `regressed` and that no review of this pass reported, since a match to an entry the pass already holds would record two findings under one id, each `{"id", "state", "line", "distance"}`, `line` being the line of the entry's latest pass and `distance` the absolute difference from the new finding's line (`null` when either line is not a whole number), sorted by distance, `null` last, then by id, and `[]` when there is none (decision 143). A result with no such array, or `is_error` true, is a failed review: the script exits 1 naming the file, the pass is recorded `failed` with the result text, and the run ends `unconverged`; the gate never writes a finding list of its own. Before it reads pass `n` into the ledger, and after a repeated pass's own entries are rolled back, the script looks for a match written without its link: an entry whose `first_pass` is the highest pass the ledger then holds, whose state is `carried` or `regressed` and which has no `match`, since only a match gives a finding new in that pass either state. For each, in id order, it prints `findings: warning: <id> is <state> with no match; write the match of Step 1.6` on stderr and goes on, the exit staying 0; a `deferred` entry is not checked, since a new finding the triage defers holds that state with no match (decision 154). `findings.mjs --check <pass> <ledger>` prints the same warnings for the ledger as it stands, for the entries new in `<pass>`, and writes nothing, since after a pass with no findings the highest pass the ledger holds is an earlier one, exit 0, 1 for a bad ledger and 2 for usage or IO; Step 1.6 runs it after each triage write, so a match written without its link is repaired in the pass that made it, the last pass included, and the repair writes `match` in `findings.json` and keys the finding under the earlier id in that pass's `findings` of `passes.json`, the earlier id being the one that pass's `findings` already keys it under, else the one its reason names; with neither, the entry stays as it is and the Log names it. Exit codes: 0; 1 for a bad or empty review; 2 for usage or IO. Check: test (fixtures: an entry new in the last pass and `carried` with no match, printed with the warning, and by `--check` on the ledger alone; a bare array; prose, array and notes; two group outputs sharing one finding; no array; `is_error`; a text file from the stand-in; a reworded finding beside a rejected entry, printed with its candidate).
307. **Stand-in engine.** When `claude` is not on the PATH, or a child session's result says the `code-review` skill is not available, the gate reviews through an Agent subagent at `opus` (`models.fallback-reviewer`) over `diff-<n>[-<slug>].patch`, written from `git diff <merge-base>...HEAD`, with `-- <path>` for a split group, with the level word passed as `effort` and the request asking for the same fenced JSON array; the reply is saved as `review-<n>[-<slug>].md` and parsed by `findings.mjs` as text. Once chosen the stand-in stays for the run, and the reading block and the report name it with the reason. Check: review; test (`findings.mjs` text input); acceptance.
308. **The remembered level is untouched.** The gate never invokes `code-review` through the Skill tool, and a level typed in a child session does not write `codeReviewLastEffort` to the host's configuration (verified, decision 119), so a run leaves the user's interactive level as it was, and the report says so in one line. Check: review; acceptance.

### Record

309. **Record location.** `.reimagine/gate/<branch-slug>/` in the target repository, the slug as requirement 82; `.reimagine/` is added to the exclude file that `git rev-parse --git-path info/exclude` names, run in the target's repository and read relative to that repository's folder when it is not absolute, since `git -C <path>` prints a path relative to `<path>` that a write from the session's folder would miss, and `--path-format=absolute` needs git 2.31, never to `.gitignore`; nothing under it is ever staged; `passes.json` keeps the exact branch name and a differing branch is the collision of requirement 295. Check: review; acceptance.
