# Requirements: 0.1.0

Drafted 2026-10-14 from the product specification. Architecture is in architecture.md, the order of work in build-plan.md, the hand-run checks in acceptance.md, and the choices with their evidence in decisions.md. Where this document and the architecture disagree, this document wins until it is amended. Nothing here is implemented.

Each requirement ends with how it is checked:

- **test**: an automated test under `tests/`, run by `npm test` and CI.
- **lint**: a rule in `tools/lint.mjs`, run by `npm run lint` and CI.
- **acceptance**: a hand-run item in acceptance.md, recorded with date, machine and CLI versions.
- **review**: checked by reading, once, in the pull request that merges it.

A requirement that rests on a spike names the spike in decisions.md. If a later run of that spike fails, the requirement is amended before the milestone that depends on it merges.

Numbers are never reused. A retired requirement keeps its number with the word "Retired" and the reason.

## Suite

1. **One repository, one marketplace.** The marketplace is named `reimagine-engine` and lists exactly four plugins: `rules`, `loop`, `audit` and `primer`, each at `plugins/<name>/`. Before a release a prerelease catalog may list a plugin that is built at a prerelease version (requirement 14), so a work machine can install it from `main` before its release, and may list `repo-docs` until requirement 268 retires it. Check: lint.
2. **Plugin directories hold only what a user installs.** Under `plugins/<name>/` there are the manifest, the skills, commands, agents, hooks, scripts, output styles and reference files the plugin uses at run time, plus `README.md` and `LICENSE`. No tests, no design documents, no fixtures. Check: lint.
3. **ASCII.** Every shipped file under `plugins/` is ASCII. Check: lint.
4. **License per plugin.** The root `LICENSE` and each `plugins/<name>/LICENSE` is the Apache License 2.0 text with the holder line `Copyright 2026 vibecodedapps.net`. Check: lint.
5. **Prerequisites.** Node 22 or later and, on Windows, Git for Windows. The audit plugin's live checks, work-item validation and collision check also need `jq`; the README says so and says what runs without it. No other tool is required. Check: review.
6. **Prompt first.** The only executable files under `plugins/` are `plugins/rules/scripts/rules.mjs`, the ten audit scripts (`readonly.sh`, `handoff.sh`, `ledger.sh`, `working-tree.sh`, `revert-tests.sh`, `live.sh`, `memory.sh`, `work-items.sh`, `collisions.sh`, `run-copies.sh`) and the two primer hooks `plugins/primer/hooks/drift.sh` and `plugins/primer/hooks/notice.sh`. Every one of them has a test under `tests/`. A new script ships only with its test. A workflow script under `plugins/audit/workflows/` is an executable whose check is `node --check`, the lint rule of requirement 219 and acceptance item 43, because its runtime needs a session (decision 95); none ships until requirement 270's gate is met. Check: lint.
7. **No plugin options.** No manifest declares `userConfig`, and no file references `${user_config.*}`. Check: lint.
8. **Three hooks outside a request.** Only three hooks run without a session request: the rules SessionStart staleness notice, the primer SessionStart memory notice and the primer drift check. No other plugin ships a `hooks/hooks.json`. Check: lint.
9. **Independent plugins.** `loop` and `audit` do not require `rules`; no manifest declares `dependencies`. Each plugin works alone after `/plugin install <name>@reimagine-engine`. Check: lint; acceptance.
10. **Reusable files carry nothing owner-specific.** No shipped file names a person, a person's email address (an address at a `.invalid` domain is allowed), an absolute path under a user's home, or a specific repository other than this one. Check: lint.
11. **Nothing external names a model, agent or tool.** Pull request bodies, pull request comments, ticket comments and commit messages name the activity and the date, never the model, the agent type or the tool that produced the text. Run records and reports kept in a run directory may name them. The loop never types an attribution trailer; the host's attribution setting decides that alone. Check: review; acceptance.
12. **Commit form.** Commits in this repository and commits the loop makes read `type(scope): subject` in lowercase, with a body that says why. A bare `@token` in a subject or pull request text is written in backticks. Check: review.
13. **Moves and renames apart.** A commit that moves or renames files changes no file content; string renames go in their own commit. Check: review.
14. **Versions and tags.** Each plugin has its own version line in its manifest and its catalog entry, which agree. The first release is 0.1.0; before it a built plugin may ship as `0.1.0-alpha.<n>`, a semver prerelease that sorts below 0.1.0, and the 0.1.0 target of every plugin stands. A release is tagged `<plugin>--v<version>` with `claude plugin tag`. A plugin directory that changed since its last tag carries a version above that tag. There is no shared suite version. Check: lint.
15. **One changelog.** `CHANGELOG.md` has a heading `## <plugin> <version> - <YYYY-MM-DD>` for every tagged version of every plugin, prerelease versions included, newest first; a version not yet tagged needs none, so a bump passes lint before its heading is written. Check: lint.
16. **The repository keeps its own instruction file by its own rules.** The root `CLAUDE.md` is a primer hub (requirement 238), and the primer drift hook runs in sessions on this repository through the tracked `.claude/settings.json`. Check: acceptance.
17. **Windows and POSIX.** Every test and script runs on ubuntu, macOS and Windows with Git for Windows, and the awk-using audit scripts also run on mawk. Check: test (CI matrix).

### Mechanism

22. **One target.** The target file is `$CLAUDE_CONFIG_DIR/CLAUDE.md`, else `~/.claude/CLAUDE.md`. It is created when missing. There is no other target. Check: test.
23. **Bytes outside the block are kept.** Every byte before the begin marker and after the end marker is preserved, including a byte order mark, bytes that are not UTF-8, the file's line ending, and a missing final newline. Check: test.
24. **Symlinks.** A target that is a symlink is written through, at the file it points to. A dangling or hard-linked target is refused without writing. Check: test.
25. **Block format.** The block starts with `<!-- reimagine:house-rules begin version=<v> options=<list> join=<none|blank|newline> digest=<16 hex> -->` and ends with `<!-- reimagine:house-rules end -->`. The digest is of the body in LF form; a CRLF file gets a CRLF block. Check: test.
26. **States.** A target is `absent`, `current`, `stale`, `edited`, `malformed` or `declined`. A version change alone with the same rules is `current`. A malformed block is reported with its line numbers and nothing is written. Check: test.
27. **Plan then apply.** `plan` writes a plan file in the plugin data directory and shows the diff, one hunk per changed run, with three lines of context. `apply` refuses when the target changed after the plan, including a file created where none was. Check: test.
28. **Ask per change.** The skill shows the diff and asks before `apply`, once per target change. Check: review; acceptance.
29. **Backup.** An existing target is copied to `<path>.reimagine-backup-<YYYYMMDDHHMMSS>` before any write; an existing backup is never overwritten and the write does not happen. A created file has no backup and `remove` deletes it unless the user added text, in which case only the block is removed. Check: test.
30. **Atomic writes.** The target is written to `<path>.reimagine-tmp-<pid>` and renamed into place, keeping permissions. Two applies started at once both land in the state and plan files; a lock directory `rules.lock` serializes them and a lock left by a dead run is taken over. Check: test.
31. **Remove.** `remove` takes out the block and the bytes of its join, so install then remove gives back the original bytes for LF, CRLF, BOM and no-final-newline files. Check: test.
32. **Decline.** `decline` records the digest; the next plan says so and the staleness notice stays quiet until the shipped text changes. Check: test.
33. **Adopt.** `plan --adopt` finds rules already present outside the block, as a Markdown reader sees them (items, paragraphs, headings; not fences, HTML comments or indented code), removes a full copy including its headings, and puts the block where the copy was. Text that differs, fenced examples, and user text under a heading are kept. A file holding Markdown that adopt does not handle is left alone and the plan recommends decline. Check: test.
34. **Recommendation.** The plan counts the rules already outside the block and recommends `apply`, `adopt` or `decline`; decline only when every rule is already present. Check: test.
35. **Imports.** `@path` imports in the target are followed read-only: at a line start or after white space, not in code, fences, quotes or the block; relative to the importing file, from `~/`, or absolute; four hops; fifty files; 256 KiB per file; a directory, an oversized file or a missing nested file is a read error, not a skip. The plan names what each import holds. Check: test.
36. **Options.** `core` is always applied; `windows` is added on Windows and refused elsewhere. Recorded options are kept on a rerun unless `--options` overrides them. Check: test.
37. **Script output.** A refusal is one line on stdout starting `rules: ` with exit 1; `status` exits 0. Check: test.
38. **Script size.** `rules.mjs` is at most 700 lines and imports only `node:` built-ins. Check: lint.
39. **The skill never edits the file itself.** `/rules` runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs <verb> ${CLAUDE_PLUGIN_DATA}` and relays its output; it never writes `CLAUDE.md` with the Edit or Write tool. The skill sets `disable-model-invocation: true`. Check: lint; review.
40. **The skill names the output style.** `/rules` ends by printing how to select the output style: `/output-style rules:Concise Plain`, or the equivalent `/config` path. Check: review; acceptance.
41. **Staleness notice.** The SessionStart hook, matcher `startup` only, runs `node ${CLAUDE_PLUGIN_ROOT}/scripts/rules.mjs session-start ${CLAUDE_PLUGIN_DATA}` and prints one `systemMessage` line, `rules: the house rules in <path> are older than this plugin's; run /rules to update them`, when the block is `stale` and not declined. It prints nothing otherwise, writes nothing, and exits 0 even when the state file cannot be read. Check: test; acceptance (the message is visible at startup).
42. **Line-ending changes do not hide staleness.** A block whose file changed line ending still reads as current or stale by its rules, and a hand edit still reads as edited. Check: test.

## The `loop` plugin

### Invocation

45. **Prose invocation.** The skill is `run` in the `loop` plugin, so it answers as `/loop:run`; it is user-invocable and its description names "reimagine loop" as the primary phrase and "run the loop" as a secondary one. There is no separate command. The bare `/loop` belongs to the host's bundled interval skill and is not ours. There are no flags; a token starting with `--` is read as prose. Check: lint (frontmatter); acceptance (each phrase invokes this skill, not the bundled one).
46. **Reading block first.** After only the read-only calls that resolve ids (`git remote`, `gh`, `az`, an MCP read, a file read) and before any other tool call, the skill states how it read the request in one block with four headings: Tickets, Mode, Scope, Effort. Each ticket line says how the id resolved (`gh`, `az boards`, `mcp:<tool>`, `file`, `text`). An id that cannot be resolved gets one line and the run continues with the other inputs. Check: acceptance.
47. **Ticket forms.** Accepted forms: `#123` and an issue or pull request URL (GitHub, resolved with `gh`); `AB#12345` or a bare number on a repository whose remote is Azure DevOps (resolved with the Azure DevOps MCP tool if one is listed, else `az boards work-item show`); a Salesforce case number or record id (resolved with a Salesforce MCP tool if listed); a readable file path; pasted text. Ticket text obtained by any means passes through the credential scan before it is written. Check: review; acceptance.
48. **A pull request reference continues its branch.** A pull request URL or number on GitHub that is open, not cross-repository and in the primary repository sets the branch to continue. Its tickets come from the branch record, else from the pull request's closing references, else the run ends `blocked` asking for a ticket, file or description. A pull request on another host is one line and the run continues without it. Check: acceptance.
49. **Modes.** Mode is one of: build and publish (default); plan only ("plan only" in the request); build without publishing ("do not publish", ending `prepared`); continue (a pull request reference, "continue <branch>", an existing record whose `tickets` list holds one of the request's tickets, or an existing record for the predicted branch). "confirm the plan" adds one pause for a clear yes after the plan review. "budget <n> minutes" sets the run budget. "on branch <name>" names the branch. Check: review; acceptance.
50. **Scope.** The primary repository is the session's, or the checkout that "primary <path>" names (requirement 281). "also edit <path>" adds a writable checkout. A path in ticket text that maps to another checkout is adopted only after the user answers a question with a clear yes or a comma-separated subset; any other answer ends `stopped` with the "also edit <path>" form to rerun without the question. Multi-repository scope is never adopted from prose alone. Check: review; acceptance.
281. **Primary checkout by request.** "primary <path>" sets the primary checkout `<checkout>` for the run. The path must be a git toplevel or a linked worktree: `git -C <path> rev-parse --show-toplevel` prints that path, else preflight ends `blocked` naming it. Every primary git command runs as `git -C <checkout>` and every other command that acts on its tree runs in one Bash call as `cd <checkout> && <command>`, the forms of the worktree run; the permission statement counts them as prompts, since the skill pre-approves only the plain forms. The reading block's Scope line names the checkout in use. When the named checkout is a linked worktree, the record of requirement 82 lives in its main checkout, the first `worktree` line of `git -C <checkout> worktree list --porcelain`, and the detached-worktree run of requirement 80 does not apply: a differing flagged path there ends `blocked`, naming the path and the main checkout, which "primary <main checkout>" runs with the exception. The word is "primary", not "in", because the remaining request text is joined into the ad-hoc description and "in" occurs in prose; it mirrors the Scope line. Check: review; test (the phrase in SKILL.md and Step 0); acceptance (item 45).
282. **Base branch by request or configuration.** "base <branch>" in the request, else `.reimagine.json` `base`, names the base branch `<b>` of requirement 76 in place of the remote's default branch. Step 0.2 fetches it with the same explicit refspec, a fetch that fails ends `blocked` naming the branch, and `run.md` and the reading block's Mode line record it (`; base <branch>`). It is the review base (requirement 88), the pull request base (requirement 116) and the branch whose workflow files the deploy judgment reads (requirement 56). An open pull request on a continued branch whose base differs from it ends `blocked`, since the loop never retargets a pull request. An additional repository keeps its remote's default branch. Check: review; test (the phrase in SKILL.md and Step 0; the key in the configuration block); acceptance (item 45).
51. **Effort is a hint.** Words such as "quick", "thorough", "low", "high" set the effort passed to subagents. A floored run (requirement 69) passes effort at least `high` to its reviewers, and no hint lowers that. Check: review.
52. **Echo redaction.** The echoed request text is credential-scanned and redacted before it is printed and capped at 300 characters; the reading block that follows has no cap. Branch slugs come from the redacted text. Check: review.
53. **Credential scan.** Before anything is written to the record, every input is scanned for keys named password, passwd, secret, token, api_key, apikey, client_secret, private_key or connection_string, for blocks under headings containing cred, secret or password, for `AKIA` followed by sixteen uppercase alphanumerics, and for a PEM header. A match asks `keep` or `drop`; `drop` writes `<redacted: key>` in place; any other answer ends `stopped`. Check: review; acceptance.

### Approval scope

54. **What invoking approves.** Invoking the loop by name approves, for that run only: creating a branch, committing, pushing that branch, opening one pull request per repository, editing the body of a pull request this loop opened, commenting once per run on that pull request, and commenting on the source tickets. Check: review.
55. **Instruction files win.** Before changing anything the loop reads the user's instruction files in `$CLAUDE_CONFIG_DIR` (else `~/.claude`), the repository's instruction files and `.reimagine.json`, records every ask-first rule, and prompts for any approved action those rules cover. The loop never removes an ask-first rule. In multi-repository runs the rules of every repository are unioned. Check: review; acceptance.
56. **Always ask.** Force push, `--no-verify`, merging, anything that deploys (including a push or pull request that triggers a deploy, judged from the workflow files on the base branch of requirement 76 and on the branch being pushed), editing repository settings, and opening a new issue always prompt. An answer that is not a clear yes is a denial. Check: review.
57. **Denial.** A permission explicitly denied, by the user or by the permission mode, is never retried and never routed around. A denial in steps 0 to 6 or after the first push marks dependent steps not done, runs the independent ones, and ends `blocked`; a step 7 denial before any push ends `prepared`. A denial is a refused tool call or a non-yes to a permission question; the decision questions of requirements 50, 53 and 49 are not permissions; a missing resource is "not run", never a denial. Check: review.
58. **A dropped call is not a denial.** A dropped read is retried once serially; a dropped write only if a check shows it did not take effect; after any drop, preflight commands run serially. A subagent's report is model output, never approval. Check: review.
59. **Pre-approved reads.** `date`, `sleep` for the CI poll, and read-only `git` and `gh` commands are the only commands the skill's `allowed-tools` pre-approves. Check: lint.

### Roles and models

60. **Orchestrator.** The session model orchestrates, judges, reviews each slice diff and decides; it never implements a slice. No fallback: without it the run stops. Check: review.
61. **Implementer.** Each slice is implemented by an Agent subagent at model `sonnet`, one per slice, parallel for slices with disjoint files, serial otherwise. Parallel implementers run no checks and say so; the orchestrator runs each slice's checks afterwards one command at a time, and a command several slices name runs once. Check: review; acceptance.
62. **Plan reviewer and final reviewer.** A fresh-context Agent subagent at model `fable`, given the request text, the file paths and the required reply shape, told to read and report only. On a model or tool error the call is retried once at `opus` and the swap is recorded and named in the report; a denial or a timeout is not an error. The reviewer stays swapped for the rest of the run. Check: review; acceptance.
63. **Higher-risk final review.** When the run is higher-risk (requirement 70) step 5 uses the built-in `code-review` skill with an explicit level and the range `<merge-base>...HEAD` as a full sha, never `--comment` or `--fix`; where that skill is not listed, or the diff lives in a worktree or an additional repository, an Agent subagent at `opus` reviews a patch file with the acceptance criteria and the same reply shape. The stand-in is continued with SendMessage in later rounds; it is not a swap and is named in the report. Check: review; acceptance.
64. **Reader.** Read-only work worth splitting out runs on `haiku`; the orchestrator may instead read itself. Check: review.
65. **Model configuration.** `.reimagine.json` `models` accepts `implementer`, `reviewer`, `fallback-reviewer` and `reader`, each one of `sonnet`, `opus`, `haiku`, `fable`. It never changes the risk floor or the higher-risk role. Unknown keys and bad values are reported and ignored. Check: review; acceptance.
66. **Agent calls carry the request shape.** A plan review asks for a numbered list of objections ranked by impact, each marked blocking or non-blocking with a confidence of high, medium or low and a one-line reason, ending with `NO BLOCKING OBJECTIONS` when there are none, and asks the reviewer to name the code that reads each contract change and confirm the shapes match. Blocking means the change would ship wrong behavior, break an acceptance criterion, or violate a repository rule. A diff review receives the plan, the inputs, the acceptance criteria, the disposition of every earlier finding, and reads `git diff <merge-base>` itself after new files are marked with `git add -N`, or a patch file for a worktree or additional repository. An empty diff is never sent to review. Check: review.

### Budgets and rounds

67. **Per-call budgets.** Minutes: `subagent` 20 for an implementer call, `review` 30 for a review pass, `check` 15, `ci` 45. `.reimagine.json` `timeouts` overrides any of them; `run` sets the run budget. Where a tool takes a timeout the budget is passed; the Bash foreground cap is 10 minutes, so a longer check runs in the background and is stopped at expiry. Check: review.
68. **Run budget.** The default run budget is 240 minutes, overridden by "budget <n> minutes" in the request, then `timeouts.run`, then a session instruction. Waits on questions are excluded. On expiry the output is kept and the run ends `blocked`, naming the budget; after a push the pull request is left as it is. Check: review.
69. **Risk floor.** A change that adds, alters or removes an auth check, a permission rule, a schema or migration, a row-level security policy, a data access path, or a public API's signature or behavior, directly or through shared code or configuration, is floored: reviewers receive effort at least `high`, and the report says which trigger applied. Incidental edits (a typo in a migrations README, a comment in an auth module, a rename with no signature change) do not trigger it. The floor is judged at the plan and again on the actual diff after step 4, and never falls. Check: review; acceptance.
70. **Higher-risk rule.** A run is higher-risk when a floor trigger exists, when more than eight distinct files are changed across all slices including created files, or when a new module, type, interface or rule section is cited by another file. It is judged at the plan, after step 4, before every step 5 round and before every CI repair. Once higher-risk, always. It selects the step 5 role only. Check: review.
71. **Date discipline.** `date -u +%Y-%m-%dT%H:%M:%SZ` runs only at the start of step 0 and of each step, before and after each timed call, after each push returns, at the terminal state, and just before and after each question. Times are copied into the record from the command output, never from memory or arithmetic. Check: review.
72. **Round cap.** No step repeats more than three times. A round is one pass by the stage's reviewer plus the fixes it leads to. The orchestrator's single fix after the step 4 cap is not a round; step 5 has no such fix, and its third round fixes nothing. Each CI repair cycle gets one step 5 round and one full step 6 run; cycles are capped at three. Check: review.

### Preflight (step 0)

73. **Nothing written before the record exists.** Until step 0.5 the run writes nothing; a failure before it prints the report only. The one exception is a worktree run, which writes the `.reimagine/` exclude, the record directory and the worktree at step 0.3; from then a failure writes the report to the record. Check: review.
74. **Host detection.** The remote is the one `gh repo view` resolves, else `origin`, else the only remote; several remotes without `origin` is a preflight failure. A GitHub host where `gh` fails ends with "gh not authenticated". On a non-GitHub host steps 0 to 6 run, the end of step 6 writes the run's body file from `pr-body.md`, and the run ends `prepared` with the push commands and the body file to paste. A remote is Azure DevOps when its host is `dev.azure.com`, `ssh.dev.azure.com` or `vs-ssh.visualstudio.com`, or ends in `.visualstudio.com`; preflight records that and the remote's organization and project. Check: review; test; acceptance.
75. **Permission statement.** Step 0.1 prints the approved actions, the carve-outs, and for each action whether a prompt will occur, from the permission mode, the settings files and the allow rules; an undeterminable permission counts as a prompt. It predicts the worktree, credential, adoption, plan-confirmation and branch questions, and prints "this run will prompt at: ..." or "this run is unattended", naming the request forms that avoid each question. Check: review; acceptance.
76. **Base branch and base commit.** Step 0.2 resolves the base branch `<b>`: "base <branch>" in the request, else `.reimagine.json` `base`, else the remote's default branch (requirement 282); fetches it with the explicit refspec `+refs/heads/<b>:refs/remotes/<r>/<b>`; and records the base commit. A continued branch equal to the base branch is rejected. Check: review.
77. **Continue checks.** A continued branch must pass `git check-ref-format --branch` and must not be checked out in another worktree (the failure names the three ways around it: start the run inside that worktree, "primary <that path>", or "also edit <that path> on <branch>"). A branch named in the request without a record must exist as the exact ref `refs/heads/<branch>` on the remote. A branch with a record may exist locally only, as after a `prepared` run, or nowhere, as after a plan-only run, and is then created like a new branch; when it also exists on the remote, the local tip must be at or behind the remote head and is fast-forwarded to it. A local branch that diverged ends `blocked`. The session HEAD ends at the branch tip. Check: review; acceptance.
78. **Open pull requests.** On GitHub, `gh pr list --head <branch> --state open --limit 100 --json number,state,baseRefName,url,isCrossRepository`, filtered on `isCrossRepository`; 100 entries counts as incomplete and fails; one open pull request is recorded; several end `blocked`. Check: review.
79. **Clean tree.** `git status --porcelain` must be empty and `git diff --cached --quiet` must pass, else `blocked`; the loop never stashes, resets or cleans. Check: review; acceptance.
80. **Flagged files.** Paths marked skip-worktree or assume-unchanged are compared against HEAD with `git cat-file --filters`; a difference with a clean status creates a detached worktree at `<checkout-parent>/<checkout-name>-reimagine-<branch-slug>`, beside the checkout and never inside it. Dependencies are installed in the worktree before the baseline, else the check is "not run". A switch in a worktree detaches in place and fast-forwards with `git fetch .`. Check: review.
81. **Malformed configuration.** A `.reimagine.json` that does not parse ends `blocked`. All of its keys are optional: `commit`, `checks`, `timeouts`, `models` and `base`. Check: review; test (the configuration block in the skill is byte-identical to the README's and has exactly those keys).

### Record and idempotency

82. **Record location.** The record lives at `.reimagine/loop/<branch-slug>/` in the primary repository, where the slug is the branch name lowercased with every run of characters outside `[a-z0-9]` replaced by `-`, at most 60 characters. `.reimagine/` is added to `.git/info/exclude`, never to `.gitignore`. Nothing under `.reimagine/` is ever staged. `steps.json` records the exact branch name; a record whose branch differs from the run's branch is a slug collision and ends `blocked`. Check: review; acceptance.
83. **Branch known at preflight.** The branch is the continued one, the "on branch" one, the branch of the one existing record whose `tickets` list holds one of the request's tickets (several such records stop the run), or the predicted name: `fix/<ids>-<slug>` when a ticket is labeled bug or titled "fix", else `feat/<ids>-<slug>`, else `work/<slug>`; a collision with an existing local or remote branch that has no record ends `blocked`. A record whose pull request merged or closed ends `blocked`, naming the pull request and the "on branch" form that starts a new branch. Check: review.
84. **Record files.** `inputs.md` (invocation block with time, each ticket as fetched, files and text, verification notes, drift corrections, buildable status, risk floor), `plan.md` (plan plus a review log per round), `run.md` (the durable log), `steps.json` (the completion record), `report.md` (every terminal state), `handoff.md` and `audit-manifest.json` (when the run has its own commit), patch and snapshot files, and `pr-body.md` and comment bodies, which are never committed. Check: review.
85. **Completion record.** `steps.json` holds the branch, a list of runs with number, start, end and terminal state, and one entry per step with `status` (`running`, `complete`, `failed`, `skipped`), the run number, start and end, the hashes of its inputs (for Steps 1 and 2, each open input's version: an issue's `updatedAt`, a work item's `rev`, a case's `SystemModstamp`, or the hash of a file or description), and its output paths. The entry is written `running` when the step starts and `complete` only after its outputs exist; it is written through a temporary file and a rename; it is the only record of completion. Check: review; acceptance.
86. **Second run appends.** A second invocation on the same branch appends run `n+1` to the same record; `run.md` and `inputs.md` gain a dated section per run; nothing from a prior run is modified except `steps.json`, `plan.md` (appended), and `report.md`, `handoff.md` and `audit-manifest.json` (rewritten). Per-run files without a counter (the pull request body, ticket comments, patches) take a `-run<n>` suffix from run 2 on, so none is overwritten. Check: acceptance.
87. **Preflight reads the branch state.** On an existing record the loop lists `git log <merge-base>..<tip>`, where the tip is the remote head when the branch exists on the remote, marks every commit either as its own (named by a commit line the loop wrote in `run.md`) or foreign, writes the list to `inputs.md`, and judges tickets done by their recorded closing commit. Check: acceptance.
88. **Review base.** Every diff review and every "changed lines" count uses the merge-base with the base branch of requirement 76, so foreign commits are reviewed with the loop's own. Check: review.
89. **Built slices are not rebuilt.** A slice whose closing commit is on the branch is skipped; a ticket with a closing commit is marked done. A slice the loop built and did not commit records its file hashes and counts as committed when the branch tip holds them, as after a `prepared` run that the user committed. Check: acceptance.
90. **Same tickets, no new work.** When every ticket is done and the plan has no open slice, the run verifies the checks (step 6). When the work is published (the run that last reached step 7 ended `done` and a pull request is open on the branch), it rewrites the report, posts nothing, commits nothing, and ends `done`; otherwise step 7 publishes the committed work. Check: acceptance.
91. **New tickets extend the plan.** New tickets add slices to `plan.md`, which goes through plan review again; the new slices are built and reviewed; the pull request this loop opened gets its body updated once per run with `gh pr edit --body-file <absolute path>` and one comment per run; a pull request the loop did not open gets a comment only and its body is never edited. Check: acceptance.
92. **Interruption safe.** Every step records completion before the next starts. A rerun recomputes the input hashes, reuses every step whose inputs are unchanged and whose outputs exist (step 4 only when its slices are committed), rechecks the tree, and resumes at the first incomplete or changed step. Step 3.7 sets up the checkout in every run that builds or checks. Check: acceptance.
93. **Never rewrite.** The loop never force pushes, rebases, resets or amends. Before each push it reads the remote head with `git ls-remote`; a head that differs from the one preflight fetched ends the run `blocked` (fast-forwarding belongs to preflight, requirement 77). Check: review; acceptance.
94. **Terminal states.** `done` (pull request open, CI green or not applicable, report written); `plan-only`; `prepared` (every step through 6 complete, publication withheld before any push, with the publish commands); `blocked` (a blocking defect, a denied permission, a budget exceeded, a preflight failure); `stopped` (a question the run cannot decide, before any branch is created). After `blocked` nothing more is published; pushed work stays and is linked. Check: review.
95. **Snapshot before an implementer call.** Before each implementer or fix call the loop records `git status`, a patch and file hashes. After a failed call it restores only paths that were clean before the call; anything else ends `blocked`. Check: review.
96. **Commit snapshot option.** With `.reimagine.json` `commit: true`, each run that publishes commits `docs/runs/<branch-slug>/plan.md` and `report-<n>.md` with state `publishing`, and the terminal report is posted as a pull request comment in its external form: the header without the lines that name local paths, What changed, Checks, Deferred items, and Blocked, stopped or prepared, without the Risk, Decisions, Findings rejected and Log sections, so that it names no model, agent or tool. Check: review; acceptance.

### Plan (steps 1 to 3)

97. **Verification before planning.** For each ticket the loop reads the inputs, verifies claims (for a bug it reproduces or runs a check that confirms or rejects the explanation), records drift between the ticket and the code in `inputs.md`, and marks each input buildable, partial or blocked. Check: review.
98. **Repository gate.** A candidate checkout (an absolute path in the inputs that `git -C <dir> rev-parse --show-toplevel` maps to a checkout other than the primary, its submodules or the adopted ones, and that the inputs ask to change) triggers the adoption question of requirement 50; one found later ends `blocked`. A submodule path is not a separate repository. Check: review.
99. **Plan content.** `plan.md` holds, per input, scope, acceptance criteria and buildable status; across inputs, shared changes, migrations and API changes, tests, checks, order of work, and slices with disjoint files; per slice, the files owned, the change, criteria, tests, checks and the implementer. Slice count is a plan property. Check: review.
100. **Plan review rounds.** Each round verifies every objection, revises, appends a review log to `plan.md`, and is done when the reply ends `NO BLOCKING OBJECTIONS` and the orchestrator finds none. A disagreement that is the user's call ends `stopped`; the cap with a blocking objection ends `blocked`. Check: review.
101. **Plan only.** In plan-only mode the run ends `plan-only` after the review, having changed nothing in the tree. A plan confirmation not answered with a clear yes also ends `plan-only`; a change request is another round within the cap; after a yes the clean-tree, flagged-file, branch, remote-head and pull request checks run again. Check: review; acceptance.
102. **Execution setup.** After the plan is final the loop reverifies against the base when the base moved, creates or switches to the branch, discovers the checks and runs the baseline once, and installs plan-added dependencies after the ask-first yes and before any implementer. Check: review.
103. **No comment before the plan.** Nothing is published before the plan is final, and nothing new is published on a blocked run. Check: review.

### Build (step 4)

104. **Slice brief.** Each implementer receives its slice from `plan.md`, the files it owns, the acceptance criteria, the checks, the repository's line-ending convention, and the instruction to change nothing outside its files and add nothing the brief does not ask for. Check: review.
105. **Slice review.** The orchestrator reviews each slice diff with `git add -N` then `git diff <merge-base> -- <slice files>`, checks line endings with `git ls-files --eol`, and sends findings back; three rounds per slice, then one orchestrator fix; a still-blocking finding ends `blocked`. Check: review.
106. **Re-evaluation.** After step 4 the risk floor and the higher-risk rule are judged on the actual diff. Check: review.
107. **Baseline failures.** A check failing on the base is matched by test names, not counts, since some failures are timing-dependent. Check: review.

### Final review (step 5)

108. **Integrate first.** Step 5.1 runs the full suite on the integrated tree and fixes regressions; every later edit is logged. Check: review.
109. **One final role per run.** Before every round the higher-risk rule is judged and one role reviews the complete diff from the merge-base. The role never weakens after step 4. Check: review.
110. **Findings.** Findings are merged, deduplicated, checked against recorded rejections, verified, and fixed in one batch through the slice's implementer. A rejected finding is recorded with its reason. A repeated rejected finding keeps its disposition unless it brings new evidence. Check: review.
111. **Rounds.** A fresh pass each round, cap three; a blocking finding in round three ends `blocked`. Every fix is seen by a later round, so the third round fixes nothing. Check: review.

### Checks (step 6)

112. **Discovery order.** `.reimagine.json` `checks` first, then manifest-defined test, lint, typecheck and build commands (npm scripts, Makefile, pyproject pytest, ruff and mypy, cargo test and clippy, go test and vet, gradlew check), then CI jobs that run those; a CI job not mappable to a local command is deferred to CI, not guessed. Check: review.
113. **Reuse.** Step 6 reuses the step 5.1 run when no edit was logged since. Each failure not matching the baseline gets a step 5 round; step 6 runs at most three times before publication, plus one run per CI repair cycle (requirement 127). Check: review.
114. **Not run versus denied.** A check without its resource is "not run" with its exact command and directory; "denied" means only a refused permission. Check: review.

### Publish (step 7)

115. **Commit.** Paths are staged by name, never `git add -A` or `.`; nothing under `.reimagine/` is staged; after a run's first push, that run commits only CI repairs. Check: review.
116. **Push and pull request.** `git push -u <remote> <branch>`, never forced, then `gh pr create --title "<title>" --body-file <absolute path>` against the base branch of requirement 76, where the title is the single ticket's title or the plan's one-line summary, at most 70 characters; every `--body-file` is an absolute path. A pull request opened on a continued branch lists the commits from before the run and says they were reviewed as part of this run's diff. Check: review; acceptance.
117. **Body sections.** `pr-body.md` has, in order: What changed (per input, complete or partial), Drift corrections, Decisions for the reviewer, Checks not run, Related pull requests, Closes. `Closes <ref>` only when every acceptance criterion is confirmed met, else `Refs <ref>`; one line per ticket; file and text inputs get no closing line; across repositories only the ticket's own repository closes it. An Azure DevOps ticket is `Refs AB#<n>` on GitHub and `Refs [<type> <n>](https://dev.azure.com/<org>/<project>/_workitems/edit/<n>)` on an Azure DevOps remote, with `<type>` and `<project>` from the work item read (`System.WorkItemType`, else `Work item`; `System.TeamProject`, else the remote's project, spaces as `%20`) and `<org>` from the remote; a `Refs` line does not attach the work item, so a `prepared` report asks the user to link it. On an Azure DevOps remote the description is capped at 4,000 characters, so the body is always the short form (Related pull requests, Closes, and "Details are in the first comment.") and the full body, What changed included, is a comment file to post first. On a non-GitHub host the body covers every input of every run of the record. Check: review; test.
118. **Ticket comments.** After the pull request is open, one status comment per ticket the run took up, where a ticket done at preflight gets none unless no run has commented on it: state (complete, partial, blocked), the pull request link, criteria met, not met or not confirmed with evidence, not done, deferred. GitHub through `gh issue comment`; Azure DevOps through the MCP tool, else `az boards work-item update --discussion`; Salesforce through its MCP tool; a host without a tool gets the comment text in the report instead. No comment is posted on a blocked run and no issue is opened. The text names no run-internal path. Check: review; acceptance.
119. **Deferred items.** Each deferred item is listed with its reason in the report and the pull request body, or, on an Azure DevOps remote, in the full body written to the comment file to post first; none becomes an issue. Check: review.
120. **Handoff and manifest.** When the run has its own commit, `handoff.md` (requirement 137) and `audit-manifest.json` are written in the record, and the report suggests `/audit:run "<absolute manifest path>"` when the work spans more than one repository, more than one ticket, or 500 or more changed lines over the three-dot diff. A pull request is named in the manifest only when the live remote head equals the local HEAD. Check: review; acceptance.

### CI watch

121. **Reads name the host.** Every `gh api` call passes `--hostname`, is spelled out as one endpoint, runs one read per Bash call, and never inside a shell loop. A failed read ends `blocked`, except an HTTP 403 whose message says to upgrade or make the repository public, which means no rulesets. Check: lint (backtick spans); review.
122. **Required checks.** Read from `repos/{owner}/{repo}/branches/<base>` `.protection` and from `rules/branches/<base>` with pagination, including required workflows, never from `/protection`. Check: review.
123. **Pull request state at every poll.** `gh pr view --json headRefOid,mergeable,baseRefName,state` plus the merge commit sha. Not OPEN ends `blocked`; a retarget ends `blocked`; the live remote head must equal the last pushed sha, with a stale `headRefOid` pending for two minutes; `CONFLICTING` ends `blocked` at once. Check: review.
124. **Results.** Latest result per context and per check suite, from check-runs with `filter=latest`, statuses, and `actions/runs?head_sha=` for required workflows. Pass is success, neutral or skipped. The gated commit is the test merge commit when it has results, else the head. A status-only check that names an app ends `blocked`. Check: review.
125. **Applicability.** `pull_request_target` is judged from the base branch's file; branch, path and type filters apply; skip markers make a workflow not applicable but required checks stay required; a deferred check whose filters exclude the pull request is not expected. Check: review.
126. **Green.** Every required check, every deferred check and every applicable workflow reported, and every latest result passed. CI is not judged before two minutes after the push; polls are about thirty seconds apart; pending past the `ci` budget ends `blocked`. Not applicable only when nothing is required, applicable, expected or seen within two minutes. Check: review.
127. **Repair.** A red result re-enters step 5 for one round and step 6, at most three cycles; still red ends `blocked` with the pull request linked. Check: review.

### Multi-repository

128. **One pull request per repository with a diff**, each on its own branch and base, with its own baseline and checks; no slice spans repositories. Bodies carry "Related pull requests" with "pending" first, then each body the loop opened is edited once with the sibling links. `done` needs every pull request green; a block in any repository stops publication in all, except the sibling-link edit. Check: review; acceptance.
129. **Commands per repository.** Git uses `git -C <path>`; gh uses `-R <host>/<owner>/<repo>` or runs inside the checkout. A host mismatch between repositories ends `blocked`. Check: review.
130. **Skip-worktree paths.** No slice may edit a skip-worktree path of an additional repository, since the edit is invisible to diff, `add -N` and staging. An additional repository's review reads a patch from `git -C <path> diff`. Check: review.
131. **Branch suggestion.** When a continued branch must be chosen among candidates, the suggestion uses the shared-stem rule: the longest common prefix of the names, not cut at `/`, never a default-branch prefix. Check: review.
132. **Handoff bundle order.** The first bundle is the primary, then the "also edit" order; a verified check is listed only for the first bundle. Check: review.

### Reporting

133. **Report compiled from the record.** `report.md` is written at every terminal state from `run.md`, never from memory. Every section is present; an empty one says "none". Check: review.
134. **Header.** Run number, branch, record path, terminal state, host, run budget and its source, base commit, merge-base, worktree, repositories, pull request, CI state, handoff and audit lines. Check: review.
135. **Sections.** Attended or unattended (prompts predicted and seen, question waits); Risk (floor trigger, higher-risk judgment, step 5 role, swaps); What changed (per input, completion, changes, criteria with evidence, drift); Decisions (choice, reason, who decided: user, plan confirmation, review or run); Findings rejected and why; Checks (run, not run with command and directory, deferred to CI, failing at baseline with evidence); Deferred items; Blocked, stopped or prepared (what, steps not done, where the work is, what would unblock it, the exact commands); Log (implementer per slice, rounds, elapsed against budget). Check: review.
136. **Headless reports.** Text asked of the model before a Skill call is not shown in a headless session, so the report header carries everything a reader needs to find the record. Check: review.

### Handoff format

137. **Typed handoff.** `handoff.md` starts with frontmatter `reimagine-handoff: 1` and `generated: <ISO 8601>`, then the sections Bundles, Tickets, Decisions, Raised tickets, once each in that order; the audit's `handoff.sh check` validates it when the audit reads it, and the loop runs no check of its own. Check: review; test (audit `handoff.sh`).
138. **Ticket entries.** Each `### <ticket id>` carries, in order, type, state, iteration, owner, parent (optional), links (optional), bundles, problem, decision, commits (`- <bundle> <sha>: <text>`), verified (`<statement>; check: <check|not recorded>`). Ids are normalized to `github:owner/repo#n`, `ado:<org>/<project>#<n>`, `sf:<case number>` or `file:<path>`. Check: review; test.
139. **Decisions.** Each `### D<n>` carries ticket, decision, rationale, options (`chosen:` or `rejected: ...; why: ...` or `none recorded`), decided_by (`role: <role>`, `checkpoint (recommended option taken)` or `not recorded`; never a person's name and never a model, agent or tool), recorded_at, status. The record's four deciders map to decided_by in one table that the loop's `handoff.md` and the audit's `handoff.md` carry word for word: user to `role: session user`, plan confirmation to `role: session user (plan confirmation)`, review to `checkpoint (recommended option taken)`, run to `role: orchestrator`. Check: review; test (the two tables are identical).
140. **Parent and links.** The GitHub parent is read through GraphQL with `--hostname`, late in the run so the run's own pull request is included; a failed read writes no key, never `links: none`. Check: review.
141. **Written only with a commit.** The handoff is written only after the run's own commit, in any terminal state; the loop never commits in order to write one. Check: review.

## The `audit` plugin

### Invocation

142. **Prose invocation.** The skill `audit` is user-invocable and its description names "reimagine audit". Requests such as "reimagine audit PR 123 and 124 in app, tickets AB#4567 and AB#4580" are read into bundles; a manifest file path is accepted and is what the loop handoff writes. Thin commands `/audit:run`, `/audit:resume`, `/audit:act` and `/audit:handoff` forward to the skill. Check: lint (frontmatter); acceptance.
143. **Reading block.** After only the read-only calls that resolve ids and before any other tool call, the skill states bundles (repository, pull request or branch and base, tickets), references, sources of truth, claims files, effort hint, budget and model overrides, and how each ticket resolved. Check: acceptance.
144. **Effort is a hint; size sets the default.** The default tier is `low` for one bundle, one ticket and under 500 changed lines; `medium` up to three bundles, five tickets and under 5,000 lines; `high` otherwise. A hint ("effort high") overrides it. The tier sets the pass-one scopes, how much pass two attacks, and whether the late adversary runs. Check: review.
145. **Manifest.** Keys: `bundles[]` (`repo`, `pr` or `branch` plus `base`, `tickets[]`, `ticket_token`, `run_once`, `head`, `test_command`, `test_run`, `test_paths`, `test_setup`, `test_timeout`), `references[]`, `sources_of_truth[]`, `claims[]`, `scratch`, `forge_exports`, `groups[]`, `questions`, `models`, `budget`, `max_agents`, `_test`. Validation messages name the key. Check: review; test (fixture manifests).
146. **Exported forge files.** A ticket or pull request on a host without a tool is supplied as a `file:` export in markdown with frontmatter or JSON; a ticket requires id, url, title, state and description, a pull request id, url, title and body, every file source, exported_by and exported_at; a missing key stops the run. `forge_exports.command` is recorded, never run. An Azure DevOps or Salesforce MCP tool used for a read is recorded as `mcp:<tool>`. Check: review; test.
147. **Pause background fetch.** After the summary the skill tells the user to pause background fetch, for example VS Code `git.autofetch`. Check: review.

### Stage model

148. **Nine stages.** Orient, digest, domain map, pass one, pass two, second opinion, converge, report, act, in that order with these dependencies: 1 alone; 2, 3 and 4 together; a per-group barrier opens stage 5 when 2 and 3 are done and top-ups finished; 6 after every pass two; 7 the late adversary and the merger; 8 always. A stage whose input is absent is `not_applicable`; a failed stage counts as satisfied and the run ends `partial`. Check: review; acceptance.
149. **Completion record.** `stages.json` holds `plugin_version`, `approvals[]` (`fetch`, `live`, `export-over-1gb`, `background-fetch`) and per-stage entries with `status` (`running`, `complete`, `failed`, `not_applicable`, `superseded`), `inputs` as file hashes from `git hash-object --no-filters`, `outputs`, `agents[]` (type, requested model, scope, start, end, tokens labeled "task notification, subagent_tokens; scope not documented", duration, result), `swaps`, `superseded`. It is written through a temporary file and `mv -f`, the entry goes `running` at start and final only after the outputs exist and the read-only check passed, and it is the only record of completion. Check: review; acceptance.
150. **Roles.** Digester `haiku`; mapper and merger `sonnet`; auditor and adversary `opus`; second opinion a fresh `adversary` at `fable`. The manifest `models` key overrides any role with `opus`, `sonnet`, `haiku` or `fable`. Agents are launched with the Agent tool as `audit:<role>`, in the background, never as a fork, never general-purpose, each with its own scratch folder. Check: review; acceptance.
151. **Failure ladder.** Digester, mapper, auditor and adversary: relaunch on the same model, then on `fable` as a swap, then the scope fails. Merger: the orchestrator merges, a second failure fails stage 7. Second opinion, per batch: relaunch on `opus`, then stage 6 fails. An agent fails when it returns an error, when its last line is not `status: complete`, or when fault injection marks it failed. Swaps are recorded and named in the report. Check: review.
152. **Queue and budget.** At most `max_agents` (default 8) agents run; launch order digests, maps, pass one; relaunches go first; scope is never merged or dropped to fit. A soft budget applies only to the invocation that gave it; once expired nothing more launches from stages 2 to 7, unstarted stages are recorded `failed` with "not run: budget expired", and the run goes to stage 8. Check: review.
153. **Orient.** Stage 1 refuses partial clones, sets `GIT_NO_LAZY_FETCH=1`, asks once for one `git fetch --no-tags --refmap=` into remote-tracking refs, takes the read-only baseline per repository before any other work, builds a working-tree head with `working-tree.sh` when asked, reads forge data into files without passing it through the model, writes the three-dot diffs with `--no-ext-diff`, exports trees by one `git cat-file --batch` stream, prepares revert keys, writes claims, groups, the brief and the stage entry. Check: review; test.
154. **Digest.** Applicable when a source of truth is a document corpus (more than half of its files have document extensions). Chunks of about 450,000 bytes filled with whole directories; oversized files split at the last LF into byte ranges read in slices of at most 24,000 bytes; an incomplete read ends `status: failed at byte <offset>`. Check: review; test.
155. **Domain map.** Per-ticket questions `<ticket>-M<n>` with group ids; the mapper answers with quotes or `not found` with the search used. Check: review.
156. **Pass one.** Scopes by tier: `low` one `combined`; `medium` one per group plus `tests-hygiene` plus `interactions` with more than one bundle; `high` one per group plus `tests`, `hygiene`, `interactions`. The barrier compares `consumed:` hashes with the digest and map outputs and runs a top-up per miss until none remains. A missing Decisions, Scope or Outward trace section is `not assessed`, not a failure. Check: review; test.
157. **Pass two.** A fresh adversary per complete pass-one report, never a continuation, attacking none, the five riskiest, or all Verified OK and outward-trace entries by tier, writing verdicts, challenged sections, coverage gaps, new findings `<scope>-P<n>` with `origin: pass2`, map corrections (one round of top-ups writing `<scope>-T<n>`), claims challenged. The ledger `ledger/5.md` is built by `ledger.sh build5` from `ledger/inventory.txt` and checked with `ledger.sh check --through 5`, one retry. Check: review; test.
158. **Second opinion.** Stage 6 always runs. A fresh `adversary` at `fable` (then `opus`) receives the request file with every finding including dropped ones, every pass-two file, the brief, evidence rules, claims, diffs, live files, and the audited sources named by absolute path and sha; inputs carry a sentinel line that the answer must acknowledge.
