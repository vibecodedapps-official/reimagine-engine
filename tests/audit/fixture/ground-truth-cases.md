# Ground-truth set: 20 confirmed review findings, de-identified

Every case below is a defect a reviewer raised on a finished change and confirmed, which neither the change's author nor a second review of the same diff raised. Names, identifiers, tickets, and data are generic. Each case gives the shape needed to plant it in a small shell or Python fixture.

Severity: the reviewer labeled findings as "blocking", "non-blocking", or left them unlabeled with a request. The mapped severity in each case is the set author's, from that label and the blast radius. "Confirmed by" says how the reviewer or the author showed it was real.

Pattern key: `sibling` (missed sibling or symmetry), `test` (test that does not discriminate), `callee` (failure branches of a new call or readers of a widened input), `producer` (base producer drift), `run-once` (journaled script), `artifact` (rule stated in several artifacts), `other`.

## Sibling cases

**S1. One of three symmetric query branches gets the filter.**
Pattern: sibling. Before: a SQL view emits "related record" links from three UNION branches (direct relations, relations through type A, relations through type B); a downstream importer rejects any record whose link points at a target in an ineligible state. Change: adds a state-eligibility filter (`WHERE status IN (...)`) to the first branch only, and a data-quality sweep query that reports dropped links reads only the first branch. Defect: a target reached through branch two or three in an ineligible state still emits a link, the importer rejects the whole record, and the sweep does not report it. Confirmed by reading; the author then found a reachable case (a target in a rejected state admitted by the root filter on an unrelated flag). Severity: medium (reviewer: non-blocking, no rows hit in current data; a gap for future sources). Why missed: the agent edited the branch the ticket described and never read the other two, which sit twenty lines below in the same file. Plant: a shell script with three `case` arms or a Python function with three `elif` branches that build the same list, the fix applied to one.

**S2. New endpoint lacks the guard every sibling endpoint carries.**
Pattern: sibling. Before: six import endpoints in one handler file each start with `enforce_import_right(request)`. Change: adds a seventh import endpoint modeled on the one directly above it, with every line copied except the guard. Defect: any authenticated caller, regardless of role, can create or update the new record type; this reopens a class of defect a previous bug had closed with a regression suite that the new endpoint is not in. Confirmed by reading, then by the reviewer adding the with-right and without-right test pair, which failed before the one-line fix. Severity: high (reviewer: blocking; the reviewer pushed the fix). Why missed: the agent compared the new function to the ticket, not to its siblings; the regression suite's naming made the gap visible only by listing which endpoints it covered. Plant: six functions with a first-line guard, a seventh without, and a test file that enumerates six names.

**S3. Fix applied to two of the four record types the ticket names.**
Pattern: sibling. Before: four JSON schema files, one per record type, each declare a `category` property as a plain string where the model expects an object reference. Change: fixes two files and adds a schema test over those two. Defect: the ticket names all four; a third file carries the identical defect and would have taken the same two-line change; the fourth cannot be fixed because it has been invalid JSON since an older commit, which the author did not know. Confirmed by reading and by loading the fourth file. Severity: medium (reviewer: scope note, approved; asked that the ticket not auto-close). Why missed: the agent scoped to the two files the earlier investigation touched and did not reopen the ticket's list. Plant: four schema files with the same wrong type, a ticket export naming four, a fix touching two.

**S4. Update path loses a column its two sibling functions guard.**
Pattern: sibling. Before: three SQL upsert functions, one per record type; two of them write `source_identifier = COALESCE(incoming, source_identifier)` on update, the third writes `source_identifier = incoming`. Change: fixes the create path for the third function and adds a test that pins the update path's lossy behavior as expected. Defect: a re-import that omits the field nulls a column that reporting and a downstream mapping service read; the new test now freezes the loss, so a later fix must change a test asserting the opposite. Confirmed by reading the three functions side by side. Severity: medium (reviewer: question, not labeled a defect; the author took the one-line fix). Why missed: the agent treated the residual as a disclosed limitation and wrote a test for it instead of checking what the siblings do. Plant: three upsert functions in shell or Python, two with a fallback, one without, and a test asserting the no-fallback result.

**S5. Runtime stops enforcing a rule; the published contract still declares it.**
Pattern: sibling, artifact. Before: the service validates a `required` list from an OpenAPI schema; a sibling pull request for a near-identical record type removed `required: [items]` from the spec in the same change that stopped enforcing it in code. Change: this pull request stops enforcing `required: [items]` in code only; both spec files still declare it. Defect: the published contract misleads the upstream mapping team, and the "parity with the sibling PR" claim holds for the runtime half only. Confirmed by reading both spec files and diffing the two branches (four shared files byte-identical). Severity: low (reviewer: non-blocking; no functional impact because the deployed validator had no `required` on that definition). Why missed: the agent copied the sibling's code change and not its spec change. Plant: a code validator plus a `spec.yml` with a `required` list, and a sibling branch that changed both.

## Test cases

**T1. A waiver matches a bare string; a later base change prefixed it; the unit test and the scenario pass either way.**
Pattern: test, producer. Before: a bulk-import waiver removes validation errors equal to the constant `"flag is required"`. A base commit eight days later changed the validator to return `"<field path>: <message>"` for every message without a placeholder. Change: this bundle carries the waiver from a branch written before that base commit; its unit test asserts `DoesNotContain(e => e == SAME_CONSTANT)`, and the integration scenario was rewritten the same day to accept either success or the rejection message. Defect: the waiver removes nothing on the merged code; every import on a tenant with the setting on rejects every record; the unit test passes before and after; the scenario cannot tell fixed from unfixed. Confirmed by running: with the unit test assertion changed to match the real string it failed; the deployed build then rejected the record; after the fix the scenario passed through the success branch. Severity: high (reviewer: "your call", from reading; the author confirmed by running). Why missed: the agent compared the test against the code's own constant, and the second reviewer read the diff, not the producer on the base. Plant: a producer function on the base branch that gains a prefix after the merge-base, a matcher on the feature branch that compares the bare string, and a test that imports the same constant.

**T2. Text-only "contract tests" stand in for executing SQL; one ticket has no executed verification.**
Pattern: test. Before: a unit suite with no database; a class of "drift guard" tests that read SQL files as text and assert a `RETURNING` clause is present, a placeholder assignment is absent, and a regex finds no unguarded call. Change: four SQL fixes, each covered only by those text assertions; the description says they are covered. Defect: nothing executes the SQL; one fix (a trigger that re-reads a stored JSON null) ships with zero executed verification, and another's claimed coverage asserts statement ordering only. Confirmed by reading the test class and reconciling per ticket against the integration suite. Severity: medium (reviewer: not blocking, "worth a deliberate call rather than an oversight"). Why missed: the agent counted a test per ticket without asking whether the test runs the change. Plant: a SQL file, a test that greps it, and a claims file saying the ticket is covered.

**T3. The control assertion runs after the assertion it controls.**
Pattern: test. Before: an integration scenario asserts two dates on a fetched record; the header says the second date is a control that "passes before and after the deploy, so if both fail the comparison itself is at fault". Change: adds the scenario with the controlled assertion first. Defect: the assertion step throws on failure, so when the first date fails the control never runs, in exactly the case it was written for. Confirmed by reading the step binding. Severity: low (reviewer: non-blocking; swap the two lines). Why missed: the agent wrote the diagnostic rationale without tracing the failure path through the test framework. Plant: a test with two `assert` lines where the second is labeled the control.

**T4. A static field holds state across scenarios, so a guard weakens after the first run.**
Pattern: test. Before: a shared step class with `static` fields; a new "Then" step fails when the fetched row is null, with the message "run the read step first". Change: adds the read step that sets the static field and the assertion step that guards on it; no before-scenario reset. Defect: once any scenario has run the read step, the field stays populated for the process; a later scenario using the assertion step without the read step compares against the previous scenario's row and can pass for the wrong reason. Confirmed by reading; no reset hook existed in the class. Severity: low (reviewer: non-blocking). Why missed: the agent checked the happy path within one scenario. Plant: a Python test module with a module-level variable set by one test and read by another, run in both orders.

**T5. A scenario that needs a new database role fails instead of skipping where the role is absent.**
Pattern: test, other. Before: the harness has a `@needs-role:<name>` tag; a hook ignores a scenario whose named roles are missing from the environment's accounts file. Change: a new scenario reads the database through a new role entry present in one environment's accounts file only, tagged with the API persona's role but not the database role. Defect: on any other environment the scenario runs, dies inside the database step with a role-file error, and reports a failure rather than an ignore; the hook that exists to prevent exactly that is bypassed by a missing tag. Confirmed by reading the hook. Severity: low (reviewer: one-line fix). Why missed: the agent satisfied the tag convention for the persona it knew about and did not list every new external dependency. Plant: a test runner that skips on a missing `requires:` entry, and a test that uses a resource without declaring it.

## Callee and consumer cases

**C1. A new external call inside a batch transaction fails two ways: total abort or silent relaxation.**
Pattern: callee. Before: a bulk import path with per-record isolation and no external settings dependency, inside a transaction whose catch does rollback-and-rethrow. Change: adds a settings lookup (one call, cached) so a validation rule follows a tenant setting. Defect: the callee's own catch splits three ways by exception message text: two messages rethrow (whole batch rolls back, caller gets 500, a 3,700-record load dies on an unrelated cache blip), every other exception returns the default `null`, which the caller compares to `"yes"`, so every conditional rule is silently off for the batch with no log. The pull request description mentions the fail-closed branch only. Confirmed by reading the callee (the reviewer grepped the folder to show it was the only such call). Severity: high (unlabeled; the author made the policy explicit at both points). Why missed: the agent read the call site and the ticket, not the callee's catch blocks. Plant: a function whose error handling returns a default on some exceptions and rethrows on others, newly called from inside a loop with a rollback.

**C2. Passing a two-key settings map changes a third rule nobody asked about.**
Pattern: callee (consumer of a widened input). Before: a validator receives `null` for tenant settings, so every setting-conditional rule is treated as enabled; the model has three such rules keyed on two setting names. Change: passes a real map populated with the two keys, to make one rule follow the tenant. Defect: the third rule, keyed on one of those same names, now also follows the tenant; an import omitting an office is accepted on tenants with that setting off; no ticket, description line, or test covers it. Confirmed by reading the model's attributes and the constant that maps the rule to the key. Severity: medium (reviewer: "the one behavior change I would want a QA case against"). Why missed: the agent traced the key it added, not every reader of the map. Plant: a config dict with two keys, three rules reading it, a change that populates it for one rule.

**C3. A raw database session ignores the row-level security the service relies on.**
Pattern: callee, other. Before: tables carry a row-level security policy keyed on a session parameter the service sets per request. Change: a test step opens a raw connection and selects a row by key. Defect: the session never sets the parameter, so the select either errors on the unset parameter or returns zero rows, and the step then fails on its own row-count guard with a misleading message; the harness's existing database steps hit a different database without that policy, so the precedent does not cover it. Confirmed by reading the table DDL; fixed with a parameterized `set_config` on the session. Severity: medium (reviewer: blocking, though the other half of the same thread was the reviewer's own error, see note). Why missed: the agent copied the connection pattern from a sibling step and did not read the DDL of the table it queried. Plant: a store that filters by a context variable; a test that reads it without setting the variable.

Note on C3: the reviewer opened the thread as blocking on a second claim, that the connection helper discarded the password, which was wrong; a redaction in the reviewer's own tooling had replaced `Password=` with asterisks. The reviewer retracted it in writing. Keep as a decoy if the fixture wants one: a connection string that looks redacted in one rendering and is correct in the source.

## Run-once cases

**R1. Renaming a journaled script re-runs every statement; a drop-and-add primary key is not idempotent against older tenants.**
Pattern: run-once. Before: a journaled schema script keyed on file name; it contains a `DROP CONSTRAINT IF EXISTS pk; ADD CONSTRAINT pk PRIMARY KEY (id, type)` block that ran once per tenant. Change: folds two new column scripts into that file and renames it so it re-runs everywhere. Defect: the rename re-executes the drop-and-add on every tenant, rebuilding the index each deploy; a name-only guard is wrong because tenants created before a certain date had the same constraint name on `(id)` alone, and this block is what moved them. Confirmed by reading and by querying one environment's `pg_get_constraintdef`. Severity: medium (reviewer: request with a DO-block fix comparing the definition, not the name). Why missed: the agent treated "everything in the file is idempotent" as given and did not read each statement under re-run. Plant: a shell migration with an unconditional drop-and-add and a `run_once` glob, renamed in the change.

**R2. Two open pull requests rename the same journaled script to different names.**
Pattern: run-once. Before: a function script `f_<ticketA>.sql`; another open pull request on the same target renames it to `f_<ticketB>.sql` with its own body change. Change: this pull request renames it to `f_<ticketC>.sql`. Defect: whichever merges second ships a body the first already journaled under a different name, or a name already journaled with the first's body, so the second change is silently skipped wherever the first ran; the fix is a name neither environment has seen, carrying the union of both bodies. Confirmed by reading the other pull request's file list. Severity: high (reviewer: merge-order follow-up, unresolved on purpose for visibility). Why missed: the agent checked base history for the name and not other open pull requests. Plant: two branches off the same base renaming one file to different names; the fixture's "forge export" lists the other pull request's files.

**R3. A renamed script was already deployed to an environment with a pre-fix body.**
Pattern: run-once. Before: this pull request renamed a function script to `f_<ticket>.sql` and deployed that build to a shared environment; a base commit then landed with guards the function needs. Change: the rebase carries the merged body under the same new name. Defect: the environment's journal already holds that name, so the deploy skips the file and leaves the base's guards unapplied there; a second rename (`_v2`) was required. Confirmed by reading the environment's journal table. Severity: medium (recorded by the reviewer as the outcome of the merge-order thread). Why missed: the agent checked whether the name existed at the merge-base, not whether an environment had already run it. Plant: a `data/applied.txt` journal in the fixture listing the new name, as the existing `patterns` fixture does, with the file's body differing from the journaled run.

## Base and history cases

**B1. The branch sits on a pre-rebase version of its target, so the shown diff includes unrelated deletions.**
Pattern: producer, other. Before: a feature branch targets another feature branch; the target was rebased onto the base and force-pushed. Change: none in the code; the pull request's two-dot diff now shows the target's rebase deletions as this branch's changes. Defect: the diff misleads review, and the pending rebase conflicts in a shared step file where the fetch helpers the new scenarios depend on were rewritten, so "take ours" would silently break them. Confirmed by `merge-base` against the target's old and new heads. Severity: medium (reviewer: review note; asked for re-verification of the helper semantics after the rebase). Why missed: the agent reported the branch state from the description, not from `merge-base`. Plant: a target branch with a rewritten history and a feature branch still on its old head.

**B2. A rename and a content edit in one commit break rename detection in the forge.**
Pattern: other. Before: a script `f_<old>.sql`. Change: two commits each rename the file and change its body, at 60% and 72% similarity. Defect: the forge shows delete plus add rather than rename, so the file's history breaks in that view; the fix is a rename-only commit before each edit and completing the pull request with a merge, not a squash. Confirmed by `git log --follow` and the forge's file view. Severity: low (reviewer: non-blocking, "leave it" accepted). Why missed: not a correctness defect; the agent had no rule for it. Plant: one commit that renames and edits a file below the similarity threshold.

## Hygiene cases

**H1. A test harness authenticates as the service's own read/write database account.**
Pattern: other. Before: the harness's accounts file names the service's writer role for its one database read. Change: a scenario does one `SELECT` on two columns as that account. Defect: a copy-paste into a step that runs a different statement is all it takes to write to the service's tables; a read-only role with its own secret and no bypass of row-level security gives the scenario exactly what it needs. Confirmed by reading the grants. Severity: medium (reviewer: least-privilege objection; the author created the role). Why missed: the agent reused the credential the sibling steps used. Plant: an accounts file with a writer role used by a read-only test.

**H2. Quote-doubling instead of a bound parameter in a shared step file.**
Pattern: other. Before: a query helper with no parameterized overload. Change: a step builds `WHERE hrn = '<value with '' doubled>'` for a service-minted identifier. Defect: no practical injection here, but the construction is only sound while a server setting holds, and a shared step file is where the next copy will take untrusted input; the connection is also never disposed. Confirmed by reading. Severity: low (reviewer: minor). Why missed: the agent mitigated the pattern (quote doubling) rather than replacing it. Plant: a string-concatenated query where a parameterized API exists.
